# Lesson Document Template — Complete Formatting Specification

> **Purpose:** This template defines the authoritative structure and formatting requirements for all lesson documents generated by the Professor role.
> 
> **File Location:** `curriculum/lessons/{lesson_id}/{lesson_id}.lesson.md`
> 
> **Last Updated:** 2025-12-08

---

## Document Structure Overview

Every lesson document follows this exact structure:

1. **Lesson Header** — `# {title}` from lesson.json
2. **Metadata Block** — Indented blockquote with lesson metadata
3. **Standard Opening Sections** (required, in order):
   - Why This Lesson Matters for CatchBook
   - Learning Objectives
4. **Content Sections** — Derived from lesson.json outline
5. **Checkpoints** — Inline assessments every 20 minutes
6. **Summary Section** — Required synthesis before resources
7. **Resources Section** — Required curated links at end

---

## Required Components

### 1. Lesson Header

**Location:** First line of document  
**Format:** `# {title}`  
**Source:** `title` field from `{lesson_id}.lesson.json`  
**Rules:**
- Must be exact match to lesson.json title
- No modifications or embellishments
- Single `#` (H1 heading)

**Example:**
```markdown
# Version Control Concepts and Why Git Matters
```

---

### 2. Metadata Block

**Location:** Immediately after lesson header  
**Format:** Indented blockquote with horizontal rules before and after  
**Purpose:** Human-readable metadata reference (Obsidian properties handled separately)

## Formatting Patterns

### Horizontal Rules

**Purpose:** Visual separation between major sections  
**Format:** `---` (three hyphens on their own line)

**Placement Rules:**

1. **Before metadata block** — After lesson header
2. **After metadata block** — Before first section
3. **After every major section (##)** — Before back-to-top link
4. **Before every checkpoint (###)** — Creates clear break before assessment
5. **After every checkpoint** — Before next content section
6. **Before Summary section** — Separates content from synthesis
7. **After Summary section** — Before Resources
8. **After Resources section** — End of document

**Example Pattern:**
```markdown
# Lesson Title

---

> **Lesson:** P01-M01-L01 - Title
> **Module:** P01-M01

---

## Section Content

[⬆ Back to Top](#properties)

[resources here]
```

**Consistency Rule:** Use the same pattern throughout the entire document — no exceptions.

### Back to Top Links

**Purpose:** Easy navigation back to document top  
**Format:** `[⬆ Back to Top](#properties)`  
**Emoji:** ⬆ (upward arrow)

**Placement Rules:**

1. After EVERY major section (##) — Before horizontal rule
2. After EVERY checkpoint (###) — Before horizontal rule
3. After Summary section — Before horizontal rule
4. After Resources section — End of document

**Link Behavior:**
- Links to document top (GitHub and Obsidian compatible)
- Standard markdown link syntax
- Display text: "⬆ Back to Top"
- Target: `#` (scrolls to top)

**Example:**
```markdown
## Section Title

[content]

[⬆ Back to Top](#properties)

---
```

### Emoji Usage

**Allowed Emojis:**
- ⬆ — Back to Top links only

**Prohibited:**
- No emojis in section headings
- No emojis in body content
- No decorative emojis

## Content Guidelines

### Section Depth and Length

| Section Type | Target Length | Notes |
|--------------|---------------|-------|
| Why This Matters | 10-15 lines | Context and relevance |
| Learning Objectives | 10-15 lines | 3-5 objectives total |
| Concept sections | 20-40 lines | Break into subsections if needed |
| Real-world scenarios | 15-25 lines | Concrete CatchBook examples |
| Summary | 15-25 lines | 3-7 key takeaways |
| Resources | Variable | 2-4 links per category |

### Writing Style

**Tone:**
- Conversational but precise
- Write as if teaching a friend
- Maintain technical accuracy
- Avoid condescension or oversimplification

**CatchBook Integration:**
- Every abstract concept needs a CatchBook example
- Show how concept applies to actual CatchBook features
- Reference CatchBook product spec when relevant
- Connect current lesson to CatchBook roadmap

**Progression:**
- Start simple, add complexity gradually
- Define terms before using them
- Build on previously taught concepts
- Progressive disclosure of detail

**Formatting:**
- Break long paragraphs (15+ lines) into subsections
- Use code blocks for technical examples
- Use bullet lists sparingly (prose is default)
- Avoid walls of text

### Content Transformation

**From lesson.json to lesson.md:**

1. **Outline items → Section headers (##)**
   - Each outline item becomes a major section
   - Expand outline item into 20-40 lines of content

2. **Learning objectives → Guide emphasis**
   - Objectives determine what to focus on
   - Ensure all objectives are addressed in content

3. **Professor constraints → Tone and examples**
   - Follow any specific guidance in constraints
   - Apply to writing style and example selection

4. **Assessment criteria → Checkpoint focus**
   - Use criteria to design checkpoint questions
   - Ensure questions align with assessment goals

**Example Expansion:**

Given lesson.json outline item:
```json
"Evolution of version control: CVS → SVN → Git"
```

Expand to:
- **3 subsections:** Generation 1 (Local), Generation 2 (Centralized), Generation 3 (Distributed)
- **Each subsection:** What it is, how it works, advantages, problems it solved
- **Total length:** 40-60 lines
- **Include:** Timeline markers (1970s, 1990s, 2005)
- **Conclude:** "Why this matters for CatchBook"

```markdown
## Summary

This lesson introduced you to version control concepts that will be fundamental to your entire CatchBook development journey. Understanding these foundations now will make every future lesson easier and your development process more professional.

**You've learned:**

1. **Version control** is a system for tracking changes to files over time, enabling you to revert mistakes, experiment safely, and collaborate effectively.
2. **Version control systems evolved** from local tools (RCS) to centralized systems (CVS, SVN) to distributed systems (Git, Mercurial), with each generation solving problems of the previous.
3. **Git uses a distributed architecture** where every developer has a complete copy of the repository, enabling offline work, faster operations, and more flexible workflows.
4. **Core Git concepts** include repositories (project storage), commits (snapshots of changes), branches (parallel development paths), and the staging area (change preparation).
5. **Git's snapshot model** stores complete file states at each commit rather than deltas, making operations like branching and merging fast and reliable.
6. **For CatchBook development**, Git will enable you to experiment with new features, maintain multiple versions, document your progress, and build a portfolio-worthy project history.

**Next steps:**

In the next lesson (P01-M01-L02), you'll learn the basic Git commands to initialize a repository, make commits, and view history. You'll set up your actual CatchBook repository and make your first commit.

This foundation in version control concepts will make the practical Git commands feel intuitive and purposeful, as you'll understand not just *how* to use Git, but *why* each operation matters for professional software development.
```
