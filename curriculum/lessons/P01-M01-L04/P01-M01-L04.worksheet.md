## Checkpoint 1 (20 minutes)

**Questions:**

1. You want to quickly scan the last 10 commits in your CatchBook repository to see what you worked on this week. What command would you use?

2. You see a commit hash `a3f2b9c` in `git log --oneline` output and want to see the full details of that commit. What command would you use?

3. Explain in your own words why Git uses commit hashes instead of sequential numbers (commit 1, commit 2, commit 3).

**Answers:**

1. git log --oneline -10

2. git show a3f2b9c

3. Using hashes for commits means a 40-character, unique identifier is created for each commit. (While *technically* possible to have a duplicate hash, it is astronomically *improbable* to generate a duplicate hash in the same repository). The hash is created based on the commit's content (from a snapshot of all the files to the commit message itself), which means commit's content can't be changed without changing the commit's identity. Sequential commit numbering is incapable of this.

## Checkpoint 4 (75 minutes)

**Questions:**

1. Critique this commit message and rewrite it following best practices:
   ```
   Made some changes to the API and also updated the frontend. Fixed the login button.
   ```

2. You've spent 2 hours working on CatchBook and made the following changes:
   - Added species validation to catch logger
   - Fixed a typo in README
   - Refactored database connection code
   - Added new API endpoint for weather data
   
   How many commits should this be, and why? Write appropriate commit messages for each.

3. Explain the relationship between atomic commits and Git's ability to revert changes. Why is this important for CatchBook's long-term development?

**Answers:**

1. This commit message is vague and not atomic. What are 'some changes'? What was updated on the frontend? How did you fix the login button? There are three separate commits (at minimum) here: Changes to the API, frontend update, and login button fix.

2. This should be 4 separate commits:
   - feat(catch): add species validation
   - docs(readme): fix typo
   - refactor(db): connection code
   - feat(weather): add new API endpoint

3. Atomic commits offer a more granular change and commit history to look through when looking to revert changes. If a bug is discovered and is attached to a commit that has changes to other, unrelated parts of the project, then reverting that commit may disrupt other parts of the project. Having atomic commits allows for more 'surgical' and targeted operations.
