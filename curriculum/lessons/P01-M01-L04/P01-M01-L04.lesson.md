## Reading Git History: The `git log` Command

Every commit you make creates a permanent record in Git's history. The `git log` command is your window into that history—it shows who made changes, when they were made, and what the commit messages say.

### Basic `git log`

The simplest form shows the full commit history:

```bash
git log
```

This displays commits in reverse chronological order (newest first), with each commit showing:
- **Commit hash:** A 40-character SHA-1 identifier (e.g., `a3f2b9c...`)
- **Author:** Name and email from your Git configuration
- **Date:** When the commit was created
- **Message:** The commit message you wrote

**Example output:**
```
commit a3f2b9c8d1e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8
Author: Jeff Hutting <jeff@example.com>
Date:   Mon Dec 9 14:23:45 2025 -0800

    feat(auth): add JWT token authentication
    
    Implement JWT-based auth with bcrypt password hashing.
    Add protected routes for user-specific catch data.

commit b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1
Author: Jeff Hutting <jeff@example.com>
Date:   Mon Dec 9 10:15:32 2025 -0800

    docs: create comprehensive README for CatchBook
```

While complete, this format gets verbose quickly. For navigating history, you'll usually want more concise views.

### `git log --oneline`: Compact History

The `--oneline` flag shows a condensed view—one line per commit:

```bash
git log --oneline
```

**Example output:**
```
a3f2b9c feat(auth): add JWT token authentication
b2c3d4e docs: create comprehensive README for CatchBook
c4d5e6f feat(catch): implement photo capture
d5e6f7a chore: initialize CatchBook repository
```

Each line shows:
- **Short hash:** First 7 characters of the commit hash (unique enough for most operations)
- **Subject line:** First line of the commit message

This is the view you'll use 90% of the time. It's perfect for scanning recent changes or finding a specific commit.

### `git log --graph`: Visual Branch Structure

The `--graph` flag adds ASCII art showing branch and merge history:

```bash
git log --oneline --graph
```

**Example output:**
```
* a3f2b9c feat(auth): add JWT token authentication
* b2c3d4e docs: create comprehensive README for CatchBook
| * c4d5e6f feat(catch): implement photo capture
|/  
* d5e6f7a chore: initialize CatchBook repository
```

The lines and asterisks show where branches diverged and merged. This becomes invaluable when working with feature branches (which you'll learn in Phase 2).

### `git log --all`: See Everything

By default, `git log` shows only the current branch's history. The `--all` flag shows all branches:

```bash
git log --oneline --graph --all
```

**Pro tip:** Many developers create a Git alias for this common combination:
```bash
git config --global alias.tree "log --oneline --graph --all"
```

Now you can just type `git tree` to see your full repository structure.

### Limiting Output

View just the last N commits:
```bash
git log --oneline -5  # Last 5 commits
```

View commits since a specific date:
```bash
git log --since="2 weeks ago"
git log --after="2025-12-01"
```

View commits by a specific author:
```bash
git log --author="Jeff"
```

**For CatchBook:** As your repository grows, you'll frequently use `git log --oneline` to quickly scan recent changes before starting work, and `git log --oneline --graph --all` to visualize your branch structure before merging features.

## Understanding Commit Hashes (SHA-1)

Every Git commit has a unique identifier—a 40-character hexadecimal string called a **SHA-1 hash**:

```
a3f2b9c8d1e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8
```

Git generates this hash by running SHA-1 on the commit's content:
- The snapshot of all files
- The parent commit hash(es)
- The author information
- The commit timestamp
- The commit message

**Key properties:**

1. **Deterministic:** The same content always produces the same hash
2. **Unique:** It's astronomically unlikely for two different commits to have the same hash
3. **Tamper-evident:** Changing anything about a commit changes its hash

This means commits are immutable—you can't change a commit's content without changing its identity. This is foundational to Git's data integrity.

### Short Hashes

For convenience, Git allows you to reference commits by just the first 7 characters:
```bash
git show a3f2b9c  # Instead of the full 40-character hash
```

Git uses the shortest unique prefix, which is almost always 7 characters in typical repositories. In massive repositories (Linux kernel), you might need 8-10 characters.

**For CatchBook:** You'll reference commits by short hash when inspecting specific changes, reverting mistakes, or cherry-picking commits between branches. The hash is Git's universal identifier—it works across all clones of your repository.

## Viewing Changes: `git diff`

Before committing changes, you should always preview what you're about to commit. The `git diff` command shows differences between various states of your repository.

### Three States of Files

To understand `git diff`, you need to understand Git's three states:

1. **Working directory:** Your actual files as you edit them
2. **Staging area (index):** Files you've `git add`ed, ready to commit
3. **Repository (HEAD):** The last commit on your current branch

```
Working Directory → git add → Staging Area → git commit → Repository
     (edit)                      (staged)                  (committed)
```

### `git diff`: Working vs Staging

Shows unstaged changes (what you've modified but not yet added):

```bash
git diff
```

**Example scenario:** You edit `catch_logger.py` but haven't run `git add` yet.

```diff
diff --git a/catch_logger.py b/catch_logger.py
index a3f2b9c..b4c5d6e 100644
--- a/catch_logger.py
+++ b/catch_logger.py
@@ -10,7 +10,7 @@ def log_catch(species, location):
     timestamp = datetime.now()
-    db.save(species, location, timestamp)
+    db.save(species, location, timestamp, user_id=current_user.id)
     return {"status": "success"}
```

**What this shows:**
- `---` line: The old version
- `+++` line: The new version
- `-` lines: Removed content (red in terminal)
- `+` lines: Added content (green in terminal)
- `@@` lines: Context about where in the file the change occurred

This is your chance to review changes before staging. You might notice:
- Debugging print statements you forgot to remove
- Commented-out code that should be deleted
- Changes that should be in separate commits

### `git diff --staged`: Staging vs Repository

Shows staged changes (what you've added, about to commit):

```bash
git diff --staged
# or
git diff --cached  # Same thing, historical alias
```

**When to use:** After `git add`, before `git commit`, to verify exactly what will be committed.

### `git diff HEAD`: Working vs Repository

Shows all changes—both staged and unstaged—compared to the last commit:

```bash
git diff HEAD
```

**When to use:** To see "what have I changed since my last commit?" regardless of staging status.

### Comparing Commits

Compare two specific commits:
```bash
git diff a3f2b9c b4c5d6e
```

Compare current state to a specific commit:
```bash
git diff a3f2b9c
```

**Pro tip for CatchBook:** Before every commit, run:
```bash
git diff --staged
```

This 2-second check prevents embarrassing commits like:
- Hardcoded API keys
- Print statements (`console.log`, `print("DEBUG HERE")`)
- Temporary test data
- Half-finished features

## Inspecting Specific Commits: `git show`

The `git show` command displays detailed information about a specific commit—the message, author, date, and the full diff of what changed:

```bash
git show a3f2b9c
```

**Example output:**
```
commit a3f2b9c8d1e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8
Author: Jeff Hutting <jeff@example.com>
Date:   Mon Dec 9 14:23:45 2025 -0800

    feat(auth): add JWT token authentication
    
    Implement JWT-based auth with bcrypt password hashing.
    Add protected routes for user-specific catch data.

diff --git a/auth.py b/auth.py
new file mode 100644
index 0000000..1234567
--- /dev/null
+++ b/auth.py
@@ -0,0 +1,25 @@
+import jwt
+import bcrypt
+
+def create_token(user_id):
+    payload = {"user_id": user_id}
+    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")
...
```

This is like `git log` for a single commit, but includes the actual code changes.

### When to Use `git show`

1. **Investigating bugs:** "When was this function changed? Let me see what that commit did."
2. **Code review:** "Before merging this pull request, let me see exactly what changed."
3. **Learning:** "How did I implement species identification six months ago?"
4. **Documentation:** "What was the reasoning in that commit message?"

### Showing Specific Files

You can limit `git show` to specific files:
```bash
git show a3f2b9c:auth.py  # Show auth.py as it was in that commit
```

**For CatchBook:** When debugging, you'll often use `git log --oneline` to find a suspicious commit, then `git show <hash>` to see exactly what changed. This is faster than manually comparing files.

## The `.gitignore` File: Keeping Your Repository Clean

Not every file in your project directory should be tracked by Git. Some files are generated automatically, contain secrets, or are too large to version control. The `.gitignore` file tells Git which files and directories to ignore.

### Why `.gitignore` Matters

**Files that should NEVER be committed:**

1. **Secrets:** API keys, passwords, environment variables (`.env` files)
2. **Dependencies:** `node_modules/`, Python virtual environments, package caches
3. **Build artifacts:** Compiled code, minified files, bundled assets
4. **OS files:** `.DS_Store` (macOS), `Thumbs.db` (Windows), `.swp` (Vim)
5. **IDE files:** `.vscode/`, `.idea/`, editor-specific configurations
6. **Large media:** Video files, high-res images, datasets (unless essential)
7. **Logs:** Application logs, debug files, crash reports

**Why:**
- **Security:** Committing `.env` with your OpenAI API key means anyone with repository access can steal it
- **Efficiency:** `node_modules/` can be 500MB+ and changes constantly
- **Portability:** OS and IDE files don't belong in a cross-platform project
- **Collaboration:** Dependencies are installed via `npm install` or `pip install`, not committed

**Real-world horror story:** In 2013, a developer accidentally committed AWS credentials to GitHub. Within minutes, a bot found them and spun up $50,000 worth of Bitcoin mining instances. The commit was public for less than 5 minutes.

### Creating `.gitignore`

Create `.gitignore` in your repository root:

```bash
cd ~/dev/catchbook
touch .gitignore
```

**Important:** The filename is literally `.gitignore` (with the leading dot, no file extension).

### `.gitignore` Syntax

Each line is a pattern:
```gitignore
# Comments start with #

# Ignore specific file
secret_keys.txt

# Ignore all files with extension
*.log
*.pyc

# Ignore entire directory
node_modules/
__pycache__/

# Ignore files in any directory
**/.DS_Store

# Negate a rule (track this file even though *.log is ignored)
!important.log

# Ignore files only in root directory (not subdirectories)
/config.local.js

# Ignore files in specific directory
build/*.js
```

**Pattern matching:**
- `*` matches any characters (except `/`)
- `**` matches any characters including `/` (recursive)
- `?` matches a single character
- `[abc]` matches any character in brackets

### Common `.gitignore` Patterns for CatchBook

Since CatchBook uses React Native (JavaScript/TypeScript) and Python (FastAPI backend), you need patterns for both ecosystems:

**JavaScript/React Native:**


### Retroactive `.gitignore`

If you already committed files that should be ignored, `.gitignore` won't help—Git is already tracking them. You must remove them from Git's index:

```bash
# Remove from Git, keep in working directory
git rm --cached filename

# Remove directory from Git, keep in working directory
git rm -r --cached directory/

# Then commit the removal
git commit -m "chore: remove accidentally committed node_modules"
```

**CRITICAL:** Once you've committed secrets (API keys, passwords), they're in Git history forever. Changing `.gitignore` doesn't remove them from history. If this happens:
1. Revoke/rotate the compromised credentials immediately
2. Use tools like `git filter-branch` or BFG Repo-Cleaner to rewrite history (advanced)
3. For public repos, assume the secret is compromised even if you delete it quickly

**For CatchBook:** Create `.gitignore` NOW, before committing anything sensitive. It's much easier to prevent problems than fix them later.

## Writing Professional Commit Messages

Commit messages are documentation. Six months from now, when you're debugging a CatchBook feature, clear commit messages will help you understand what changed and why. Bad messages like "fixed stuff" or "updates" are useless.

### Anatomy of a Good Commit Message

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Example:**
```
feat(catch): add AI species identification

Implement OpenAI Vision API integration for automatic species detection
from catch photos. Falls back to manual entry if API fails.

- Add species_detector.py with GPT-4 Vision integration
- Handle API errors gracefully with retry logic
- Update catch logging to accept both AI and manual species entry

Closes #23
```

### Subject Line Rules (First Line)

1. **Type prefix:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`
2. **Scope (optional):** Component affected (`catch`, `auth`, `api`)
3. **Imperative mood:** "add feature" not "added feature" or "adds feature"
4. **50 characters max:** Forces clarity
5. **No period at end:** It's a title, not a sentence
6. **Lowercase after type:** `feat(api): add endpoint` not `feat(api): Add endpoint`

**Common types:**
- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation only
- `style`: Formatting, missing semicolons (no code logic change)
- `refactor`: Code change that neither fixes bug nor adds feature
- `test`: Adding or refactoring tests
- `chore`: Maintenance tasks (dependencies, configs)

### Body Rules (Optional, After Blank Line)

- **Explain what and why, not how:** Code shows how, commit explains motivation
- **Wrap at 72 characters per line:** Readable in terminals
- **Use bullet points for multiple changes**
- **Reference issues/tickets:** `Closes #23`, `Fixes #45`

### Bad vs Good Examples

**Bad:**
```
fixed bug
```
*What bug? Where? How?*

**Good:**
```
fix(auth): prevent duplicate user registration

Add unique constraint on email field in users table.
Check for existing email before creating account.

Fixes #78
```

---

**Bad:**
```
updated files
```
*Which files? Why?*

**Good:**
```
refactor(api): extract validation logic to middleware

Move request validation from route handlers to reusable middleware
functions. This reduces code duplication and makes adding new
endpoints faster.

- Create validators.py with common validation patterns
- Update all API routes to use validation middleware
- Add tests for validation edge cases
```

---

**Bad:**
```
changes to catch logger and species detector and also fixed the thing
```
*This is multiple changes—should be multiple commits (atomic commits)*

**Good (split into two commits):**
```
Commit 1:
fix(catch): handle missing GPS coordinates gracefully

Default to manual location entry if device GPS is unavailable.
Display user-friendly error message.

---

Commit 2:
feat(species): add fallback for AI identification failures

If OpenAI API returns error, prompt user for manual species entry
rather than failing silently.
```

### Breaking Changes

If your commit introduces breaking changes (requires users to change their code), add `!` after type:

```
feat(api)!: change authentication to JWT

BREAKING CHANGE: Password-based auth is removed. All clients must
migrate to JWT tokens. See MIGRATION.md for instructions.
```

### The 50/72 Rule

- **Subject:** 50 characters max
- **Body:** 72 characters per line

**Why 50?** Git tools display subject lines in various places. Keeping them short ensures they're readable everywhere.

**Why 72?** Terminal windows default to 80 characters. With Git's indentation, 72 leaves comfortable margins.

**How to check:** Use VS Code's ruler feature or Git's built-in warnings.

### Commit Message Template

Set up a commit message template to remind yourself:

```bash
# Create template file
cat > ~/.gitmessage << 'EOF'
# <type>(<scope>): <subject>
# 
# <body>
# 
# <footer>
# 
# Types: feat, fix, docs, style, refactor, test, chore
# Scope: component affected (catch, auth, api, etc.)
# Subject: imperative, lowercase, no period, <50 chars
# Body: what and why, not how, wrap at 72 chars
# Footer: reference issues (Closes #123)
EOF

# Configure Git to use it
git config --global commit.template ~/.gitmessage
```

Now `git commit` opens your editor with this template pre-filled.

**For CatchBook:** Every commit should follow this format. As you build your portfolio, prospective employers will read your commit history. Professional messages demonstrate attention to detail and communication skills.

## Atomic Commits: One Logical Change Per Commit

An **atomic commit** contains one logical change—one complete, self-contained improvement that doesn't break the application.

### What Makes a Commit Atomic?

1. **Single purpose:** Fixes one bug or adds one feature
2. **Complete:** Leaves the code in a working state
3. **Reversible:** Can be reverted without breaking other features
4. **Testable:** Easy to verify the change works

**Good atomic commit:**
```
feat(catch): add photo upload validation

- Check image file size (max 10MB)
- Validate image format (JPEG, PNG only)
- Display clear error messages for invalid uploads

All catch logging functionality still works if validation fails.
```

**Bad non-atomic commit:**
```
- Add photo upload validation
- Fix species detector bug
- Update README
- Refactor database queries
- Change button colors in UI
```
*This is 5 separate changes. If the database refactor breaks something, you can't revert it without losing the other improvements.*

### When to Commit

**Commit when:**
- You've completed a discrete task
- Tests pass
- The application works (even if feature is incomplete)
- You're about to switch tasks
- You're ending your work session

**Don't commit when:**
- Code doesn't compile/run
- Tests are failing (unless you're specifically committing a failing test first, TDD-style)
- You're mid-refactor with files in inconsistent states
- You have unrelated changes mixed together

### Workflow for Atomic Commits

```bash
# 1. Make one logical change
# Edit species_detector.py to add fallback logic

# 2. Stage only that change
git add species_detector.py

# 3. Preview what you're committing
git diff --staged

# 4. Commit with clear message
git commit -m "feat(species): add fallback for AI identification failures"

# 5. Repeat for next change
# Edit catch_logger.py for different feature
git add catch_logger.py
git commit -m "fix(catch): handle missing GPS coordinates"
```

### Staging Partial Files

What if one file has multiple logical changes? Use `git add -p` (patch mode):

```bash
git add -p species_detector.py
```

Git will show each change and ask:
```
Stage this hunk [y,n,q,a,d,s,e,?]?
```

- `y` = yes, stage this change
- `n` = no, skip this change
- `s` = split into smaller chunks
- `q` = quit

This lets you commit line 10's bug fix now, and line 50's new feature in a separate commit.

### The "Git Tells a Story" Principle

Your commit history should read like a book:
- Chapter 1: Initialize project
- Chapter 2: Add user authentication
- Chapter 3: Implement photo upload
- Chapter 4: Add species detection

Not:
- Random changes
- Fix stuff
- More fixes
- Actually fix it this time
- Final version
- Final version 2

**For CatchBook:** Atomic commits make debugging easier. If the species detector breaks, you can use `git log -- species_detector.py` to see every change to that file, then `git revert <hash>` to undo the problematic commit without affecting other features.


## Summary

This lesson equipped you with the essential Git commands and practices for professional repository management. These aren't theoretical skills—you'll use them daily as you build CatchBook.

**You've learned:**

1. **`git log` variations** (`--oneline`, `--graph`, `--all`) let you navigate repository history efficiently. The `git log --oneline --graph --all` combination (aliased as `git tree`) is your go-to for visualizing project structure.

2. **Commit hashes** are SHA-1 identifiers that uniquely identify every commit. They're immutable and work across all repository clones, making them Git's universal reference system.

3. **`git diff`** shows changes between different states: working vs staging (`git diff`), staging vs repository (`git diff --staged`), and working vs repository (`git diff HEAD`). Reviewing diffs before committing prevents embarrassing mistakes like committed API keys.

4. **`git show`** provides detailed inspection of specific commits, including the full diff of changes. Combined with `git log`, it's your primary debugging tool for understanding when and why code changed.

5. **`.gitignore`** prevents Git from tracking files that shouldn't be versioned: dependencies (`node_modules/`, `venv/`), secrets (`.env`), build artifacts, and OS files. Create `.gitignore` early to avoid security issues and repository bloat.

6. **Professional commit messages** follow the format `<type>(<scope>): <subject>` with optional body. Subject lines use imperative mood, stay under 50 characters, and clearly describe the change. The body explains what and why, not how.

7. **Atomic commits** contain one logical change each, leaving the application in a working state. They're complete, reversible, and testable. Atomic commits make debugging easier and enable safe reverts of specific changes without affecting unrelated features.

**Next steps:**

You've completed Module P01-M01 (Git Fundamentals). Your CatchBook repository now has professional hygiene: clear history, descriptive commits, and comprehensive `.gitignore` configuration.

In the next module, you'll learn Git branching strategies, which let you work on multiple features simultaneously without conflicts. Branching is where Git's distributed architecture truly shines, enabling rapid experimentation and parallel development.

Your CatchBook repository is ready for serious development. Every commit you make from now on will follow professional standards, building a portfolio-worthy project history that demonstrates your technical discipline and communication skills.
