## Checkpoint 1: Understanding Branches (20 minutes)

### Question 1: What is a Git branch?

**Your Response:**
> A Git branch is simply a pointer to a specified commit in my repo's history. From that commit, any further commits on that branch are independent of other branches - particularly the 'main' (working) branch.

**Professor Feedback:**

Perfect! You've nailed the essential insight that branches are just lightweight pointers. Your addition about independence is excellent—this is exactly why branches enable parallel development.

**Small refinement:** When you make new commits on a branch, the branch pointer *moves forward* to point to the new commit, while other branches stay where they are. This is how divergence happens.

**Assessment:** ✅ Exceptional - Core concept mastered

---

### Question 2: Why is branch creation fast?

**Your Response:**
> Since the branch is just a pointer to a singular commit, it isn't necessary to copy any files or create separate directories.

**Professor Feedback:**

Exactly right! This is a huge conceptual shift from systems like SVN or even just manually copying directories. Creating a branch in Git is essentially just:
```
echo "commit-hash" > .git/refs/heads/new-branch-name
```

That's why you can create hundreds of branches without performance impact—it's just creating tiny pointer files, not duplicating your codebase.

**Assessment:** ✅ Exceptional - Architectural understanding demonstrated

---

### Question 3: How feature branches help CatchBook development

**Your Response:**
> Feature branches allow a developer to test new or experimental features independently of the main (working/production) branch. The new features can be merged back to the main branch once they are proven to work and don't cause any errors.

**Professor Feedback:**

Great practical understanding! You've captured the safety and experimentation aspects perfectly.

**Additional context for CatchBook:** Think about this scenario as you build across 28 phases:
- Your species identification AI is working perfectly on `main`
- You want to experiment with a new image compression library for photo uploads
- If that compression breaks something, you don't want to also break the working species ID
- Feature branch lets you isolate the experiment: `feature/photo-compression`
- Main stays stable with working species ID while you test compression
- Only merge when compression is proven

This isolation becomes *critical* when you're juggling multiple features across different phases (e.g., working on authentication in Phase 10 while refining the UI from Phase 3).

**Assessment:** ✅ Exceptional - Strategic thinking applied to CatchBook

## Checkpoint 2: Creating Branches (40 minutes)

### Question 1: Difference between `git branch` and `git checkout -b`

**Your Response:**
> `git branch <n>` creates a new branch but does not switch to it. `git checkout -b <n>` creates a new branch *and* switches to it.

**Professor Feedback:**

Perfect, concise, accurate. You've captured the exact functional difference.

**Real-world usage stats:** In professional development, `git checkout -b` is used about 90% of the time because the typical workflow is "I need to work on something new RIGHT NOW." The standalone `git branch` command is less common but has its place for batch creation or scripting.

**Assessment:** ✅ Exceptional - Precise technical understanding

---

### Question 2: When to create without switching

**Your Response:**
> Creating new branches that you know you will use later may be a reason to create a new branch and not switch to it immediately.

**Professor Feedback:**

Good thinking! Here are some concrete scenarios where this happens:

**Scenario 1 - Preparing for sprint planning:**
```bash
# Friday afternoon, planning next week's work
git branch feature/weather-api
git branch feature/species-model
git branch bugfix/photo-rotation

# Monday morning, pick one to start
git checkout feature/weather-api
```

**Scenario 2 - Creating branches from specific commits:**
```bash
# You're on main, but want a branch from 3 commits ago
git branch hotfix/security-patch HEAD~3
# Creates branch pointing to old commit, but you stay on main
```

**Scenario 3 - Scripting/automation:**
```bash
# Script that creates multiple branches for a release
for feature in auth upload species; do
  git branch release-2.0/$feature
done
```

Most of the time though, you're right—you create and immediately switch.

**Assessment:** ✅ Proficient - Good conceptual grasp with room for scenario recognition

---

### Question 3: Why Git introduced `git switch`

**Your Response:**
> The `git checkout -b <n>` command uses `git checkout` which has other functions besides creating new branches. Having `git switch` reduces confusion and creates a new command with a more narrow function focus.

**Professor Feedback:**

Excellent analysis! You've identified the core problem that Git developers were trying to solve.

**The full picture of `git checkout` confusion:**

`git checkout` does at least **4 different things**:

1. **Switch branches:** `git checkout main`
2. **Create and switch:** `git checkout -b feature/new`
3. **Restore files:** `git checkout -- file.txt` (undoes changes)
4. **Checkout specific commits:** `git checkout a3b2c1d` (detached HEAD)

This "Swiss Army knife" approach confused beginners (and veterans!). Git 2.23's solution (2019):
- `git switch` — **only** for branch operations
- `git restore` — **only** for file operations
- `git checkout` — still works (backward compatibility) but discouraged

You've touched on something important: **good tools have focused, single-purpose commands**. This is a broader software design principle that applies to CatchBook development too—when you build the API in Phase 8, you'll want endpoints that do **one thing well** rather than multi-purpose endpoints that are hard to reason about.

**Assessment:** ✅ Exceptional - Design philosophy understanding demonstrated

## Checkpoint 3: Branch Naming Conventions (60 minutes)

### Question 1: Difference between `feature/` and `hotfix/` branches

**Your Response:**
> a `feature/` branch is for when new code is adding value to the project. These branches create a safe space for experimenting with new ideas and features. `hotfix/` branches are for fixing bugs that are critical, urgent, and negatively impacting the user experience. Login, security, database errors are some examples of when a `hotfix/` branch may be used.

**Professor Feedback:**

Perfect understanding! You've captured both the **purpose** (adding value vs. critical fixes) and **urgency** (experimental vs. immediate) dimensions.

**Additional real-world context:**

The workflow differences are important:

**Feature branches:**
- Created from `main`
- Developed over days/weeks
- Go through code review
- Tested thoroughly before merge
- Example timeline: 3-7 days

**Hotfix branches:**
- Created from `main` (or production tag)
- Fixed in hours, not days
- May skip normal review process (emergency override)
- Deployed immediately
- Example timeline: 30 minutes to 4 hours

**CatchBook scenario:** Imagine you're in Phase 15, demoing CatchBook to potential users, and you discover that the species identification AI is returning wrong species 50% of the time due to an API key typo. That's a `hotfix/species-id-api-key` situation—you need it fixed NOW before the demo continues.

Meanwhile, you might also have `feature/social-sharing` in progress (adding ability to share catches on social media). That can wait—it's adding value but isn't breaking the user experience.

**Assessment:** ✅ Exceptional - Professional workflow understanding

---

### Question 2: Importance of descriptive names

**Your Response:**
> Descriptive names after the branch prefix allows for quick, at-a-glance identification on what is being worked on in each branch.

**Professor Feedback:**

Exactly right! Let me show you why this matters at scale.

**Bad branch names (imagine reviewing these 6 months later):**
```
feature/new-feature
feature/update
bugfix/fix-bug
```

**What are these?** You'd have to check commit messages or git history to understand.

**Good branch names (self-documenting):**
```
feature/species-identification-ai
feature/weather-api-integration
bugfix/photo-rotation-ios
```

**Instant clarity!** You know exactly what each branch does without investigation.

**Real CatchBook scenario (Phase 21):**

When you're preparing for deployment, you might have:
```
git branch -a
  feature/offline-mode-pwa
  feature/push-notifications
  bugfix/image-upload-timeout
  hotfix/database-connection-leak
* main
  release/v1.0-candidate
```

At a glance, you can see all active work and prioritize accordingly. This clarity is essential when managing complex projects.

**Assessment:** ✅ Exceptional - Scalability thinking demonstrated

### Question 3: Create proper branch names

**Your Response:**
- Catch statistics dashboard: `feature/catch-statistics-dashboard`
- Photo timestamp bug: `bugfix/72-photo-timestamp`
- Critical security issue: `hotfix/93-security-issue`

**Professor Feedback:**

Excellent! All three follow proper conventions. The inclusion of ticket numbers (72, 93) is particularly professional—you independently discovered a best practice that many beginners miss.

**Refinements:**

**1. Catch statistics dashboard:** ✅ Perfect as-is

**2. Photo timestamp bug:** ✅✅ Excellent with ticket number
Even more descriptive option: `bugfix/72-photo-timestamp-timezone` (adds what's specifically wrong)

**3. Critical security issue:** ✅ Good, with refinement opportunity
For security issues, be clear without being too detailed:
- `hotfix/93-login-security-patch` (tells you enough)
- `hotfix/93-auth-vulnerability` (professional)
- Avoid: `hotfix/93-sql-injection-login` (too explicit for public repos)

**The full workflow you'll use in P01-M04:**

1. Create GitHub Issue: "Photo timestamps show wrong timezone" → Issue #72
2. Create branch: `bugfix/72-photo-timestamp-timezone`
3. Make commits referencing issue:
   ```
   git commit -m "fix: correct timezone calculation for EXIF data
   
   Fixes #72"
   ```
4. When merged, GitHub automatically closes Issue #72

This creates a complete audit trail from bug report → code change → resolution.

## Checkpoint 4: Visualization and Aliases (75 minutes)

### Question 1: What `git branch -v` shows

**Your Response:**
> `git branch -v` shows the last commit on each branch, whereas `git branch` displays the branches only.

**Professor Feedback:**

Exactly right! The `-v` (verbose) flag adds the last commit hash and message.

**Pro tip - even more info:**
```bash
git branch -vv  # Double verbose shows upstream tracking info
```

This shows whether your local branch is ahead/behind the remote—extremely useful when collaborating.

**Assessment:** ✅ Exceptional - Precise understanding

---

### Question 2: Why graph visualization is more useful

**Your Response:**
> `git log --graph --all --oneline` will show the entire tree in ASCII art format, giving an easier-to-read, visual overview of the branch structure of the project.

**Professor Feedback:**

Perfect! You've identified all three key benefits:
1. **Graph visualization** (ASCII art)
2. **All branches** (not just current)
3. **Easy to read** (condensed format)

**Real CatchBook scenario (Phase 15):**

When you're working on multiple AI features simultaneously, you might see:
```
* 9h8j7k6 (HEAD -> feature/species-id-v2) Improve model accuracy
* 7f6e5d4 Add training data
| * 3c4d5e6 (feature/recommendation-engine) Implement filtering
| * 1a2b3c4 Add user preference tracking
|/
| * 5e6f7g8 (bugfix/photo-upload-timeout) Increase timeout
|/
* 2c3d4e5 (origin/main, main) Merge authentication feature
```

At a glance you know:
- Three features in active development
- Which feature you're currently on
- Where each feature diverged from main
- Main has been updated with authentication

This is essential for navigating complex development.

**Assessment:** ✅ Exceptional - Comprehensive understanding

### Question 3: Create git alias

**Your Response:**
> I created the git alias by issuing the command `git config --global alias.lg "log --graph --all --oneline --decorate"`. It worked as intended.

**Professor Feedback:**

Perfect! You didn't just write the answer—you actually ran the command and verified it works. This is exactly the hands-on approach that builds real skills.

Your alias is now saved in `~/.gitconfig` and you'll use `git lg` dozens of times per day once you're juggling multiple feature branches in Phases 8-15.

**Common aliases professional developers use:**
```bash

git config --global alias.last "log -10 --oneline"
git config --global alias.amend "commit --amend --no-edit"
```

These become muscle memory and save hundreds of keystrokes per week.
