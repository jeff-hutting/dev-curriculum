## What Are Branches? Understanding Pointers and Commit History Divergence

At its core, a Git branch is incredibly simple: **it's just a pointer to a commit**. That's it. A branch is a lightweight movable reference that points to a specific commit in your repository's history.

When you create a new branch, Git doesn't copy all your files or create a separate directory structure. Instead, it creates a new pointer. This makes branching in Git extremely fast and cheap—you can create hundreds of branches without significant performance impact.

### The Default Branch: `main`

When you initialized your CatchBook repository with `git init`, Git automatically created a branch called `main` (or `master` on older Git versions). This is your default branch—the primary line of development.

Every commit you've made so far has moved the `main` branch pointer forward:

```
main → [C3] ← HEAD
         ↑
       [C2]
         ↑
       [C1]
```

In this diagram:
- `C1`, `C2`, `C3` represent commits
- `main` points to the most recent commit (C3)
- `HEAD` (we'll discuss this soon) points to `main`

### Creating a New Branch: Divergence Begins

When you create a new branch—let's call it `feature/species-model`—Git creates a new pointer that also points to your current commit. Now you have two pointers at the same location:

```
main → [C3] ← feature/species-model ← HEAD
         ↑
       [C2]
         ↑
       [C1]
```

Nothing has changed yet—both branches point to C3. But when you make a new commit while on the `feature/species-model` branch, **only that branch moves forward**:

```
main → [C3]
         ↑
       [C2]     feature/species-model → [C4] ← HEAD
         ↑                               ↑
       [C1] ←---------------------------/
```

Now `feature/species-model` has diverged from `main`. Commit C4 exists only on the feature branch. Meanwhile, `main` still points to C3—your stable, working code is completely untouched.

### Why This Matters for CatchBook

Imagine you're building CatchBook's photo upload feature. You want to experiment with different image compression libraries without breaking the login system you just finished. Here's how branches save you:

**Without branches:** You'd need to comment out working code, make changes, test, then uncomment and restore everything. One mistake and you've broken your working app.

**With branches:** You create `feature/photo-upload`, make all your experimental changes there, test thoroughly, and only merge back to `main` when it works perfectly. Your stable code on `main` never breaks.

This is **parallel development**—the ability to work on multiple concerns simultaneously without interference. It's the foundation of professional software development.

## Creating Branches: `git branch` vs `git checkout -b`

Git provides two main ways to create branches, each with different use cases.

### Method 1: `git branch <branch-name>` (Create but Don't Switch)

The `git branch` command creates a new branch but **does not switch to it**. You remain on your current branch.

```bash
# Create a new branch
git branch feature/update-readme

# Verify it was created
git branch
```

Output:
```
  feature/update-readme
* main
```

The asterisk (*) indicates your current branch. You've created `feature/update-readme`, but you're still on `main`.

**When to use this method:**
- You want to create a branch for later use
- You're planning multiple branches and want to create them all at once
- You're scripting or automating branch creation

### Method 2: `git checkout -b <branch-name>` (Create and Switch)

This is the most common workflow. The `-b` flag tells `git checkout` to create a new branch **and immediately switch to it**:

```bash
# Create and switch in one command
git checkout -b feature/species-model

# You're now on the new branch
git branch
```

Output:
```
* feature/species-model
  main
```

Now the asterisk is next to `feature/species-model`—you're on the new branch and ready to work.

**When to use this method:**
- You want to start working on a new feature immediately (most common)
- You're following a feature branch workflow
- You want fewer commands to type

### Modern Alternative: `git switch`

Git 2.23 (released 2019) introduced a clearer command for switching branches:

```bash
# Create and switch (equivalent to checkout -b)
git switch -c feature/ui-redesign

# The -c flag means "create"
```

The `git switch` command was introduced because `git checkout` does multiple things (switching branches, restoring files, creating branches), which can be confusing. `git switch` is specifically for branch operations.

**Both work identically—use whichever feels clearer to you.** Throughout this curriculum, you'll see both, as they're both widely used in the industry.

### Branch Naming: What's Valid?

Git branch names must follow these rules:
- Cannot start with a slash or contain `..`
- Cannot contain spaces (use hyphens or underscores)
- Cannot contain special characters like `~`, `^`, `:`, `?`, `*`, `[`
- Should be descriptive and purposeful

**Valid branch names:**
```
feature/photo-upload
bugfix/login-error
hotfix/security-patch
jeff/experiment-with-ai
v2.0-development
```

**Invalid branch names:**
```
my feature        (contains space)
feature..name     (contains ..)
/feature-name     (starts with /)
feature/name*     (contains *)
```

## The HEAD Pointer: Tracking Your Current Location

Understanding `HEAD` is crucial to understanding how Git branches work. **HEAD is Git's way of tracking where you are right now.**

### What is HEAD?

`HEAD` is a special pointer that indicates:
1. Which branch you're currently on
2. Which commit is currently "checked out" in your working directory

In most cases, HEAD points to a branch, and that branch points to a commit:

```
HEAD → main → [C3]
                ↑
              [C2]
                ↑
              [C1]
```

When you make a commit, Git:
1. Creates the new commit
2. Moves the branch pointer to the new commit
3. HEAD follows the branch (because HEAD points to the branch)

### HEAD Follows Your Moves

When you switch branches, HEAD moves:

```bash
# You're on main
git branch
# * main
#   feature/photo-upload

# Switch to feature branch
git checkout feature/photo-upload

# Now HEAD points to feature/photo-upload
```

Internally:
```
Before:  HEAD → main → [C3]

After:   main → [C3]
         HEAD → feature/photo-upload → [C3]
```

### Viewing HEAD's Current Position

You can always see where HEAD points:

```bash
# Show current branch
git branch
# * feature/photo-upload  ← asterisk shows HEAD location
#   main

# Or more explicitly
git rev-parse HEAD
# Shows the commit hash HEAD points to
```

### Why HEAD Matters for CatchBook Development

Imagine you're working on CatchBook's species identification feature when you realize there's a critical bug in the login system (which is already on `main`). Here's how HEAD helps you context-switch quickly:

1. You're on `feature/species-id` (HEAD → feature/species-id)
2. You switch to `main` (HEAD → main)
3. Git instantly updates your working directory to match main's state
4. You fix the bug, commit on main
5. You switch back to `feature/species-id` (HEAD → feature/species-id)
6. Git restores your species identification work exactly as you left it

HEAD is the mechanism that makes this seamless branch switching possible. It's Git's mental model of "where you are" in your repository.

## Branch Naming Conventions: feature/, bugfix/, hotfix/

Professional development teams use **branch naming conventions** to make the purpose of each branch immediately clear. This becomes essential when you have dozens of branches in active development.

### Standard Prefixes

The most common convention uses prefixes to categorize branches:

#### `feature/` — New Functionality

Use for branches that add new capabilities to CatchBook:

```
feature/photo-upload
feature/species-ai-model
feature/weather-integration
feature/user-authentication
feature/catch-statistics-dashboard
```

**When to use:** Any time you're building something new that adds value to the product.

#### `bugfix/` — Non-Critical Bug Fixes

Use for fixing bugs that aren't urgent:

```
bugfix/login-validation
bugfix/photo-rotation-error
bugfix/timezone-calculation
bugfix/missing-species-icon
```

**When to use:** You've found a bug that needs fixing but doesn't break core functionality or pose a security risk.

#### `hotfix/` — Critical Production Fixes

Use for urgent fixes that need to go to production immediately:

```
hotfix/security-vulnerability
hotfix/crash-on-ios-upload
hotfix/data-loss-prevention
hotfix/api-rate-limit-error
```

**When to use:** Something is broken in production and users are affected. These branches often merge directly to `main` and skip the normal review process due to urgency.

#### Other Common Prefixes

```
chore/update-dependencies      # Maintenance work
docs/api-documentation         # Documentation updates
refactor/simplify-auth-logic   # Code improvement without new features
test/add-species-id-tests      # Adding test coverage
experiment/try-new-ui-library  # Exploratory work (might be deleted)
```

### Descriptive Names

After the prefix, use descriptive names that explain **what** you're doing:

**Good:**
```
feature/add-species-identification
bugfix/fix-photo-upload-timeout
hotfix/prevent-data-corruption
```

**Bad (too vague):**
```
feature/new-stuff
bugfix/fix-bug
hotfix/update
```

### Including Issue/Ticket Numbers

If you're using GitHub Issues (which you'll learn in P01-M04), include the issue number:

```
feature/23-add-weather-api
bugfix/45-fix-login-error
hotfix/67-security-patch
```

This creates a direct link between the code change and the issue that requested it.

### For CatchBook Development

As you build CatchBook across 28 phases, you'll create dozens of feature branches. Here are some you'll likely use:

```
Phase 3:  feature/landing-page-design
Phase 8:  feature/rest-api-catches-endpoint
Phase 10: feature/jwt-authentication
Phase 15: feature/species-identification-ai
Phase 17: feature/weather-api-integration
Phase 23: feature/pwa-offline-mode
Phase 27: feature/ios-app-release
```

Using this convention from day one makes your repository professional and your development history clear.

## Listing Branches: `git branch`, `git branch -a`, `git branch -v`

As your CatchBook repository grows, you'll accumulate branches. Git provides several ways to view them.

### Basic Branch Listing: `git branch`

The simplest command shows all local branches:

```bash
git branch
```

Output:
```
  feature/photo-upload
  feature/species-model
* main
```

The asterisk (*) marks your current branch (where HEAD points).

### Showing Remote Branches: `git branch -r`

When working with GitHub, you'll have remote branches (branches that exist on GitHub but may not be on your local machine):

```bash
git branch -r
```

Output:
```
  origin/main
  origin/feature/photo-upload
  origin/feature/species-model
```

The `origin/` prefix indicates these branches exist on the remote repository (GitHub).

### All Branches (Local + Remote): `git branch -a`

To see everything:

```bash
git branch -a
```

Output:
```
  feature/photo-upload
  feature/species-model
* main
  remotes/origin/HEAD -> origin/main
  remotes/origin/feature/photo-upload
  remotes/origin/main
```

This shows both local branches and remote-tracking branches.

### Verbose Mode: `git branch -v`

Add `-v` to see the last commit on each branch:

```bash
git branch -v
```

Output:
```
  feature/photo-upload  a3b2c1d Add image compression
  feature/species-model 7f8e9a0 Implement AI model
* main                  2c3d4e5 Update README
```

This is useful for quickly seeing what work has been done on each branch.

### Combining Flags

You can combine flags:

```bash
# Show all branches with last commit info
git branch -av
```

This gives you a comprehensive view of your entire branch structure.

## Visualizing Branches: `git log --graph --all --oneline`

Text listings are useful, but visualizing your branch structure makes the relationships between branches crystal clear.

### Basic Log: Linear History

On a single branch, `git log` shows a linear history:

```bash
git log --oneline
```

Output:
```
2c3d4e5 (HEAD -> main) Update README
1b2a3c4 Add .gitignore
9f8e7d6 Initial commit
```

This shows commits in reverse chronological order (newest first).

### Graph View: Branch Visualization

Add `--graph` to see the branch structure:

```bash
git log --graph --oneline
```

Output with a feature branch:
```
* a3b2c1d (HEAD -> feature/photo-upload) Add image compression
* 7f8e9a0 Implement upload endpoint
| * 2c3d4e5 (main) Update README
|/
* 1b2a3c4 Add .gitignore
* 9f8e7d6 Initial commit
```

The ASCII art shows:
- `*` represents a commit
- `|` shows a branch line
- `/` shows where branches diverged

### All Branches: `--all` Flag

By default, `git log` only shows history for your current branch. Add `--all` to see all branches:

```bash
git log --graph --all --oneline
```

This is the command you'll use most often to understand your repository structure.

### Full Command for Maximum Insight

Here's the full command with useful formatting:

```bash
git log --graph --all --oneline --decorate
```

Output:
```
* a3b2c1d (HEAD -> feature/photo-upload) Add image compression
* 7f8e9a0 Implement upload endpoint
| * 5e6f7g8 (feature/species-model) Add species database
| * 3d4e5f6 Train AI model
|/
* 2c3d4e5 (main) Update README
* 1b2a3c4 Add .gitignore
* 9f8e7d6 Initial commit
```

The `--decorate` flag shows branch names and HEAD position inline with commits.

### Creating a Git Alias

You'll use this command so often it's worth creating an alias. Add this to your `~/.gitconfig`:

```bash
git config --global alias.lg "log --graph --all --oneline --decorate"
```

Now you can just type:

```bash
git lg
```

This is a command professional developers use dozens of times per day.

### Interpreting the Graph for CatchBook

When developing CatchBook, you might see a structure like this:

```
* 9h8j7k6 (HEAD -> feature/photo-upload) Complete upload feature
* 7f6e5d4 Add tests
| * 3c4d5e6 (feature/species-ai) Train model
| * 1a2b3c4 Add dataset
|/
* 5e6f7g8 (main) Merge authentication feature
* 2c3d4e5 Add user login
* 1b2a3c4 Initial commit
```

This tells you:
1. `main` is at "Merge authentication feature"
2. Two feature branches (`photo-upload` and `species-ai`) diverged from this point
3. You're currently on `photo-upload` (HEAD indicator)
4. Both features are in active development
5. When ready, both will merge back to `main`

Being able to visualize this structure helps you understand where your work fits in the larger CatchBook development timeline.

## Understanding Detached HEAD State (Common Pitfall)

There's one branch-related scenario that confuses beginners: **detached HEAD state**. It's worth understanding now so you don't panic when it happens.

### What is Detached HEAD?

Remember that normally, HEAD points to a branch, and the branch points to a commit:

```
HEAD → main → [C3]
```

A **detached HEAD** occurs when HEAD points directly to a commit instead of a branch:

```
HEAD → [C2]
        ↓
main → [C3]
```

In this state, you're "floating" at a specific commit with no branch attached.

### How Does This Happen?

Detached HEAD typically occurs when you checkout a specific commit by its hash:

```bash
# This creates detached HEAD
git checkout a3b2c1d

# Git warns you:
# You are in 'detached HEAD' state...
```

Or when checking out a remote branch without creating a local branch:

```bash
# Also creates detached HEAD
git checkout origin/feature/photo-upload
```

### Why It's "Dangerous"

In detached HEAD state, any commits you make won't belong to any branch. If you switch branches, those commits can become orphaned and eventually be garbage collected (deleted).

Example:
```bash
# In detached HEAD state
git checkout a3b2c1d

# Make a commit
git commit -m "Experimental change"

# Switch back to main
git checkout main

# Your experimental commit is now orphaned (no branch points to it)
```

### How to Fix It

If you realize you're in detached HEAD and want to keep your work, create a branch:

```bash
# While in detached HEAD, create a branch
git checkout -b feature/save-my-work

# Or more explicitly
git branch feature/save-my-work
git checkout feature/save-my-work
```

Now your commits are safe on a named branch.

### When Detached HEAD is Useful

Detached HEAD isn't always bad. It's useful for:
- Inspecting old code states without affecting branches
- Running tests on historical commits
- Bisecting to find bugs (git bisect uses detached HEAD)

Just remember: **if you want to keep commits, make sure HEAD points to a branch**.

### For CatchBook Development

You probably won't encounter detached HEAD often in normal CatchBook development. But if you see this warning:

```
You are in 'detached HEAD' state. You can look around, make experimental
changes and commit them, and you can discard any commits you make in this
state without impacting any branches...
```

Now you'll know what it means and how to recover.

## Deleting Branches: `git branch -d` vs `git branch -D`

Eventually, you'll finish a feature and merge it to `main`. At that point, the feature branch has served its purpose and can be deleted.

### Safe Delete: `git branch -d`

The `-d` flag (lowercase) performs a **safe delete**:

```bash
# Delete a fully merged branch
git branch -d feature/photo-upload
```

Git checks if the branch has been merged to your current branch. If it hasn't, Git refuses to delete it:

```
error: The branch 'feature/photo-upload' is not fully merged.
If you are sure you want to delete it, run 'git branch -D feature/photo-upload'.
```

This safety check prevents you from accidentally losing work.

### Force Delete: `git branch -D`

The `-D` flag (uppercase) performs a **force delete**:

```bash
# Delete branch regardless of merge status
git branch -D feature/abandoned-experiment
```

This deletes the branch even if it hasn't been merged. Use this for:
- Abandoned experiments you don't want to keep
- Prototype branches that didn't work out
- Branches you created by mistake

**Warning:** Force delete is permanent. Make sure you really want to discard that work.

### Deleting Remote Branches

To delete a branch on GitHub (the remote repository):

```bash
# Delete remote branch
git push origin --delete feature/photo-upload
```

This is typically done after merging a pull request on GitHub.

### Workflow Example for CatchBook

```bash
# Create feature branch
git checkout -b feature/weather-integration

# Work on feature, make commits
git add .
git commit -m "feat(weather): integrate OpenWeather API"

# Push to GitHub, open pull request, get it merged

# Switch back to main and pull the merged code
git checkout main
git pull origin main

# Delete local feature branch (safe delete)
git branch -d feature/weather-integration

# Delete remote feature branch
git push origin --delete feature/weather-integration
```

This keeps your repository clean by removing branches that are no longer needed.

### Viewing Merged vs Unmerged Branches

Git can show you which branches have been merged:

```bash
# Show branches merged into current branch
git branch --merged

# Show branches not yet merged
git branch --no-merged
```

This helps you identify which feature branches are safe to delete.

## Summary

This lesson introduced Git branching—one of the most powerful features you'll use throughout CatchBook development. Understanding branches transforms Git from a simple backup tool into a professional development workflow system.

**You've learned:**

1. **Branches are lightweight pointers** to commits, not copies of files. This makes creating and switching branches extremely fast and enables fearless experimentation.

2. **The HEAD pointer tracks your current location** in the repository. When you switch branches, HEAD moves, and Git updates your working directory to match that branch's state.

3. **Creating branches** can be done with `git branch <name>` (create only) or `git checkout -b <name>` (create and switch). The modern `git switch -c <name>` command is also available and often clearer.

4. **Branch naming conventions** (feature/, bugfix/, hotfix/) make the purpose of each branch immediately clear and keep repositories organized as they scale.

5. **Listing branches** with `git branch`, `git branch -v`, and `git branch -a` helps you navigate complex repositories with many active branches.

6. **Visualizing branch structure** with `git log --graph --all --oneline --decorate` makes the relationships between branches clear and helps you understand project history.

7. **Detached HEAD state** occurs when HEAD points directly to a commit instead of a branch. While usually unintentional, it can be recovered by creating a new branch from that commit.

8. **Deleting branches** with `git branch -d` (safe) or `git branch -D` (force) keeps your repository clean after features are merged.

**Next steps:**

In P01-M02-L02, you'll learn how to push your feature branches to GitHub and create pull requests—the professional workflow for proposing changes and collaborating with others. You'll open your first PR for the CatchBook documentation update you just made.

You now have the foundational branching skills that will structure every feature you build across CatchBook's 28-phase development journey. Every new capability—species identification, weather integration, authentication, mobile apps—will start with a feature branch and merge back to main when complete.
