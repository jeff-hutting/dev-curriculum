## What is Merging? Integrating Divergent Branch Histories

When you create a feature branch in CatchBook, you're creating a parallel timeline. While you work on `feature/species-identification`, someone else (or future you) might be working on `feature/weather-api` or making hotfixes directly to `main`. Eventually, these timelines need to converge.

**Merging** is the process of integrating changes from one branch into another. Most commonly, you'll merge feature branches into `main`:

```
feature/update-readme  →  main
feature/species-id     →  main
feature/weather-api    →  main
```

But merging can happen in any direction:
- `main` into `feature/long-running-branch` (to sync with latest changes)
- `develop` into `feature/branch` (if using Git Flow)
- `hotfix/bug-123` into `main` and `develop` (critical fixes)

### What Happens During a Merge?

Git performs three fundamental operations:

1. **Identifies the common ancestor** — The commit where the branches diverged
2. **Compares the changes** — What changed in each branch since divergence
3. **Combines the changes** — Creates a new state that includes both sets of modifications

The *how* of step 3 depends on your merge strategy. Let's explore the three main approaches.

## Merge Strategy 1: Merge Commit (Preserves Full History)

A **merge commit** is the default Git merge behavior. It creates a new commit that has two parents: the tip of your feature branch and the tip of the target branch (usually `main`).

### How It Works

```
Before merge:
       C---D  feature/update-readme
      /
 A---B        main

After merge commit:
       C---D
      /     \
 A---B-------E  main  (E is the merge commit)
```

Commit `E` contains all changes from both branches and explicitly records that a merge occurred.

### Anatomy of a Merge Commit

```bash
commit e7f8a9b (main)
Merge: b2c3d4e d5e6f7a
Author: Jeff Hutting <jeff@example.com>
Date:   Wed Jan 8 10:30:00 2025 -0800

    Merge branch 'feature/update-readme' into main
```

Notice the `Merge:` line showing two parent commits—this is the signature of a merge commit.

### When to Use Merge Commits for CatchBook

**Use merge commits when:**
- You want to preserve the complete development history
- The feature branch has meaningful, well-crafted commits you want to keep
- You're merging a long-running branch with significant work
- Multiple developers collaborated on the feature

**Example CatchBook scenarios:**
- Merging `feature/ai-species-identification` (Phase 15-16, months of work)
- Merging `feature/mobile-pwa-conversion` (Phase 23, major architectural change)
- Release branches into `main` (preserves all QA fixes and adjustments)

### Advantages
- Complete audit trail of development
- Easy to see when features were integrated
- Can revert entire feature with one command: `git revert -m 1 <merge-commit>`

### Disadvantages
- Git log becomes cluttered with merge commits
- Harder to follow linear history
- "Messy" appearance if many small features are merged

## Merge Strategy 2: Squash and Merge (Clean Linear History)

**Squash and merge** takes all commits from your feature branch and combines them into a single commit on the target branch. The feature branch's individual commits disappear from the main timeline.

### How It Works

```
Before squash:
       C---D---E  feature/update-readme
      /
 A---B            main

After squash and merge:
 A---B---F        main  (F contains changes from C+D+E combined)
 
 (feature/update-readme still exists but won't be in main's history)
```

Commit `F` has only one parent (`B`) and contains all changes from commits `C`, `D`, and `E` combined into a single commit.

### What Gets Squashed?

All commits from your feature branch merge into one. If your feature branch had:
```
- feat: add species field to catch model
- fix: correct validation logic
- docs: update API documentation
- style: format code
```

After squashing, you get one commit:
```
- feat: add species identification to catch logging (#42)
```

The individual commits are "squashed" together like compressing a spring.

### When to Use Squash for CatchBook

**Use squash and merge when:**
- Feature branch has messy WIP commits ("fix typo", "forgot semicolon", "actually fixed it this time")
- You want a clean, linear main branch history
- Individual commits aren't meaningful outside the PR context
- Feature is small to medium-sized

**Example CatchBook scenarios:**
- Merging `feature/update-readme` (this lesson's hands-on exercise)
- Merging `feature/fix-timezone-bug` (small bug fix with 3-4 commits)
- Merging `feature/add-email-validation` (straightforward feature)

**This is GitHub's recommended default** and what we'll use for most CatchBook feature branches.

### Advantages
- Clean, linear main branch history (one commit per feature)
- Easy to understand what changed and when
- Git log is readable and professional
- Individual commit messages can be sloppy (they disappear)

### Disadvantages
- Loses individual commit history (can't see how feature evolved)
- Can't cherry-pick individual commits from the feature
- If you need to revert, you revert the entire feature at once

## Merge Strategy 3: Rebase and Merge (Linear History, Preserves Commits)

**Rebase and merge** replays your feature branch commits on top of the target branch, then fast-forwards the target. The result is a linear history with all individual commits preserved.

### How It Works

```
Before rebase:
       C---D  feature/update-readme
      /
 A---B        main

After rebase and merge:
 A---B---C'---D'  main  (C' and D' are replayed commits)

(Original C and D exist on feature branch but aren't in main's history)
```

Git "replays" each commit from your feature branch as if you had made them directly on `main`. The commits get new hashes (`C'`, `D'`) because their parent changed.

### When to Use Rebase for CatchBook

**Use rebase when:**
- You want linear history AND meaningful individual commits
- Feature branch commits are well-crafted and tell a story
- You're comfortable with Git internals (rebase rewrites history)

**Example CatchBook scenarios:**
- Merging well-documented infrastructure changes
- Educational codebases where commit-by-commit progression matters
- When main branch moved ahead and you need to update your feature branch first

**Important:** We'll defer deep rebase coverage to Phase 25 (Advanced Git Topics). For now, stick with squash or merge commit for CatchBook.

### Why Defer Rebase?

Rebasing rewrites history and can be destructive if misused. Until you're comfortable with Git fundamentals, **squash and merge** gives you 90% of rebase's benefits without the risk.

## Fast-Forward Merges vs Three-Way Merges

Not all merges are created equal. Git chooses between two merge mechanisms based on whether the branches have diverged.

### Fast-Forward Merge: No Divergence

If `main` hasn't changed since you created your feature branch, Git can simply "fast-forward" `main` to point at your feature branch's latest commit:

```
Before (main hasn't moved):
 A---B        main
      \
       C---D  feature/update-readme

After fast-forward:
 A---B---C---D  main, feature/update-readme
```

No merge commit is created because there's nothing to merge—`main` just moves forward.

**Fast-forward characteristics:**
- No merge commit (unless you force one with `--no-ff`)
- Clean, linear history
- Only possible if target branch hasn't changed

**In practice:** Rare in collaborative projects because `main` usually has new commits by the time you finish your feature.

### Three-Way Merge: Branches Diverged

If `main` has new commits since you created your feature branch, Git must perform a **three-way merge**:

```
Before (main has moved ahead):
       C---D  feature/update-readme
      /
 A---B---E---F  main

After three-way merge:
       C---D
      /     \
 A---B---E---F---G  main  (G is merge commit)
```

Git compares three commits:
1. **Common ancestor** (`B`) — where branches diverged
2. **Feature branch tip** (`D`) — your changes
3. **Main branch tip** (`F`) — changes that happened on main

Then creates merge commit `G` that combines both sets of changes.

**Why "three-way"?** Because Git examines three points in history to determine what changed.

### Force a Merge Commit with `--no-ff`

Even if a fast-forward is possible, you can force a merge commit:

```bash
git merge --no-ff feature/update-readme
```

This creates an explicit merge commit even when branches haven't diverged. Some teams prefer this for a clearer feature integration history.

**For CatchBook:** GitHub's squash-and-merge makes this decision for you—it always creates a single commit regardless of fast-forward possibility.

## What Are Merge Conflicts? Same File, Same Lines, Different Changes

A **merge conflict** occurs when:
1. Two branches modify the **same lines** in the **same file**, and
2. Git can't automatically determine which change to keep

### Example CatchBook Conflict Scenario

You're working on `feature/update-readme` and modify the README introduction. Meanwhile, someone else (or you on a different branch) also modifies the same README section on `main`. When you try to merge, Git says:

```
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

### What Git Can Auto-Merge

Git successfully merges:
- Changes to different files (`api.py` vs `README.md`)
- Changes to different sections of the same file
- One branch added lines, the other branch didn't touch them

### What Causes Conflicts

**Conflicts happen when both branches modify:**
- The same line with different content
- Adjacent lines in incompatible ways
- One branch deletes a section the other branch modifies

**Important:** Conflicts are normal in collaborative development. They're not errors—they're Git asking you to make a decision.

### Conflict Frequency in CatchBook

As you build CatchBook across 28 phases:
- **Frequent conflicts:** Documentation files (README, CHANGELOG)
- **Occasional conflicts:** Configuration files (package.json, requirements.txt)
- **Rare conflicts:** Isolated feature code (components, utilities)

Good branch strategy and small, focused PRs minimize conflicts.

## Anatomy of a Conflict Marker

When Git encounters a conflict, it annotates the file with **conflict markers** showing both versions:

```markdown
# CatchBook

<<<<<<< HEAD
AI-powered fishing journal with photo-based catch logging and predictive intelligence.
=======
Smart fishing journal that uses AI to log catches from photos automatically.
>>>>>>> feature/update-readme
```

### Breaking Down the Markers

```
<<<<<<< HEAD
[Current branch content]
=======
[Incoming branch content]
>>>>>>> feature/update-readme
```

**Components:**

1. **`<<<<<<< HEAD`** — Start of conflict, followed by the current branch's version
   - `HEAD` represents the branch you're merging *into* (usually `main`)

2. **`=======`** — Separator between the two versions

3. **`>>>>>>> feature/update-readme`** — End of conflict, preceded by the incoming branch's version
   - Shows the branch you're merging *from*

### What You Must Do

**Choose one:**
- Keep `HEAD` version (current branch)
- Keep incoming version (feature branch)
- Keep both (if they can coexist)
- Write entirely new content (combining both manually)

Then **delete the conflict markers** (`<<<<<<<`, `=======`, `>>>>>>>`). Git won't let you commit until you do.

## Resolving Conflicts in VS Code: Visual Merge Tool

VS Code provides the most beginner-friendly conflict resolution interface. When you open a file with conflicts, you'll see:

### VS Code Conflict UI

```markdown
# CatchBook

<<<<<<< HEAD (Current Change)
AI-powered fishing journal with photo-based catch logging and predictive intelligence.
||||||| merged common ancestors
Original fishing journal for kayak anglers.
=======
Smart fishing journal that uses AI to log catches from photos automatically.
>>>>>>> feature/update-readme (Incoming Change)
```

**VS Code adds clickable buttons above the conflict:**

```
Accept Current Change | Accept Incoming Change | Accept Both Changes | Compare Changes
```

### Four Resolution Options

**1. Accept Current Change**
- Keeps the `HEAD` version (what's currently in `main`)
- Discards the feature branch version
- Click this when your feature branch changes were wrong/outdated

**2. Accept Incoming Change**
- Keeps the feature branch version
- Discards the `main` version
- Click this when your feature is the correct/newer version

**3. Accept Both Changes**
- Keeps both versions, one after the other
- Removes conflict markers but preserves both texts
- Useful when both changes are valid additions

**4. Compare Changes**
- Opens side-by-side diff view
- Shows exactly what each version contains
- Best for understanding complex conflicts before deciding

### After Clicking a Button

VS Code:
1. Removes conflict markers automatically
2. Keeps the version(s) you selected
3. File is now "resolved" but not yet staged
4. You still need to `git add` the file and commit

### Manual Editing

You can also:
- Ignore the buttons and manually edit the file
- Combine parts from both versions
- Write entirely new content

Just make sure to delete all conflict markers before saving.

## Resolving Conflicts on Command Line: Manual Editing

While VS Code is recommended, you should understand the command-line workflow for when you don't have a GUI available.

### Step-by-Step Command Line Resolution

**1. Git tells you there's a conflict:**

```bash
$ git merge feature/update-readme
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.
```

**2. Check which files have conflicts:**

```bash
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   README.md
```

**3. Open the conflicted file in any editor:**

```bash
$ nano README.md
# or
$ vim README.md
# or
$ code README.md  # opens VS Code
```

**4. Find and resolve conflicts manually:**

Look for `<<<<<<<`, `=======`, `>>>>>>>` markers. Edit the file to keep what you want and delete all markers.

**Before (with conflict markers):**
```markdown
<<<<<<< HEAD
AI-powered fishing journal with photo-based catch logging.
=======
Smart fishing journal that uses AI to log catches from photos.
>>>>>>> feature/update-readme
```

**After (conflict resolved):**
```markdown
AI-powered fishing journal with photo-based catch logging and predictive intelligence.
```

**5. Stage the resolved file:**

```bash
$ git add README.md
```

**6. Complete the merge with a commit:**

```bash
$ git commit
# Git opens your editor with a pre-filled merge commit message
```

Or write your own message:

```bash
$ git commit -m "Merge feature/update-readme, resolved README conflict"
```

### Aborting a Merge

If you realize mid-conflict that you're not ready to resolve:

```bash
$ git merge --abort
```

This returns your repository to the state before you started the merge. No harm done—you can try again later.

## Testing After Merge: Always Verify Functionality

**Critical rule:** Never merge code without testing that it still works.

### Why Testing Matters

After resolving a conflict, your code *might*:
- Run perfectly (you combined changes correctly)
- Have syntax errors (you left a conflict marker by accident)
- Have logical errors (both changes work individually but conflict when combined)
- Break tests (changes were incompatible in non-obvious ways)

### Post-Merge Testing Checklist for CatchBook

**1. Visual inspection of resolved files:**
```bash
git diff HEAD~1 README.md  # Compare to before merge
```

Check that no conflict markers remain:
```bash
grep -n "<<<<<<< HEAD" README.md  # Should return nothing
```

**2. Run the application:**
```bash
npm run dev  # or python manage.py runserver, depending on phase
```

Visit `http://localhost:3000` and verify:
- Application starts without errors
- Pages load correctly
- No console errors in browser DevTools

**3. Run automated tests (when you have them):**
```bash
npm test  # Phase 19-20 (Testing & Quality)
```

**4. Manual smoke test of affected features:**

If you merged a species identification PR:
- Upload a test photo
- Verify species detection works
- Check that data saves correctly

### When Tests Fail Post-Merge

If something breaks after merging:

**Option 1: Fix forward**
```bash
# Make corrections
git add .
git commit -m "fix: correct post-merge integration issue in species detection"
```

**Option 2: Revert the merge**
```bash
git revert -m 1 HEAD  # Reverts the merge commit
```

This creates a new commit that undoes the merge. Then you can fix the conflict on the feature branch and try again.

2. Click "Pull requests" tab

```
Merge pull request ▼
  ├─ Create a merge commit
  ├─ Squash and merge  ← CHOOSE THIS for CatchBook
```

**For CatchBook feature branches, always choose "Squash and merge"** unless you have a specific reason to preserve individual commits.

GitHub pre-fills a commit message with your PR title and all individual commits. Edit it:

Click "Confirm squash and merge"

1. Combines all commits from your feature branch into one
2. Merges that single commit into `main`
3. Closes the pull request
4. Optionally deletes the feature branch

### Step 7: Pull Latest Main Locally

```bash
git checkout main
git pull origin main
```

Your local `main` now has the squashed commit from the PR.

## Cleaning Up: Delete Local and Remote Feature Branches

After merging, your feature branch is no longer needed. Clean it up to keep your repository tidy.

### Delete Local Branch

```bash
git branch -d feature/update-readme
```

**Expected output:**
```
Deleted branch feature/update-readme (was a1b2c3d).
```

**Why `-d` (lowercase)?** This is the "safe" delete—Git won't let you delete a branch with unmerged changes.

If Git complains the branch isn't merged, you can force delete with `-D`:
```bash
git branch -D feature/abandoned-experiment
```

But only do this if you're certain you want to discard the work.

### Delete Remote Branch

If you didn't check "Delete branch" on GitHub after merging:

```bash
git push -d origin feature/update-readme
```

Or using the alternative syntax:
```bash
git push origin :feature/update-readme
```

**Why delete remote branches?** They clutter your repository's branch list and serve no purpose after merging.

### Verify Branch Cleanup

```bash
git branch -a
```

You should see:
- `main` (local)
- `remotes/origin/main` (remote)

Your feature branch should be gone from both local and remote.

## Post-Merge Workflow: Pull Main, Verify, Delete Local Branch

Here's the complete end-to-end workflow you'll use for every CatchBook feature after merging:

### The Standard Post-Merge Ritual

**1. Switch to main:**
```bash
git checkout main
```

**2. Pull the merged changes from GitHub:**
```bash
git pull origin main
```

This fetches and merges the squashed commit that GitHub created.

**3. Verify the merge:**
```bash
git log --oneline -5
```

You should see your squashed commit at the top.

**4. Delete the local feature branch:**
```bash
git branch -d feature/update-readme
```

**5. Verify branch cleanup:**
```bash
git branch -a
```

**6. Start your next feature from updated main:**
```bash
git checkout -b feature/next-task
```

### Why This Sequence Matters

**If you skip step 2 (pulling main):**
- Your local `main` is outdated
- New feature branches start from wrong base
- You'll create merge conflicts with your own merged work

**If you skip step 4 (deleting branch):**
- `git branch` list becomes cluttered
- Temptation to accidentally reuse old branch
- Confusion about which branches are active

**If you skip step 6 (new branch from main):**
- You might accidentally commit directly to `main`
- Your workflow becomes inconsistent
- Risk of mixing features

### Muscle Memory Goal

This sequence should become automatic after every PR merge:

```bash
git checkout main && git pull origin main && git branch -d feature/old-branch && git checkout -b feature/new-branch
```

By the time you finish CatchBook Phase 28, you'll type this without thinking.

## Summary

This lesson equipped you with the skills to safely integrate CatchBook features through multiple merge strategies and conflict resolution techniques. You've moved from theoretical branching to practical production workflows.

**You've learned:**

1. **Three merge strategies exist** (merge commit, squash, rebase), each with specific use cases. Squash-and-merge is the default for CatchBook feature branches because it keeps `main` history clean while allowing messy commits on feature branches.

2. **Merge conflicts occur when two branches modify the same lines** in the same file. They're not errors—they're Git asking you to make a decision about which changes to keep.

3. **Conflict markers** (`<<<<<<<`, `=======`, `>>>>>>>`) show you both versions. VS Code's visual interface makes resolution intuitive, but you can also edit manually on the command line.

4. **Fast-forward merges** happen when the target branch hasn't moved; **three-way merges** create explicit merge commits when branches have diverged. Git chooses the appropriate mechanism automatically.

5. **Always test after merging**—resolved conflicts might work individually but fail when combined. Run your application, check for console errors, and verify affected features work correctly.

6. **GitHub's PR interface** provides three merge options. For CatchBook, consistently choose "Squash and merge" to maintain a professional, linear main branch history.

7. **Post-merge cleanup is essential:** Pull latest `main`, delete merged branches locally (`git branch -d`) and remotely (`git push -d origin`), and start new features from updated `main`.
