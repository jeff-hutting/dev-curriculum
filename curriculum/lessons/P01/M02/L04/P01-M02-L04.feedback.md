## Checkpoint 1 (20 minutes)

**Your Response:**

1. A **merge commit** is a commit that has two parent commits - the most recent feature branch commit and the most recent target branch commit (often `main`). A **squash commit** takes all commits from the branch and combines them into one commit on the target branch, deleting the feature branch's commits from the timeline. I would use a **merge commit** when I want to preserve an extensive branch commit history, the branch commits are meaningful and well-put-together, the branch contains a lot of significant work, or multiple collaborators contributed to the branch. I would use a **squash commit** for CatchBook if the branch commits are messy or small in significance, the feature isn't big enough to justify a merge commit, or I just want a clean, linear main branch commit history.

I will say Module 1 of Phase 3 (CatchBook landing page) is a good candidate for a **squash commit** - it's a medium-sized feature (although foundational in many respects) but not something I envision needing to go back and reference repeatedly once it is established.

**Professor Feedback:**

Excellent responses, Jeff! You've clearly grasped the core distinctions and applied them thoughtfully to CatchBook scenarios.

Your technical explanation is spot-on—you nailed the two-parent structure of merge commits and the consolidation behavior of squash. More importantly, you identified the key decision criteria: significance of individual commits, scope of work, collaboration context, and history preferences. This shows you're thinking beyond mechanics to decision-making strategy, which is exactly what separates junior from mid-level developers.

One nuance to add: You mentioned "deleting the feature branch's commits from the timeline" with squash—technically, those commits still exist on the feature branch itself (until you delete the branch), but they don't appear in `main`'s history. In that case, you might still squash (for cleanliness), but you'd write a detailed squash commit message summarizing that evolution. This gives you the best of both worlds—clean history, documented reasoning.

You're already operating at a systems level rather than just a tactical level, recognizing that not all features deserve the same historical treatment and considering what "future Jeff" will need when debugging or auditing.

**Professor Feedback:**

Strong responses again, Jeff! You're demonstrating solid understanding of conflict mechanics and practical resolution strategies.

Your explanation of what causes merge conflicts is technically accurate and complete. You identified all three conflict scenarios: same line/different changes, adjacent lines with incompatibilities, and one branch deletes while another modifies. Your conclusion—"requires a human decision"—is exactly right. Git is conservative by design. When it encounters ambiguity, it stops and asks you to decide rather than guessing incorrectly.

For the conflict resolution example, your choice shows good UX thinking—"Getting Started" is indeed more approachable than "Installation." However, this is a perfect example where both versions have value and you should consider combining them. Why not use "Getting Started" as the friendlier parent heading with "Installation" as a subsection? This demonstrates a key conflict resolution skill: Don't just choose—synthesize.

Your reasoning about error reduction with VS Code is spot-on. The cognitive load of finding markers, understanding versions, editing carefully, removing markers without typos, and saving correctly is significantly higher on the command line. VS Code's buttons eliminate steps where most mistakes happen.

Your predictions about leftover markers are all correct. In code files, conflict markers would cause immediate syntax errors. In Markdown/HTML, they would render visibly as ugly, unintended text displayed to users—exactly as you predicted.

One clarification: You said "Git will not merge the branches" if markers remain—not quite. Git has already merged at the point where markers appear. What happens is Git creates the file with conflict markers, and you're responsible for resolving and staging. If you stage a file with markers still in it, Git allows this (it trusts you). But your tests/linters/compilers will catch it. This is why the lesson emphasizes testing after merge—it's your safety net.

You're connecting dots across contexts: less typing = fewer errors (software engineering principle), visual tools reduce cognitive load (UX principle), syntax errors vs rendering errors (systems thinking). This practical mindset will serve you well.

**Professor Feedback:**

Excellent responses, Jeff! You're demonstrating mature understanding of Git workflows and the reasoning behind best practices.

Your squash-and-merge reasoning is outstanding. You've identified the key benefits: reduced overhead, easier navigation of main branch history, safety net (commits preserved on branch until deletion), and appropriate scope assessment. The "safety" point you made is particularly insightful—you're right that no history is lost until branch deletion. This is why many teams configure GitHub to auto-delete merged branches while still preserving the PR itself as documentation.

One additional professional context: Squash-and-merge also helps with bisecting bugs (Phase 25: Advanced Git Topics). When every commit on `main` represents a complete, working feature, you can use `git bisect` to binary-search through history to find which feature introduced a bug. Your merge commit criteria are spot-on: "big, broad, or important scope that will undoubtedly require more detail." Perfect examples from CatchBook include Phase 15-16 (AI Species Identification), Phase 10 (Authentication & Security), and Phase 23 (Mobile PWA Conversion).

For the "forgot to pull main" scenario, you correctly identified that you'd be working from an outdated base. Let me show you the disaster that unfolds: If commit E (the one you're missing) modified the same files as your new work in commits F and G, you'll get merge conflicts with your own previous work. This is why the post-merge ritual is sacred. Make this muscle memory.

Your explanation of the `-d` flag is perfect: "safe delete that won't allow me to delete a branch that changes that have not been merged yet." Exactly right. The `-d` vs `-D` distinction is Git's way of implementing "confirm before destructive action." It's like the difference between moving a file to trash (recoverable) vs holding Shift while deleting (permanent). Git won't let you accidentally destroy work unless you explicitly force it with `-D`.

You're consistently demonstrating systems thinking (understanding why workflows exist, not just how to execute them), risk awareness (recognizing what's "safe" vs what needs caution), forward-thinking (considering "future-me" in your decisions), and practical judgment (knowing when rules apply strictly vs when context matters). These aren't just Git skills—they're professional software engineering habits that will serve you across all 140+ remaining lessons.
