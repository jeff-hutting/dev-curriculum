## Checkpoint 1 (20 minutes)

**Questions:**

1. In your own words, explain the difference between a merge commit and squash-and-merge. When would you choose each for CatchBook development?

2. Why might you want to preserve individual commits from a feature branch? When might you want to squash them instead?

3. Looking at your CatchBook roadmap (28 phases, 141 modules), which features do you think would benefit from merge commits vs squash? Give one example of each and explain your reasoning.

**Answers:**

1. A **merge commit** is a commit that has two parent commits - the most recent feature branch commit and the most recent target branch commit (often `main`). A **squash commit** takes all commits from the branch and combines them into one commit on the target branch, deleting the feature branch's commits from the timeline. I would use a **merge commit** when I want to preserve an extensive branch commit history, the branch commits are meaningful and well-put-together, the branch contains a lot of significant work, or multiple collaborators contributed to the branch. I would use a **squash commit** for CatchBook if the branch commits are messy or small in significance, the feature isn't big enough to justify a merge commit, or I just want a clean, linear main branch commit history.

2. I feel like I already answered this in question 1. 

3. I would say the Phase 10 work (Authentication & Security) will be a big one and something I'd prefer a **merge commit** for. This seems like a huge feature to work on and is really, really important. As security concerns arise, it would be good to have as complete of a commit history as possible to answer the why's and how's that future-me will inevitably ask. I will say Module 1 of Phase 3 (Catchbok landing page) is a good candidate for a **squash commit** - it's a medium-sized feature (although foundational in many respects) but not something I envision needing to go back and reference repeatedly once it is established.
