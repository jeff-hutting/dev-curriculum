## Checkpoint 1 (20 minutes)

**Questions:**

1. In your own words, explain why code review is valuable for CatchBook development even though you're currently a solo developer.
2. What's the difference between code review as a "quality gate" vs a "learning opportunity"? Give a CatchBook-specific example of each.
3. Think about a recent change you made to CatchBook. What's one question a reviewer might have asked that you didn't consider?

**Answers:**

1. Code Review is valuable for this project for several reasons. The opportunity to catch bugs before they reach Production is a huge reason. Transferring knowledge between past-me, current-me, and future-me is another critical reason for Code Review. It also reduces cognitive load and stress through consistency in things like error handling, variable naming conventions, documentation style, commit structure among many other things. Consistent code review practices also build confidence and professionalism, which can be shown to a prospective employer by showing my GitHub profile. 

2. As a Quality Gate, Code Review creates opportunities to find and squash bugs, identify logic errors, etc. Reviewing with 'fresh eyes' and a rested perspective may provide insight into improving/fixing the code. As a learning opportunity, Code Review creates an opportunity to learn continuously from someone else by having them review your code. Reviewing other-people's code is a learning experience in and of itself, providing practice in reading unfamiliar code and finding ways to improve it. 

3. "Why not create a separate set of documentation for standards and conventions? Why clutter the README file with instructions on how to work in your project? Should the README file just offer a overview and technical explanation of the project?"

## Checkpoint 2 (40 minutes)

**Questions:**

1. Explain the difference between "Approve," "Request Changes," and "Comment" review actions. When would you use each for a CatchBook PR?
2. What's the benefit of line comments vs review-level comments? Give an example of when you'd use each.
3. Look at your most recent CatchBook PR. If you were reviewing it as someone else, what's one line comment you might leave? What would you write?

**Answers:**

1. `Approve` would be used when the PR is OK to merge. `Request Changes` would be used when identifying issues that need to be addressed before a merge is allowed. `Comment` would be used when a reviewer has feedback but nothing that would impede a merge. I would approve a CatchBook PR (that, for example, creates document files that separate areas of focus) that I have carefully reviewed for errors, clarity, and context. I may Request Changes in this CatchBook PR if I find API documentation in the README where it doesn't belong. I might leave a comment on this PR if I feel the API_DOCUMENTATION.md file should be named API-DOCUMENTATION.md instead. 

2. Line comments are great for pointing out specific bugs on the highlighted line, suggesting improved variable names, inquiring about a line's logic or function, or making a note of an error-handling issue. Review-level comments are handy for commenting on the overall approach or design of the changes included in the PR. It's also a great place to leave compliments or encouragement to the team working on the PR. General architecture and testing comments can be made here as well. In the case of the CatchBook Documentation PR (from question 1), I may leave a line comment on a misspelled word, or a phrase that doesn't have an appropriate tone. A review-level comment may include my opinions on the general formatting and layout of the documents.

3. I may leave a comment on Line 36 "- `hotfix/*` — Critical production fixes" asking what defines a *critical* fix, exactly.

## Checkpoint 3 (60 minutes)

**Questions:**

1. Why is it important to start review comments with appreciation rather than jumping straight to criticism?
2. Rewrite this harsh review comment in a constructive way: "This code is a mess. You should have used async/await instead of this callback hell. Fix it."
3. What's the difference between "must fix" and "nice to have" feedback? Why does this distinction matter for PR reviews?

**Answers:**

1. It is important to start review comments on a positive note to help reduce anxiety and potential defensiveness, let the teammates feel 'seen' and 'heard', demonstrates a willingness to collaborate, and may make any imminent critiques a little bit easier to take. Jumping straight to criticism creates anxiety, can be interpreted as confrontational, and can create an uninspiring work environment.

2. "I am having trouble deciphering what is going on here. It looks like extensive use of callbacks, which may be tough to untangle down the road. Have you considered using async/await in this situation? It may be the better option - let me know what you think!"

3. 'Must Fix' feedback would contain items that are merge-stoppers. These are the non-negotiables - these must be addressed before moving forward. "Nice To Have" feedback can be things that would be great to address if resources (especially time and money!) were infinite. Alas, they are not, so we can earmark those things for later implementation, but should not block a merge. Making the distinction between the two can help reduce anxiety for the author, help them prioritize what needs to be done, and keeps the project moving forward.

**Answers:**

## Checkpoint 5 (90 minutes)

**Questions:**

1. Why is it important to start your response to review feedback with gratitude, even if you disagree with some suggestions?
2. Walk through the steps: You've received feedback on a CatchBook PR requesting a null check. What's the complete workflow from making the fix to notifying the reviewer?
3. When would you explain your reasoning rather than immediately implementing a reviewer's suggestion? Give a CatchBook example.

**Answers:**

1. Starting a response with gratitude conveys respect for the reviewers time and consideration. I want to establish a positive tone (even if the review hurt my feelings 😭) and set a professional example. I also want to increase the likelihood the reviewer will help me out in the future. 

2. I would address the null check issue(s), and commit the changes. I would then push to the remote branch (making sure it's the same branch as the PR), then leave a comment in the PR with an explanation of what was changed. I would then request a re-review from anyone that had requested that change.

3. If I had spent a lot of time thinking through the design and implementation of something, I may explain my reasoning. Also, if I am in unfamiliar territory and writing code that I am less-than-confident about, I may make that clear as well. Sometimes the reviewer doesn't have the entire context behind certain decisions, so it's important to be honest, but open to discussion. For instance, a reviewer might ask that I do away with `subSpecies` and run with `species` instead for simplicity, and I would have to explain to them that, for example, Smallmouth Bass and Largemouth Bass are both Black Bass (and have mouths 🤓), but their feeding habits, behaviours, and preferred environments are almost completely different. It is imperative that we maintain a distinction between them.
