## Introduction: Pull Requests as Collaboration and Quality Gates

Pull requests are one of the most powerful features in modern software development. At their core, pull requests are **proposals to merge code from one branch into another**, typically from a feature branch into `main`.

But PRs are much more than just a merge mechanism. They serve three critical purposes:

**1. Code Review Gateway**  
Before code reaches `main`, other developers (or future you) review the changes. PRs provide a structured space for feedback, questions, and suggestions. For solo developers like you building CatchBook, PRs serve as a forcing function to review your own work with fresh eyes before merging.

**2. Documentation Trail**  
Every PR contains a description explaining *what* changed and *why*. This creates a searchable history of decisions. When you return to CatchBook in Phase 15 to add AI species identification, you'll reference the PRs from Phase 3 to understand how the photo capture system was originally designed.

**3. Quality Assurance Checkpoint**  
PRs integrate with automated testing and continuous integration (CI). When you open a PR, tests run automatically. Status checks verify your code doesn't break existing functionality. We'll see a preview of this in today's lesson (full CI/CD coverage comes in Phase 21).

For CatchBook, you'll use PRs even as a solo developer because they enforce discipline: every feature gets documented, reviewed (by you, systematically), and merged cleanly. This prevents the "spaghetti commit history" problem where `main` becomes a chaotic mix of half-finished features.

## The GitHub Flow: Branch → Commit → Push → PR → Review → Merge

Professional teams follow a workflow called **GitHub Flow**, which is simple but powerful:

### The Complete GitHub Flow

```
1. Create a branch from main
   └─> Isolate your work
   
2. Make commits on that branch
   └─> Build the feature incrementally
   
3. Push branch to GitHub
   └─> Back up your work, enable collaboration
   
4. Open a pull request
   └─> Propose merging branch into main
   
5. Discuss and review changes
   └─> Get feedback, iterate if needed
   
6. Merge the pull request
   └─> Integrate changes into main
   
7. Delete the feature branch
   └─> Keep repository clean
```

You completed steps 1-2 in the previous lesson when you created `feature/update-readme` and committed changes. Today, you'll complete steps 3-4 (push and open PR). In upcoming lessons, you'll learn steps 5-7 (review, merge, cleanup).

### Why This Order Matters

**Why push before opening PR?**  
GitHub needs your branch on the remote server to compare it with `main`. You can't create a PR from local-only branches.

**Why open PR before merging?**  
PRs enable review and discussion. Even if you're working solo, the PR interface provides tools for examining diffs, running checks, and documenting changes before they're permanent.

**Why delete branches after merging?**  
Branches are temporary workspaces. Once merged, the feature lives in `main` history. Deleting branches keeps your repository organized (imagine 100+ feature branches cluttering `git branch -a` output).

### CatchBook Application

Throughout the 28 phases, every feature follows this flow:

- **Phase 3:** Build landing page → `feature/landing-page` → PR → merge
- **Phase 8:** Create catch logging API → `feature/catch-api` → PR → merge
- **Phase 15:** Add species ID → `feature/species-identification` → PR → merge

This consistency makes it easy to track progress: count merged PRs, and you know how many features are complete.

## Pushing Feature Branches to GitHub

Before you can open a PR, your feature branch must exist on GitHub's servers (the "remote" repository). Right now, `feature/update-readme` only exists locally on your machine.

### The `git push` Command

The command to upload your branch is:

```bash
git push -u origin feature/update-readme
```

Let's break down what each part means:

**`git push`**  
The command to upload commits to a remote repository.

**`-u` (or `--set-upstream`)**  
Establishes a tracking relationship between your local branch and the remote branch. After this first push with `-u`, future pushes can simply use `git push` (Git remembers the upstream).

**`origin`**  
The name of your remote repository. By convention, `origin` refers to the GitHub repository you cloned from (or connected via `git remote add origin`). You can have multiple remotes (e.g., `origin` for GitHub, `backup` for a secondary server), but `origin` is the standard default.

**`feature/update-readme`**  
The name of the branch you're pushing. This must match the local branch name exactly.

### What Happens During `git push`

```
Local Repository                    Remote Repository (GitHub)
┌─────────────────┐                ┌─────────────────┐
│  main           │───────────────>│  origin/main    │
│  feature/       │                │                 │
│  update-readme  │───────────────>│  origin/feature/│
│  (3 commits)    │   git push     │  update-readme  │
│                 │                │  (3 commits)    │
└─────────────────┘                └─────────────────┘
```

Git compares your local commits with the remote branch. If the remote doesn't have your commits, Git uploads them. If the remote is ahead of your local (someone else pushed), Git rejects the push and asks you to pull first.

### First Push vs. Subsequent Pushes

**First push (with `-u`):**
```bash
git push -u origin feature/update-readme
```
Output:
```
Enumerating objects: 8, done.
Counting objects: 100% (8/8), done.
Delta compression using up to 8 threads
Compressing objects: 100% (5/5), done.
Writing objects: 100% (5/5), 1.23 KiB | 1.23 MiB/s, done.
Total 5 (delta 2), reused 0 (delta 0)
remote: Resolving deltas: 100% (2/2), completed with 1 local object.
To github.com:jeff-hutting/catchbook.git
 * [new branch]      feature/update-readme -> feature/update-readme
Branch 'feature/update-readme' set up to track remote branch 'feature/update-readme' from 'origin'.
```

The key line: `Branch 'feature/update-readme' set up to track remote branch...`

**Subsequent pushes (after upstream is set):**
```bash
git push
```
Git automatically knows to push `feature/update-readme` to `origin/feature/update-readme` because of the tracking relationship.

### Common Push Scenarios

**Scenario 1: Branch doesn't exist on remote yet**  
This is the typical case for new feature branches. Use `git push -u origin <branch-name>`.

**Scenario 2: Remote branch exists but is behind**  
You made more commits locally. Git uploads the new commits.

**Scenario 3: Remote branch is ahead of local**  
Someone else (or you on another machine) pushed commits. Git rejects your push:
```
! [rejected]        feature/update-readme -> feature/update-readme (fetch first)
error: failed to push some refs to 'github.com:jeff-hutting/catchbook.git'
```
Solution: `git pull` to merge remote changes, then push again.

**Scenario 4: Diverged branches (conflicts possible)**  
Both local and remote have unique commits. Git forces you to resolve conflicts before pushing.

For solo CatchBook development, Scenarios 3-4 are rare unless you work from multiple devices.

## Opening a Pull Request on GitHub

Once your branch is pushed to GitHub, you can open a pull request through the web interface. GitHub provides a polished UI for creating PRs, viewing diffs, and managing reviews.

### Step-by-Step: Creating Your First PR

> 💻 **Follow Along:** Complete these steps as you read. You'll create a real PR for your CatchBook repository.

**Step 1: Navigate to your repository on GitHub**  
Open your browser and go to: `https://github.com/jeff-hutting/catchbook`

**Step 2: GitHub detects recent push**  
If you just pushed a branch, GitHub shows a yellow banner at the top:

```
feature/update-readme had recent pushes 2 minutes ago
[Compare & pull request]
```

Click the **"Compare & pull request"** button.

*Alternative path (if banner doesn't appear):*  
Click the "Pull requests" tab → "New pull request" button → Select branches manually.

**Step 3: Verify branch selection**

You'll see the PR creation form with branch selectors:

```
base: main  ←  compare: feature/update-readme
```

- **base:** The branch you want to merge *into* (typically `main`)
- **compare:** The branch containing your changes (your feature branch)

Verify these are correct. If you accidentally selected the wrong branches, use the dropdowns to fix them.

**Step 4: Review the diff preview**

Below the branch selectors, GitHub shows a diff of all changes:

```diff
README.md
+ ## Development Workflow
+ 
+ This project follows the GitHub Flow:
+ 1. Create a feature branch
+ 2. Make commits
+ 3. Open pull request
+ 4. Review and merge
```

Green lines (`+`) are additions, red lines (`-`) are deletions. Verify this matches what you intended to change.

**Step 5: Write the PR title**

GitHub auto-fills the title with your last commit message. This is often good, but you can improve it.

**Bad title:** `Update README`  
**Good title:** `docs: add development workflow section to README`

Notice the good title:
- Follows Conventional Commits format (`docs:` prefix)
- Describes *what* changed and *where*
- Uses imperative mood ("add" not "added")

**Step 6: Write the PR description**

This is the most important part. A good PR description answers three questions:

1. **What changed?** (Brief summary)
2. **Why did it change?** (Motivation, context)
3. **How can it be tested?** (Verification steps)

Here's a template for CatchBook PRs:

```markdown
## What Changed

Added a "Development Workflow" section to README.md documenting the GitHub Flow process we're following for CatchBook feature development.

## Why

As we begin building features across 28 phases, we need a documented workflow for:
- Creating feature branches
- Opening pull requests
- Reviewing and merging changes

This ensures consistency and serves as a reference for future development.

## How to Verify

1. View the updated README.md
2. Confirm the new section appears after "Installation"
3. Verify all workflow steps are clear and actionable

## Related Issues

Closes #3
```

Notice:
- Clear section headers (`## What`, `## Why`, etc.)
- Specific details (what file, what section)
- Context for future reference
- Link to related issue (we'll create one shortly)

**Step 7: Link to issues (optional but recommended)**

If this PR addresses a GitHub issue, link it using special syntax:

```markdown
Closes #3
```

GitHub automatically closes issue #3 when this PR merges. Other linking keywords:
- `Closes #42` — Closes the issue when merged
- `Fixes #42` — Same as Closes
- `Resolves #42` — Same as Closes
- `Related to #42` — Links but doesn't auto-close

We'll create an issue first, then reference it in the PR.

**Step 8: Choose PR type (draft vs. ready for review)**

If your work isn't complete but you want early feedback, click the **"Create draft pull request"** dropdown and select "Draft PR."

Draft PRs:
- Clearly marked as work-in-progress
- Can't be merged until marked "Ready for review"
- Useful for getting feedback before finalizing

For this lesson, create a regular (non-draft) PR since your work is complete.

**Step 9: Create the pull request**

Click the green **"Create pull request"** button.

GitHub creates the PR and redirects you to the PR page. You'll see:
- PR number (e.g., `#4`)
- Title and description
- Diff view (tabs: Conversation, Commits, Files changed)
- Merge button (disabled until checks pass or you approve)

## Writing Effective PR Descriptions

The difference between a mediocre PR and an excellent PR is the description. Six months from now, when you're debugging a CatchBook issue, you'll read PR descriptions to understand past decisions.

### Anatomy of a Great PR Description

**1. What Changed (Summary)**

One paragraph, 2-4 sentences. Answers: "What files were modified and what's different?"

Example:
```markdown
## What Changed

Refactored the species identification API to use a custom TensorFlow model 
instead of Google Cloud Vision API. Updated `/api/species/identify` endpoint 
to call the new model service, and added fallback logic for low-confidence 
predictions.
```

**2. Why (Motivation and Context)**

This is the most valuable section. Explain:
- What problem does this solve?
- Why is this approach better than alternatives?
- What was the previous behavior (if changing existing functionality)?

Example:
```markdown
## Why

The Google Cloud Vision API costs $1.50 per 1,000 requests, which would 
exceed our budget at scale (target: 10,000 catches/day = $15/day = $450/month). 

A custom model trained on iNaturalist fish data achieves 87% accuracy for 
the top 50 species (our initial target set), with inference cost of ~$0.10/day 
on AWS SageMaker.

This change reduces API costs by 99% while maintaining acceptable accuracy 
for MVP launch. We can expand to more species post-launch as we gather 
user-submitted training data.
```

Notice:
- Specific numbers (costs, accuracy)
- Comparison to alternative (Google API)
- Justification for trade-off (accuracy vs. cost)
- Forward-looking context (post-launch expansion)

**3. How to Test (Verification Steps)**

Numbered list of steps to verify the changes work correctly. Think: "If someone else reviewed this PR, how would they confirm it's correct?"

Example:
```markdown
## How to Test

1. Start the API server: `python -m uvicorn main:app --reload`
2. Upload a test image of a largemouth bass: `curl -X POST -F "photo=@test_bass.jpg" http://localhost:8000/api/species/identify`
3. Verify response contains `"species": "Largemouth Bass"` with confidence >0.7
4. Upload an image of a rare species (not in top 50): `curl -X POST -F "photo=@test_rare.jpg" http://localhost:8000/api/species/identify`
5. Verify response falls back to "Unknown Species" with confidence <0.5
6. Check logs confirm fallback to Google Vision API for rare species
```

**4. Related Issues (Traceability)**

Link to GitHub issues using closing keywords:

```markdown
## Related Issues

Closes #42 — Reduce API costs
Related to #38 — Custom ML model training
```

### Common PR Description Mistakes

**❌ Too vague:**
```markdown
Updated the API.
```
This tells you nothing. What API? What changed? Why?

**❌ Too technical (no context):**
```markdown
Changed line 47 in species_service.py from `vision_client.detect()` to `model.predict()`.
```
This describes *how* but not *what* or *why*. The diff already shows the technical details—the description should explain the reasoning.

**❌ No testing guidance:**
```markdown
## What Changed
Added new feature.

## Why
Because we needed it.
```
How does a reviewer verify this works? What if it breaks existing functionality?

**✅ Clear and complete:**
```markdown
## What Changed

Added equipment tracking feature to catch logging. Users can now select 
rods, reels, and lures used for each catch. Updated database schema to 
include `catch_equipment` junction table.

## Why

Many anglers track which gear works best in specific conditions. By linking 
equipment to catches, we enable analytics like "Which lure has the highest 
success rate?" This addresses the #2 most requested feature from beta testers.

## How to Test

1. Create a new catch via the mobile app
2. Tap "Add Gear" button on the catch form
3. Select a rod, reel, and lure from your equipment catalog
4. Save the catch
5. Navigate to Analytics → Equipment Effectiveness
6. Verify the gear appears in the "Success Rate by Lure" chart

## Related Issues

Closes #27 — Equipment tracking
Related to #31 — Analytics dashboard
```

## Understanding the PR Diff View

The **diff view** is where you review exactly what changed in each file. GitHub's interface makes this easy to navigate and understand.

### The Files Changed Tab

Click the "Files changed" tab on your PR page. You'll see:

**File list (left sidebar):**
```
README.md  (+15, -2)
```

- `+15` — 15 lines added
- `-2` — 2 lines deleted
- Net change: 13 lines

**Diff display (main area):**

```diff
@@ -12,7 +12,20 @@ CatchBook is an AI-powered fishing journal...
 
 ## Installation
 
-Coming soon.
+### Prerequisites
+
+- Node.js 18+
+- Python 3.11+
+
+### Setup
+
+```bash
+npm install
+pip install -r requirements.txt
+```
 
 ## Development Workflow
+
+This project follows the GitHub Flow...
```

**Understanding diff syntax:**

- `@@` markers: Show line numbers (`-12,7` = starting at line 12, showing 7 lines from old version)
- White lines: Unchanged (context)
- Red lines (prefixed with `-`): Deleted
- Green lines (prefixed with `+`): Added

In this example:
- Line deleted: `Coming soon.`
- Lines added: Prerequisites, setup instructions, workflow section

### Viewing Changes at Different Granularities

**Unified diff (default):**  
Shows changes inline, mixed with context. Best for small changes.

**Split diff:**  
Click the settings icon (gear) → "Split" view. Shows old version (left) and new version (right) side-by-side. Best for large refactors.

**Rich diff:**  
For images, JSON, and other structured data, GitHub shows visual diffs (e.g., image before/after comparison).

### Reviewing Multi-File Changes

For PRs with many files, use strategies:

**1. Review by logical grouping:**  
GitHub groups related files (e.g., all files in `src/api/` together).

**2. Collapse reviewed files:**  
After reviewing a file, click "Viewed" checkbox. GitHub hides it from the list.

**3. Jump to specific files:**  
Click filename in sidebar to jump directly.

**4. Leave comments inline:**  
Hover over line numbers → "+" button → add comment. Useful for questions or suggestions.

### Common Diff Patterns in CatchBook Development

**Pattern 1: New feature (all additions)**
```diff
+ import { SpeciesIdentifier } from './ml/species_identifier';
+ 
+ export async function identifySpecies(imageUrl: string) {
+   const model = new SpeciesIdentifier();
+   return await model.predict(imageUrl);
+ }
```
All green lines. This is a new module.

**Pattern 2: Refactor (mixed additions and deletions)**
```diff
- const result = await fetch(API_URL);
- const data = await result.json();
- return data.species;
+ const { species } = await fetchSpeciesData(API_URL);
+ return species;
```
Red lines removed old verbose code, green lines added concise version.

**Pattern 3: Configuration change (small but critical)**
```diff
- API_RATE_LIMIT = 1000
+ API_RATE_LIMIT = 5000
```
One line changed. Small diff, big impact. This is why PR descriptions matter—the diff doesn't explain *why* the limit increased.

### Red Flags to Watch For

When reviewing your own PRs, look for:

**🚩 Unexpected changes:**  
If you see files you didn't intend to modify, investigate. Common cause: accidental `git add .` including debug files, IDE configs, etc.

**🚩 Large deletions:**  
If you deleted 500 lines, double-check you didn't accidentally remove critical code. Use `git diff` locally before pushing to catch this early.

**🚩 Sensitive data:**  
Scan for API keys, passwords, personal info. If found, immediately revoke the key and remove from Git history (use `git filter-branch` or BFG Repo Cleaner).

**🚩 TODO comments left in:**  
```diff
+ // TODO: Fix this hack before merging
```
If you left TODOs, address them before merging or convert to GitHub issues.

## Linking PRs to GitHub Issues

GitHub issues are how you track bugs, features, and tasks. Linking PRs to issues creates traceability: "Which PR fixed bug #27?" "Is feature #42 complete?"

### Creating an Issue First (Recommended Workflow)

**Step 1: Create an issue**

Navigate to your CatchBook repo → Issues tab → "New issue"

**Example issue:**
```
Title: Document development workflow in README

Description:
We need to document the GitHub Flow process for future reference. 
This will help maintain consistency as we build features across 28 phases.

Acceptance Criteria:
- [ ] README includes section on branching strategy
- [ ] README explains how to open pull requests
- [ ] README shows example of a good PR description

Labels: documentation, enhancement
Milestone: Phase 1 - Foundations
```

Click "Submit new issue." GitHub assigns it a number (e.g., `#3`).

**Step 2: Reference the issue in your PR**

When opening the PR, include in the description:

```markdown
## Related Issues

Closes #3
```

When the PR merges, GitHub automatically:
- Closes issue #3
- Links the PR to the issue (click issue #3 → see which PR closed it)
- Updates issue timeline ("closed via #4")

### Linking Keywords

GitHub recognizes these keywords in PR descriptions:

**Auto-close keywords (merge closes the issue):**
- `Closes #42`
- `Fixes #42`
- `Resolves #42`

**Reference keywords (link but don't close):**
- `Related to #42`
- `Ref #42`
- `See #42`

Use "Related to" when the PR partially addresses an issue but doesn't fully resolve it.

**Multiple issues:**
```markdown
Closes #27
Closes #31
Related to #19
```

### Why Link PRs and Issues?

**1. Project management:**  
Issues are the "what" (feature request, bug report). PRs are the "how" (implementation). Linking connects planning to execution.

**2. Searchability:**  
Six months later: "How did we implement species ID?" Search issues for "species identification" → find linked PR → read code.

**3. Automation:**  
When PR merges, issue auto-closes. Reduces manual tracking.

**4. Team coordination:**  
In collaborative projects, team members see which issues are actively being worked on (linked PRs show as "in progress").

### CatchBook Issue Structure

As you build CatchBook, organize issues like this:

**Milestones:**
- Phase 1 - Foundations
- Phase 3 - Frontend Basics
- Phase 8 - Backend API
- Phase 15 - AI Integration

**Labels:**
- `feature` — New functionality
- `bug` — Something broken
- `documentation` — Docs updates
- `enhancement` — Improvement to existing feature
- `priority: high` — Blocking or critical

**Example issue flow for Phase 8:**

1. Create issue: `#42: Implement catch logging API endpoint`
2. Create branch: `git checkout -b feature/catch-api-endpoint`
3. Build feature, commit changes
4. Push branch: `git push -u origin feature/catch-api-endpoint`
5. Open PR: "feat(api): add catch logging endpoint" + `Closes #42` in description
6. Review, merge PR
7. Issue #42 auto-closes ✅

## PR Etiquette: Reviewers, Assignees, and Labels

Pull requests support metadata that helps organize and track work, especially in team environments. Even as a solo developer on CatchBook, using these features builds good habits for future collaboration.

### Assignees

**What:** People responsible for working on the PR.

**When to use:**
- Assign yourself when you open a PR (shows ownership)
- In team projects, assign the person implementing the feature
- Leave unassigned if seeking volunteers

**How to set:** Right sidebar → "Assignees" → Select your username

**CatchBook practice:** Always assign yourself to PRs. This helps when reviewing closed PRs later: "Who worked on the species ID feature? The PR assignee shows it was you in Phase 15."

### Reviewers

**What:** People requested to review the PR before merging.

**When to use:**
- In team projects, request reviews from teammates with relevant expertise
- As a solo developer, you can skip this (you're the only reviewer)
- Later, when contributing to open-source projects, you'll request reviews from maintainers

**How to set:** Right sidebar → "Reviewers" → Select usernames

**CatchBook practice:** Leave this blank. You'll review your own PRs through the "Files changed" tab before merging.

### Labels

**What:** Tags for categorizing PRs (e.g., `bug`, `feature`, `documentation`).

**When to use:**
- Apply labels matching the type of change
- Use consistent labels across issues and PRs (makes filtering easier)
- Custom labels for project-specific needs

**How to set:** Right sidebar → "Labels" → Select from list

**Recommended CatchBook labels:**
- `feature` — New functionality (green)
- `bug` — Something broken (red)
- `documentation` — Docs updates (blue)
- `enhancement` — Improvement to existing feature (yellow)
- `refactor` — Code cleanup, no functional change (gray)
- `priority: high` — Blocking or critical (red)
- `phase-1`, `phase-3`, etc. — Track which curriculum phase (purple)

**Example:** For `feature/update-readme`, apply labels: `documentation`, `enhancement`, `phase-1`

### Projects

**What:** GitHub Projects are Kanban-style boards for tracking work (similar to Trello, Asana).

**When to use:**
- Track progress across multiple issues and PRs
- Visualize what's in-progress, under review, and completed
- Great for organizing CatchBook development across 28 phases

**How to set:** Right sidebar → "Projects" → Select a project board

**CatchBook practice:** You'll create a project board in P01-M04 (GitHub Issues + Projects). For now, leave this blank.

### Milestones

**What:** Group issues and PRs by goal or deadline (e.g., "Phase 1 - Foundations", "MVP Launch").

**When to use:**
- Track progress toward major milestones
- See % complete (e.g., "Phase 1: 75% complete, 3 of 4 modules done")
- Plan releases and feature batches

**How to set:** Right sidebar → "Milestone" → Select a milestone

**CatchBook practice:** Create milestones for each phase. For this PR, select "Phase 1 - Foundations" (create it if it doesn't exist yet).

### Draft Pull Requests

**What:** PRs marked as work-in-progress, clearly indicating they're not ready for merge.

**When to use:**
- You want early feedback on direction before finishing implementation
- You're blocked and need help from others
- You want to trigger CI checks without merging

**How to create:** When opening PR, click dropdown on "Create pull request" → Select "Create draft pull request"

**Converting draft to ready:** Click "Ready for review" button on the PR page

**CatchBook practice:** Use draft PRs when experimenting with new approaches (e.g., "Should I use TensorFlow or PyTorch for species ID?"). Get feedback early, finalize later.

## Status Checks Preview: CI/CD Integration

Modern PRs integrate with automated testing and continuous integration (CI). When you open a PR, tests run automatically, and GitHub shows status checks before allowing merge.

**Example status checks:**
```
✅ Tests passed (15 tests, 0 failures)
✅ Linting passed (no errors)
✅ Build succeeded
⚠️ Code coverage dropped below 80%
```

You'll implement CI/CD in Phase 21 (DevOps & Deployment), but here's a preview of how it works:

### How CI/CD with PRs Works

**1. You push commits to feature branch**  
Triggers webhook to CI service (GitHub Actions, CircleCI, Travis CI)

**2. CI runs automated checks**
- Run unit tests (`npm test`, `pytest`)
- Check code style (`eslint`, `flake8`)
- Build project to verify it compiles
- Run security scans

**3. CI reports status to GitHub**  
GitHub shows green checkmark ✅ or red X ❌ on PR page

**4. Merge button updates based on status**
- All checks pass → Merge button enabled
- Any check fails → Merge button disabled (or warning shown)

**5. Optional: Required status checks**  
Repository settings can require specific checks to pass before merging (e.g., "Tests must pass, coverage must be >80%")

### Why This Matters for CatchBook

Imagine you're in Phase 15, adding species identification. You open a PR, but accidentally broke the catch logging API (Phase 8). Without CI, you wouldn't notice until users report bugs. With CI:

```
❌ Tests failed (3 failures in test_catch_api.py)
   - test_create_catch: AssertionError
   - test_update_catch: NoneType error
   - test_delete_catch: Database connection failed
```

You see the failures immediately, fix them, push again, and CI re-runs. Once green, you merge confidently.

### GitHub Actions Example (Preview)

In Phase 21, you'll create a file `.github/workflows/test.yml`:

```yaml
name: Tests

on: [pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'
      - name: Install dependencies
        run: |
          pip install -r requirements.txt
          pip install pytest pytest-cov
      - name: Run tests
        run: pytest --cov=app tests/
```

This runs on every PR automatically. You don't need to understand YAML yet—just know that CI exists and you'll use it later.

### CatchBook CI/CD Roadmap

**Phase 1-7:** Manual testing (you run tests locally before merging)

**Phase 21:** Full CI/CD pipeline
- Automated tests on every PR
- Linting and code style checks
- Security scans (dependency vulnerabilities)
- Deployment to staging environment
- Production deployment on `main` branch merges

**Phase 28:** Advanced CI/CD
- Performance benchmarks
- Visual regression testing (screenshot comparisons)
- Automated release notes generation
- Slack notifications on deploy

For now, just understand the concept: PRs can trigger automated checks, and GitHub shows status before merging.

## Summary

This lesson introduced you to pull requests, a critical component of professional software development. Pull requests transform Git branches from isolated workspaces into structured proposals for integrating changes.

**You've learned:**

1. **Pull requests are proposals to merge code** from one branch (typically a feature branch) into another (typically `main`). They provide a structured space for review, discussion, and documentation before changes become permanent.

2. **The GitHub Flow workflow** follows a consistent pattern: create branch → make commits → push branch → open PR → review changes → merge → delete branch. This workflow scales from solo development to large teams.

3. **Pushing branches to GitHub** uses `git push -u origin <branch-name>` to establish tracking. The `-u` flag sets up the remote relationship, so future pushes can simply use `git push`. Your local commits are uploaded to GitHub, enabling PR creation.

4. **PR descriptions are documentation** that explains what changed, why, and how to verify. Good descriptions answer three questions: What? (summary), Why? (motivation and context), and How? (testing steps). Six months from now, PR descriptions will be your guide to understanding past decisions.

5. **PR titles follow Conventional Commits format** to maintain consistency across the project. Use prefixes like `feat:`, `fix:`, `docs:`, `refactor:` to categorize changes at a glance.

6. **Linking PRs to issues** creates traceability between planning and execution. Use `Closes #42` to automatically close issues when PRs merge, or `Related to #42` to link without closing. This connects the "what" (issues) to the "how" (PRs).

7. **The PR diff view** shows exactly what changed in each file. Green lines (`+`) are additions, red lines (`-`) are deletions. Review diffs carefully to catch unintended changes, sensitive data leaks, or errors before merging.

**Next steps:**

In **P01-M02-L03** (Code Review & Collaboration), you'll learn how to review PRs effectively, respond to feedback, request changes, and approve PRs for merging. You'll practice reviewing your own work with a systematic checklist.

In **P01-M02-L04** (Merge Strategies & Conflict Resolution), you'll learn the different ways to merge PRs (merge commit, squash, rebase), when to use each strategy, and how to resolve merge conflicts when branches diverge.

Throughout the 28 phases of CatchBook development, every feature you build will follow this PR workflow. By mastering it now, you're establishing professional habits that will serve you through hundreds of features and thousands of commits.
