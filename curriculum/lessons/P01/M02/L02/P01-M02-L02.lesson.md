## What is a Pull Request?

A **pull request (PR)** is a formal proposal to merge changes from one branch into another. Despite the name, you're not "pulling" anything—you're *proposing* that changes be pulled into the target branch after review.

Think of it like this: you've been working on a feature branch (`feature/update-readme`) where you documented CatchBook's development workflow. Now you want that work to become part of the official `main` branch. But instead of just merging it directly, you create a pull request that:

- **Displays all changes** in a reviewable format (side-by-side diffs)
- **Explains your reasoning** through a description and comments
- **Invites feedback** from reviewers (or self-review for solo projects)
- **Provides a discussion thread** for questions and iterations
- **Preserves context** forever (even after merging, the PR remains for historical reference)

### The Communication Value of PRs

PRs are as much about *communication* as they are about *code*. A good PR description answers:

- **What changed?** (summary of modifications)
- **Why did it change?** (problem being solved or feature being added)
- **How does it work?** (implementation approach if non-obvious)
- **How to test it?** (steps to verify the changes work)

For CatchBook, this means every PR documents a slice of your development journey. When you build the species identification feature in Phase 15, your PR description will explain:

- Why you chose Claude API over Google Vision API
- How you structured the image preprocessing pipeline
- What edge cases you handled (blurry photos, multiple fish in frame)
- How to test with sample images from your own fishing trips

That context is invaluable for future you, collaborators, and anyone exploring your portfolio.

### PRs vs Direct Commits to Main

You *could* work directly on `main` and push changes without PRs. Many beginners do this. But you lose:

1. **Review opportunity**: No chance to catch mistakes before they're in main
2. **Discussion space**: No place to explain your reasoning or ask questions
3. **Change documentation**: No searchable history of *why* decisions were made
4. **Collaboration readiness**: Can't easily get feedback from others

For CatchBook, establishing the PR workflow now means you'll have clean habits when your project grows complex.

## The GitHub Flow

GitHub Flow is a lightweight branching workflow centered on pull requests. It's the industry standard for web projects and maps perfectly to CatchBook development:

**The 6-Step GitHub Flow:**

1. **Create a branch** from `main` for your feature or fix
2. **Make commits** to that branch as you work
3. **Push the branch** to GitHub remote (`origin`)
4. **Open a pull request** to propose merging your branch into `main`
5. **Review and discuss** the changes (self-review or with collaborators)
6. **Merge the PR** once approved, then delete the branch

### Why This Works for CatchBook

CatchBook will span hundreds of features across 28 phases. GitHub Flow keeps development organized by:

- **Isolating risk**: Experimental work stays in feature branches until proven
- **Maintaining stability**: `main` always represents working, shippable code
- **Creating checkpoints**: Each merged PR is a milestone you can deploy
- **Enabling rollback**: If a feature causes problems, you can revert the PR

As you advance through the curriculum, you'll develop multiple features in parallel (e.g., authentication + catch logging + species ID). GitHub Flow lets you keep each feature in its own branch while maintaining a clean `main` branch ready to demo at any moment.

### GitHub Flow vs Git Flow

You might encounter references to "Git Flow" (capital F)—a more complex branching strategy with `develop`, `release`, and `hotfix` branches. That's overkill for CatchBook.

**GitHub Flow** (what we're using) is simpler and better suited for continuous deployment:
- One long-lived branch (`main`)
- Short-lived feature branches
- Deploy from `main` frequently

**Git Flow** is for teams with scheduled releases (e.g., enterprise software with v1.0, v2.0 releases). CatchBook will use continuous delivery, so GitHub Flow is the right choice.

## Pushing Your Feature Branch to GitHub

Before you can open a PR, your feature branch must exist on GitHub (the remote repository). Right now, your `feature/update-readme` branch only exists locally on your machine.

### Understanding Remote Branches

When you run `git branch`, you see your local branches:

```bash
git branch
# Output:
# * feature/update-readme
#   main
```

But GitHub (the remote named `origin`) doesn't know about `feature/update-readme` yet. You need to **push** it.

### The Push Command with Upstream Tracking

> 💻 **Follow Along:** Execute these commands to push your feature branch.

**First, verify your current branch:**

```bash
git branch
# You should see: * feature/update-readme
```

**Push the branch to GitHub and set up tracking:**

```bash
git push -u origin feature/update-readme
```

**What this command does:**

- `git push`: Send commits to the remote repository
- `-u` (or `--set-upstream`): Establish a tracking relationship between your local branch and the remote branch
- `origin`: The remote repository (your CatchBook GitHub repo)
- `feature/update-readme`: The branch name to push

**Expected output:**

```bash
Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Delta compression using up to 8 threads
Compressing objects: 100% (3/3), done.
Writing objects: 100% (3/3), 456 bytes | 456.00 KiB/s, done.
Total 3 (delta 1), reused 0 (delta 0), pack-reused 0
remote: Resolving deltas: 100% (1/1), completed with 1 local object.
remote: 
remote: Create a pull request for 'feature/update-readme' on GitHub by visiting:
remote:   https://github.com/jeff-hutting/catchbook/pull/new/feature/update-readme
remote: 
To github.com:jeff-hutting/catchbook.git
 * [new branch]      feature/update-readme -> feature/update-readme
branch 'feature/update-readme' set up to track 'origin/feature/update-readme'.
```

**Notice the helpful message from GitHub:** It provides a direct link to create the PR! You can click that link or use the GitHub web interface (we'll do the latter for learning purposes).

### What `-u` (Upstream Tracking) Means

Setting upstream tracking creates a relationship between your local branch and the remote branch. After running `git push -u origin feature/update-readme` once, you can:

- Run `git push` without arguments (Git knows where to push)
- Run `git pull` without arguments (Git knows where to pull from)
- See tracking status with `git branch -vv`

**Verify tracking was set:**

```bash
git branch -vv
```

**Output:**

```bash
* feature/update-readme abc1234 [origin/feature/update-readme] docs: add development workflow section
  main                  def5678 [origin/main] Initial commit
```

The `[origin/feature/update-readme]` tells you the local branch tracks the remote branch.

### Subsequent Pushes

For future commits on this branch, you can simply run:

```bash
git push
```

Git will automatically push to `origin/feature/update-readme` because tracking is configured.

### Common Mistake: Pushing to Wrong Branch

**Don't do this:**

```bash
git push origin main  # ❌ Pushes to main instead of your feature branch
```

This would skip the PR process entirely and merge your changes directly to `main`. Always push to your feature branch, not `main`.

## Opening a Pull Request on GitHub

Now that your feature branch is on GitHub, you can create a PR through the web interface.

> 💻 **Follow Along:** Open GitHub and complete these steps.

### Step 1: Navigate to Your Repository

1. Go to `https://github.com/jeff-hutting/catchbook` in your browser
2. You should see a yellow banner at the top:

   ```
   feature/update-readme had recent pushes less than a minute ago
   [Compare & pull request]
   ```

3. Click the **"Compare & pull request"** button

**Alternative if the banner doesn't appear:**

1. Click the "Pull requests" tab at the top
2. Click the green "New pull request" button
3. Change the "compare" dropdown to `feature/update-readme`

### Step 2: Review the PR Form

The "Open a pull request" page shows:

- **Base repository**: `jeff-hutting/catchbook` (your repo)
- **Base branch**: `main` (the branch you're merging *into*)
- **Head repository**: `jeff-hutting/catchbook` (same repo for feature branches)
- **Compare branch**: `feature/update-readme` (the branch with your changes)

**Below that:**

- **Diff view**: Shows all file changes (green = additions, red = deletions)
- **Title field**: Pre-filled with your most recent commit message (you'll improve this)
- **Description field**: Blank (you'll fill this in)

### Step 3: Write a PR Title

PR titles should follow the same **Conventional Commits** format you use for commit messages.

**Change the pre-filled title to:**

```
docs(readme): add development workflow section
```

**Why this format?**

- `docs`: Type (documentation change)
- `(readme)`: Scope (which file or area)
- `add development workflow section`: Description (what changed)

This creates consistency between commit messages and PR titles, making your project history scannable.

### Step 4: Write a PR Description

This is where you explain the *why* and *how* of your changes. GitHub provides a blank text field—fill it with context.

**Recommended PR description template:**

```markdown
## What

Added a "Development Workflow" section to README.md explaining the branch → commit → PR → merge workflow used for CatchBook feature development.

## Why

As CatchBook grows across 28 phases, maintaining clear documentation of our development process will help future contributors (and future me!) understand the branching strategy and PR conventions.

## Changes

- Added "Development Workflow" section to README.md
- Documented GitHub Flow steps (create branch, commit, push, open PR, review, merge)
- Included branch naming conventions (`feature/`, `bugfix/`, `hotfix/`)
- Added example workflow for hypothetical "species identification" feature

## Testing

- Verified Markdown renders correctly by previewing README.md in VS Code
- Confirmed all internal links work (if any were added)
- Checked formatting consistency with existing README sections

## Notes

This is the first feature branch PR for CatchBook—establishing the workflow we'll use for all future development.
```

**Copy and paste this template into the PR description field**, adjusting the content to match your actual changes.

### Why These Sections Matter

- **What**: Quick summary for busy reviewers
- **Why**: Provides context and rationale (critical for future reference)
- **Changes**: Bullet-point list of modifications (makes reviewing easier)
- **Testing**: Shows you verified your work (builds confidence)
- **Notes**: Additional context or FYIs

For solo projects, this might feel like overkill—but it's excellent practice for professional workflows. When you contribute to open source or work with teams, detailed PR descriptions are expected.

## Linking PRs to GitHub Issues

Pull requests can reference GitHub Issues to create full traceability. This connects the *what* (the code changes in the PR) to the *why* (the problem or feature tracked in an issue).

### Creating a GitHub Issue First

Best practice: create an issue *before* starting work on a feature. This helps you:

- Clarify requirements before coding
- Track progress on complex features
- Provide context for future reference

> 🛠️ **Hands-On Exercise:** Create your first CatchBook issue and link it to your PR.

**Step 1: Create an Issue**

1. On your CatchBook repository page, click the "Issues" tab
2. Click "New issue" (green button)
3. **Title**: `Document development workflow in README`
4. **Description**:

   ```markdown
   CatchBook spans 28 phases of development. We need clear documentation of our branching strategy and PR workflow to maintain consistency as the project grows.

   **Acceptance Criteria:**
   - [ ] README includes "Development Workflow" section
   - [ ] Workflow explains GitHub Flow (branch → commit → PR → merge)
   - [ ] Branch naming conventions documented (feature/, bugfix/, hotfix/)
   - [ ] Example workflow provided for context
   ```

5. Click "Submit new issue"
6. Note the issue number (probably #1 or #2)

### Linking the Issue in Your PR

Now return to your open PR (or re-open the PR creation form if you haven't submitted it yet).

**In the PR description, add this line at the bottom:**

```markdown
Closes #1
```

(Replace `1` with your actual issue number)

### GitHub's Magic Keywords

When you use `Closes #N` in a PR description, GitHub automatically:

- Links the PR to the issue
- Closes the issue when the PR is merged
- Shows the connection in both the PR and issue threads

**Other magic keywords:**

- `Fixes #N`
- `Resolves #N`
- `Closes #N`

All three work identically—choose whichever reads most naturally.

**Multiple issues?**

```markdown
Closes #1, Closes #2
```

### Why This Matters for CatchBook

As you build CatchBook across 28 phases, you'll create hundreds of issues:

- `Issue #42: Add species identification AI`
- `Issue #73: Integrate weather API`
- `Issue #104: Build catch statistics dashboard`

When each issue is linked to its PR, you create a complete development history. Six months later, you can find issue #42, see the linked PR, and understand exactly what code implemented that feature.

This also helps with portfolio presentation. You can show employers/collaborators: "Here's how I managed a complex project—every feature has an issue, every issue has a PR, every PR has thorough documentation."

## Understanding the PR Diff View

Before submitting your PR, review the **diff view**—GitHub's side-by-side comparison of what changed.

### Viewing the Diff

On the "Open a pull request" page, scroll down below the description field. You'll see:

**"Files changed" tab**: Shows all modified files with line-by-line diffs

**Example diff display:**

```diff
README.md
+15 -0

+ ## Development Workflow
+ 
+ CatchBook follows GitHub Flow for all feature development:
+ 
+ 1. Create a feature branch from `main`
+ 2. Make commits to your branch
+ 3. Push the branch to GitHub
+ 4. Open a pull request
+ 5. Review and discuss changes
+ 6. Merge the PR and delete the branch
```

**Reading the diff:**

- **Green lines** (prefixed with `+`): Additions
- **Red lines** (prefixed with `-`): Deletions
- **Gray lines**: Unchanged context
- **+15 -0**: Summary (15 lines added, 0 deleted)

### What to Check in the Diff

Before submitting your PR, verify:

1. **Only intended changes are included**: No accidental modifications to other files
2. **No sensitive data**: No API keys, passwords, or personal info
3. **No debug code**: No `console.log()`, commented-out blocks, or testing artifacts
4. **Formatting is clean**: No trailing whitespace or mixed tabs/spaces
5. **Changes make sense**: Read through your modifications with fresh eyes

### Common Diff View Mistakes

**Problem**: You see changes to files you didn't modify (e.g., `package-lock.json` changed when you only edited `README.md`)

**Cause**: You may have installed dependencies or auto-formatted files unintentionally

**Solution**: Review each file carefully. If unintended changes exist, commit only the intended files:

```bash
git checkout HEAD -- package-lock.json  # Discard changes to one file
git push --force  # Update the remote branch (safe for unpublished branches)
```

**Problem**: Diff shows hundreds of changed lines but you only modified a few

**Cause**: Line ending differences (Windows CRLF vs Unix LF) or file encoding issues

**Solution**: Configure Git to normalize line endings:

```bash
git config --global core.autocrlf input  # Mac/Linux
git config --global core.autocrlf true   # Windows
```

## Draft PRs and Work-in-Progress Visibility

Sometimes you want to open a PR before your work is complete—to show progress, get early feedback, or signal that you're working on something. That's where **draft PRs** come in.

### What is a Draft PR?

A draft PR is a pull request marked as "work in progress." It:

- **Prevents accidental merging**: The "Merge" button is disabled until you mark the PR as ready
- **Signals status**: Reviewers know you're not requesting final approval yet
- **Enables early feedback**: You can ask questions or get input before finishing

For CatchBook, draft PRs are useful when:

- Building complex features across multiple days (e.g., AI species identification)
- Experimenting with architecture and wanting input before committing fully
- Coordinating multiple related PRs (showing how they fit together)

### How to Create a Draft PR

When opening a PR, look for the "Create pull request" button. Next to it is a dropdown arrow (▼).

1. Click the dropdown arrow
2. Select **"Create draft pull request"**
3. Fill in title and description as normal
4. Submit

**To convert a draft to ready:**

1. Open the draft PR
2. Scroll to the bottom
3. Click **"Ready for review"**

The merge button becomes active and reviewers are notified.

### When to Use Draft PRs for Solo Projects

Even without teammates, draft PRs have value:

- **Incremental progress**: Open a draft when you start a feature, update it daily, convert to ready when done
- **Self-review forcing function**: Coming back to a draft PR the next day often reveals issues you missed
- **Portfolio demonstration**: Shows potential employers you understand professional workflows

For CatchBook, you might open a draft PR at the start of each module, make commits throughout the module, then mark it ready when all checkpoints pass.

## PR Etiquette: Reviewers, Assignees, and Labels

GitHub PRs include organizational features that become more important as projects grow. Even for solo work, understanding these helps when you collaborate later.

### Reviewers

**What it is**: Assign people to review your code before merging

**How to use it**:

1. On the PR page, look for the "Reviewers" section (right sidebar)
2. Click the gear icon
3. Select GitHub users to request review from

**For CatchBook (solo)**: You won't use this initially, but when you open source CatchBook or collaborate, reviewers formalize the feedback process.

### Assignees

**What it is**: Indicate who is responsible for the PR

**How to use it**:

1. Same location as Reviewers (right sidebar)
2. Click the gear icon next to "Assignees"
3. Select yourself (or others)

**For CatchBook**: Assign yourself to PRs you're actively working on. This helps when you have multiple draft PRs open simultaneously.

### Labels

**What it is**: Categorical tags for PRs (e.g., `enhancement`, `bug`, `documentation`)

**How to use it**:

1. Right sidebar, "Labels" section
2. Click the gear icon
3. Select relevant labels

**Common labels**:

- `documentation`: README changes, inline docs, architecture notes
- `enhancement`: New features
- `bug`: Fixes for broken functionality
- `good first issue`: Entry-level tasks (for contributors)

**For CatchBook**: Create custom labels matching your workflow:

- `phase-01-foundations`: PRs from Phase 1
- `catchbook-backend`: Backend-specific changes
- `catchbook-frontend`: Frontend-specific changes
- `ai-integration`: Claude API or ML features

**Creating custom labels**:

1. Go to "Issues" tab → "Labels"
2. Click "New label"
3. Choose name, color, description

Labels make filtering easier: "Show me all Phase 8 backend PRs" = select `phase-08-backend` label.

## Status Checks Preview (CI/CD Introduction)

When you view a PR, you might see a section called "Checks" or "Status checks" near the bottom. This is where **Continuous Integration (CI)** systems report results.

### What Are Status Checks?

Status checks are automated tests that run when you push code. Common checks:

- **Tests**: Unit tests, integration tests pass/fail
- **Linting**: Code style and formatting validation
- **Build**: Project compiles successfully
- **Security**: Dependency vulnerability scanning

**Example status check display:**

```
✅ All checks have passed
   ✓ Tests (pytest) — 42 tests passed
   ✓ Linting (eslint) — no errors
   ✓ Build (npm run build) — success
```

If any check fails, the merge button may be blocked until you fix the issue.

### Why Status Checks Matter for CatchBook

In Phase 21 (DevOps), you'll set up GitHub Actions to automatically:

- Run tests when you push to a PR
- Verify code formatting (Prettier, Black)
- Check for security vulnerabilities
- Build the production bundle

This prevents bugs from reaching `main`. For now, you won't have status checks configured—but understanding they exist prepares you for later.

### Manual Quality Checks (for now)

Until you set up CI/CD, perform manual checks before merging:

1. **Does the code run?** Test locally
2. **Are there typos?** Proofread documentation
3. **Did you test the feature?** Run through the workflow
4. **Does it match the issue requirements?** Check acceptance criteria

These manual steps become automated status checks in Phase 21.

## Summary

This lesson introduced pull requests—the cornerstone of professional collaborative development and a critical tool for maintaining CatchBook's code quality across 28 phases.

**You've learned:**

1. **Pull requests are proposals to merge changes** from a feature branch into a base branch (typically `main`), providing a review and discussion layer before integration.

2. **GitHub Flow is a lightweight, PR-centric workflow** that keeps development organized: branch → commit → push → PR → review → merge. This pattern will structure all your CatchBook feature development.

3. **Pushing feature branches to GitHub** requires `git push -u origin <branch-name>` to establish upstream tracking, enabling simpler push/pull commands in the future.

4. **PR titles follow Conventional Commits format** (`type(scope): description`) to maintain consistency between commit messages and PR titles, making project history scannable.

5. **PR descriptions should explain what changed, why it changed, and how to test it**, using structured templates (What/Why/Changes/Testing/Notes) to provide context for future reference.

6. **Linking PRs to issues** with `Closes #N` syntax creates full traceability between problems and solutions, automatically closing issues when PRs merge.

7. **The PR diff view shows line-by-line changes** (green for additions, red for deletions), enabling pre-merge verification that only intended changes are included.

8. **Draft PRs signal work-in-progress status**, preventing accidental merges while enabling early feedback and incremental progress visibility.

**Next steps:**

In the next lesson (P01-M02-L03), you'll learn code review best practices—how to review your own PRs effectively and provide constructive feedback when collaborating with others. You'll also merge your first PR and experience the satisfaction of integrating a feature into `main`.

Pull requests transform Git from a version control tool into a collaboration platform. Even as a solo developer, PR discipline improves code quality, creates valuable documentation, and prepares you for team environments. As you build CatchBook across hundreds of features, this workflow will become second nature—and your project history will tell a clear, professional story.
