## Checkpoint 1 (20 minutes)

**Questions:**

1. In your own words, explain what a pull request is and why you'd use one instead of merging directly to `main`.

2. Describe the six steps of GitHub Flow as they would apply to adding a new CatchBook feature (for example, a "Catch Statistics" dashboard).

3. Why is it valuable to write detailed PR descriptions even when you're the only developer on a project?

**Answers:**

1. A pull request is basically a *request* to merge changes that have been made in a branch into the main, shippable code. This creates an opportunity for review and discussion with collaborators, provides a documented, referenceable point for future-me to see when features/fixes were implented, and makes things easier for future collaborators to 'look back in time' at the history of the project. In addition to providing a point of self-review, it also helps reduce the likelihood of bad code being introduced into the production version of the project.

2. I would create a branch (called something like feat/stats-dash or something similar) and make commits to that branch as I am working on those features. I would push the branch to remote (`origin`) and open a Pull Request to propose a merge into the `main` branch. From here, I would take the time to review the changes in the PR, and then once I'm confident everything looks good, I would merge the PR. 

3. A detailed PR is important because I am essentially documenting my decisions and reasoning at that point in time so that it makes more sense (hopefully) to future-me or collaborators as to why certain changes were made, features were added, and/or fixes were made. These are checkpoints in the project's evolution that make rolling back features or components easier going forward.

**Questions:**

3. Look at the PR description template above. Which section do you think is most valuable for CatchBook's long-term development, and why?

**Answers:**

1. The `-u` flag sets upstream tracking and is usefule primarily to save keystrokes when executing future pushes on the current branch. Once upstream tracking is set on the first commit, I can type `git push` instead of `git push origin feature/update-readme` every single time. I should use this flag as part of the first `push` command I use after switching branches.

2. We would lose everything we discussed in Lesson Checkpoint 1: Documentation, Accountability, Rollback ability, Explanation of decision making, debugging capabilities, Evolution checkpoints... everything! It is important to have these changes on the remote in addition to local so that both repos have a complete version history of the project.

3. I would say the "Changes" section is most important. It establishes naming conventions, references a documented development workflow process and GitHub Flow steps. These are things that should be used consistently throughout the development of the project. A collaborator will be able to see this and 'jump right in' with consistent workflow and naming conventions.

**Questions:**

1. You added `Closes #1` to your PR description. Explain what happens when this PR is merged, and why this automatic behavior is useful for project management.

2. You're reviewing your PR diff and notice that `README.md` shows +50 lines but you only remember adding about 20 lines of content. What might explain the discrepancy, and how would you investigate?

3. Imagine you're six months into CatchBook development (Phase 15, building species identification). You want to remember why you structured the README a certain way. How would the issue/PR linking system help you find that context?

**Answers:**

1. By adding language such as `Closes #2` to the PR description, it automatically links the PR to a GitHub issue. When the PR is merged, it closes the referenced issue(s) and shows a connection in the PR *and* issue threads. Having linked Issues and PRs creates a complete development history. Additionally, it assists with presented a portfolio to prospective employer.

2. A large discrepency in a modified-line count may indicate a file encoding issue. Line endings are different in Windows vs Unix, so it would be important to understand the environment in which the file in question was created/modified.

3. GitHub Issues and Pull Requests are searchable (I think?) so I can query the topic/keywords I want to research and reference either the PR or the Issue. If I am linking them properly, I will easily be able to see the entire context and development history of that particular decision.
