## Checkpoint 1 (20 minutes)

**Questions:**

1. Explain the purpose of the `-u` flag in `git push -u origin <branch-name>`. Why do you use it on the first push but not subsequent pushes?

2. What does `origin` refer to in Git commands? Could you have multiple remotes (e.g., `origin` and `backup`), and if so, why might that be useful?

3. Imagine you're working on CatchBook from both your MacBook and iPad. You push commits from your MacBook, then switch to your iPad and try to push without pulling first. What error would Git give you, and how would you fix it?

**Answers:**

1. The `-u` flag is shorthand for `--set-upstream`, and establishes a tracking relationship between the local and remote repositories. Once the relationship has been established, it is no longer required to use the `-u` flag each time, and the push command can be shortened to simple `git push`

2. `origin` refers to the remote repository stored on the GitHub site. You *can* have multiple remotes, and if you have a second, backup remote server, it might be useful to name that one `backup`.

3. Git would reject the commits if the remote repo was ahead of my local repo and would ask me to perform a `fetch` command before proceeding.

## Checkpoint 2 (40 minutes)

**Questions:**

1. What are the three essential sections of a good PR description, and what does each section answer?

2. Why is the "Why" section often more valuable than the "What" section? Give an example from CatchBook development where understanding the *why* would be critical six months later.

3. Look at this PR description and identify what's missing or could be improved:

```markdown
Updated README

Added new section.
```

Rewrite this as a proper PR description using the template from this lesson.

**Answers:**

1. The three essential sections of a quality PR are "What Changed", "Why", and "How to Verify". The "What Changed" section provides a plain-language description of anything that was changed in this PR, and where it was changed. "Why" explains the longer-term thinking behind why the changes were necessary - sometimes adding a new feature, sometimes reducing API costs, sometimes fixing issues. "How to Verify" is important for teammates (or future-me) to see a basic testing flow to ensure the changes were implemented correctly, provide the benefit explained in the "why" section, and don't produce any unexpected errors.

2. When API costs change, or are updated, sometimes it may become beneficial to change existed, working, 100% operational code for business purposes. "Why did we deviate from ChatGPT and adopt Claude Code's API when nothing broke on ChatGPT?" - the "Why" section provides that insight.
