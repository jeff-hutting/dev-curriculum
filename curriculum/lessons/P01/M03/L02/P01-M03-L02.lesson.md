## Why This Lesson Matters for Helm

Every commit you make on Helm becomes part of its permanent history. Six months from now, when you're debugging why the drag-to-time-block feature broke after a refactor, your commit subjects will be your first clue. `fix stuff` tells you nothing. `fix: prevent task from scheduling outside working hours` tells you exactly where to look.

In this lesson you'll master the single most visible part of a commit: the subject line. Specifically, you'll learn the 50/72 rule, how to write in imperative mood, and what separates a useful subject from a vague one. These are habits that become automatic quickly — and they pay dividends every time you run `git log`.

## Quick Review: Conventional Commits Structure

You learned this in L01 — a brief reminder before we focus in:

```
<type>(<scope>): <subject>

<body>

<footer>
```

Today's lesson is entirely about that `<subject>` field. Bodies and footers come in L03. For now, know that everything after the colon and space on line 1 is your subject line, and it needs to earn its keep.

## The 50/72 Rule

The rule has two parts, one per context where your subject line appears.

### The 50-Character Target

**50 characters** is the recommended length for a commit subject. Why? Because `git log --oneline` — the view you'll use constantly — is most readable when subjects stay under 50. GitHub's UI also shows subject lines in tight spaces: the commit list, PR timelines, blame views. Short subjects fit everywhere without truncation.

Here's what 50 characters looks like in practice:

```
feat(tasks): add drag-to-schedule on calendar view
```

That's 50 characters exactly. Count the characters after the colon-space and you'll see they're tight but descriptive.

### The 72-Character Hard Cap

**72 characters** is the absolute maximum before tools start doing ugly things. `git log` wraps at 72 by default. GitHub shows ellipses past 72. Some email-based workflows break entirely past 80. So: aim for 50, never exceed 72.

If you can't describe your change in 72 characters, the commit is probably doing too much. That's a signal to split it — but we'll cover atomic commits in L04.

## Imperative Mood

Imperative mood means writing the subject as a command — as if you're telling Git what this commit does when applied.

### The Pattern

- **Correct:** `Add task priority field to sidebar`
- **Wrong:** `Added task priority field to sidebar`
- **Wrong:** `Adding task priority field to sidebar`
- **Wrong:** `This commit adds a task priority field`

### The 'If Applied' Test

Stuck on whether you've got it right? Prefix your subject with "If applied, this commit will..." and read it out loud.

- "If applied, this commit will **add task priority field to sidebar**" ✅
- "If applied, this commit will **added task priority field to sidebar**" ❌ — immediately wrong

Git itself uses imperative mood in its own messages: `Merge branch 'feat/task-list'`, `Revert "feat: add Google Calendar sync"`. Follow its lead.

## The Other Subject Line Rules

Three more quick rules that round out a professional subject line:

### Capitalize the First Word

The first word after the type/scope prefix should be capitalized. The `<type>:` is lowercase by convention; the `<subject>` starts with a capital.

```
feat(calendar): Add weekly view with time blocks   ✅
feat(calendar): add weekly view with time blocks   ❌
```

### No Trailing Period

Subject lines are titles, not sentences. Titles don't end with periods.

```
fix: Prevent duplicate task creation   ✅
fix: Prevent duplicate task creation.  ❌
```

### Be Specific

The subject should describe *what* changed, not that *something* changed.

```
feat(tasks): Add due date field to task creation form   ✅
feat(tasks): Update tasks                               ❌
chore: Fix bug                                          ❌
docs: Changes                                           ❌
```

If you find yourself writing `update`, `fix`, `change`, or `work on` without a noun after it, that's a flag to be more specific.

## Summary

A great commit subject line is short, direct, and tells a story in under 50 characters. It takes less than a minute once the habit is formed, and it compounds in value every time you use `git log`, open a PR, or try to bisect a regression.

**You've learned:**

1. **The 50/72 rule** — aim for 50 characters, never exceed 72. Short subjects fit everywhere; long ones get truncated or wrapped.
2. **Imperative mood** — write the subject as a command: "Add feature", not "Added feature" or "Adds feature". Use the "If applied..." test when unsure.
3. **Capitalize the first word** — `<type>:` is lowercase by convention; the subject starts with a capital.
4. **No trailing period** — subjects are titles, not sentences.
5. **Be specific** — vague words like `update`, `fix`, or `changes` without context are red flags.

In L03, you'll learn when and how to write commit bodies and footers — what to do when the subject alone can't capture the full context of a change.
