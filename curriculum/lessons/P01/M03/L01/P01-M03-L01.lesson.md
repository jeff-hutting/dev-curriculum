## Introduction: Why Commit Message Consistency Matters for CatchBook

Imagine you're six months into CatchBook development. You've just shipped the species identification feature, implemented weather integration, and built the equipment tracking system. One day, a user reports that catch photos aren't uploading correctly on iOS devices.

You open the Git history to find when photo upload logic last changed. You see this:

```

update
more changes
wip
final fix
actually fixed it this time

```

**This is a nightmare.** Which commit broke photo uploads? What did "update" change? When was the feature last working?

Now imagine instead you see this:

```
fix(photo): handle iOS HEIC format conversion
feat(photo): add compression before upload
refactor(photo): extract upload logic to service
test(photo): add integration tests for upload flow
```

**This tells a story.** You can immediately see that photo upload logic changed in a refactor commit, a new feature was added, then a bug fix addressed iOS-specific issues. You know exactly where to look.

Conventional Commits transforms your Git history from random notes into structured documentation. For CatchBook, this means:

**Searchability:** Need all auth-related changes? Search for `feat(auth):` and `fix(auth):`

**Context:** Each commit type signals intent (new feature vs bug fix vs documentation)

**Automation:** Tools can parse commits to generate changelogs automatically

**Versioning:** Commits map to semantic version bumps (feat = minor, fix = patch, breaking = major)

**Collaboration:** When you eventually share CatchBook or work with others, clear commit history reduces friction

The overhead of writing structured commits is tiny (5-10 seconds per commit). The benefit compounds over hundreds of commits across 28 phases. Let's learn the format that will serve you throughout CatchBook's entire development lifecycle.

## The Problem: Inconsistent Commit Messages in Real Projects

Before diving into the solution, let's understand the problem through real examples. Here are actual commit messages from various projects (anonymized):

**Vague and unhelpful:**
```
fix stuff
changes
update code
refactor
wip
oops
```

**Too verbose:**
```
Updated the authentication service to fix a bug where users couldn't log in if their email contained a plus sign, which is technically valid according to RFC 5322 but our regex wasn't handling it correctly, so I updated the validation logic and also added some tests
```

**Inconsistent style:**
```

fixed login bug
FEAT: Implement photo upload
refactor authentication service
```

**No context:**
```
fix bug
update function
change variable name
```

These messages fail in different ways:

**Vague messages** provide no information about what changed or why

**Verbose messages** bury the key information in a wall of text

**Inconsistent style** makes history hard to scan visually

**No context messages** force readers to examine the diff to understand the commit

The root problem: **Everyone has their own commit message style.** There's no shared structure, so commits become write-only—easy to create, impossible to search or understand later.

What we need is a **standardized format** that:
- Enforces structure without being bureaucratic
- Communicates intent clearly in the first line
- Allows detail when needed (but doesn't require it)
- Enables automated tooling
- Works for solo developers and large teams alike

That's exactly what Conventional Commits provides.

## Conventional Commits Specification Overview

Conventional Commits is an open specification (version 1.0.0) that defines a structured commit message format. Think of it as a grammar for commit messages—it doesn't dictate what you say, but it provides rules for how to say it.

The specification is intentionally lightweight. At its core, it defines:

**Required structure:**
```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

**Key principles:**

1. **Commits MUST be prefixed with a type** (feat, fix, docs, etc.)
2. **Type MAY be followed by a scope** in parentheses
3. **Type MUST be followed by a colon and space** before description
4. **Description MUST immediately follow the type/scope prefix**
5. **Description is a short summary of the code changes**
6. **Body MAY be provided after the description** to give context
7. **Footer(s) MAY be provided after the body** for metadata

The specification is maintained by the community and widely adopted across the industry. Major projects using Conventional Commits include:

- Angular (the original inspiration for this format)
- Electron
- Vue.js
- React Native
- Gatsby
- Babel

Why has it become the standard? Because it solves three problems simultaneously:

**1. Human readability:** Anyone can scan a commit log and understand changes at a glance

**2. Machine parseability:** Tools can extract structured data from commit messages

**3. Semantic versioning integration:** Commit types map directly to version bump rules

Let's break down each component of the format, starting with the anatomy of a commit message.

## Commit Message Anatomy: type(scope): description

Every conventional commit starts with a **header** that follows this pattern:

```
type(scope): description
```

Let's examine each component:

### Type (Required)

The **type** is a keyword that categorizes the commit. It answers: "What kind of change is this?"

Examples:
- `feat` → New feature for users
- `fix` → Bug fix for users
- `docs` → Documentation changes
- `refactor` → Code restructuring without changing behavior

**Rules:**
- MUST be lowercase
- MUST be one of the allowed types (defined by the spec or your project)
- MUST be followed by either `(scope):` or `:` (with a space)

### Scope (Optional)

The **scope** is a noun describing the section of codebase affected. It answers: "Where in the codebase is this change?"

Examples for CatchBook:
- `auth` → Authentication system
- `photo` → Photo capture/upload
- `species` → Species identification
- `api` → Backend API
- `ui` → User interface components

**Rules:**
- MUST be a noun (not a verb)
- MUST be enclosed in parentheses: `(scope)`
- Should be specific enough to be useful but general enough to group related commits
- Optional, but recommended for projects with multiple modules

### Description (Required)

The **description** is a concise summary of the change. It answers: "What did this commit do?"

Examples:
- `add JWT authentication`
- `fix photo upload timeout on slow networks`
- `update README installation steps`

**Rules:**
- MUST start with lowercase letter
- MUST use imperative mood ("add" not "added", "fix" not "fixed")
- MUST NOT end with a period
- Should complete the sentence: "If applied, this commit will..."

### Putting It Together

Here are complete examples for CatchBook:

```
feat(auth): add user registration endpoint
fix(photo): handle HEIC format on iOS devices
docs(readme): update installation instructions
style(ui): format catch card component
refactor(api): extract database queries to repository layer
test(species): add unit tests for classification logic
chore(deps): update react to version 18
```

Notice the pattern:
- Type is always lowercase, no exceptions
- Scope is in parentheses, describes a module/feature area
- Colon and space separate header from description
- Description starts lowercase, uses imperative mood, no period

This structure is instantly scannable. Even without reading the full commit, you can see:
- What kind of change (feat/fix/docs/etc)
- Where it happened (auth/photo/api/etc)
- What it did (high-level summary)

## Required Commit Types: feat and fix (Semantic Versioning Connection)

The Conventional Commits specification defines two **required** commit types that every project must support: `feat` and `fix`. These aren't arbitrary—they map directly to **semantic versioning** rules.

### Semantic Versioning Refresher

Semantic versioning (SemVer) uses three numbers: `MAJOR.MINOR.PATCH`

- **MAJOR** version: Breaking changes (backward incompatible)
- **MINOR** version: New features (backward compatible)
- **PATCH** version: Bug fixes (backward compatible)

Example: `CatchBook 2.3.7`
- Major version 2 (some breaking changes from v1)
- Minor version 3 (has 3 sets of new features)
- Patch version 7 (has 7 bug fixes since 2.3.0)

Conventional Commits creates a **direct mapping** between commit types and version bumps:

### feat → MINOR version bump

**Purpose:** Introduces a new feature for users

**Examples for CatchBook:**
```
feat(auth): add social login with Google
feat(photo): implement image compression
feat(species): add manual species override
feat(catch): enable offline data sync
```

**When to use:**
- Adding new functionality users will see/use
- Introducing new API endpoints
- Adding new UI components or pages
- Enabling new capabilities

**When NOT to use:**
- Internal refactoring (use `refactor`)
- Bug fixes (use `fix`)
- Performance improvements without new features (use `perf`)

**Version impact:** `1.2.3` → `1.3.0` (minor bump)

### fix → PATCH version bump

**Purpose:** Patches a bug that affects users

**Examples for CatchBook:**
```
fix(photo): resolve HEIC conversion crash
fix(auth): handle expired JWT tokens
fix(species): correct pelican classification accuracy
fix(ui): prevent catch card overlap on mobile
```

**When to use:**
- Fixing broken functionality
- Resolving crashes or errors
- Correcting incorrect behavior
- Patching security vulnerabilities

**When NOT to use:**
- Adding features (use `feat`)
- Refactoring without fixing a bug (use `refactor`)
- Updating documentation (use `docs`)

**Version impact:** `1.2.3` → `1.2.4` (patch bump)

### Breaking Changes → MAJOR version bump

Both `feat` and `fix` can include **breaking changes** (backward incompatible changes). We mark these with `!` after the type/scope:

```
feat(api)!: change authentication to OAuth2
fix(species)!: remove deprecated classification endpoint
```

**Version impact:** `1.2.3` → `2.0.0` (major bump)

We'll cover breaking changes in detail later. For now, understand that `feat` and `fix` are special because they directly drive semantic versioning.

### Why This Matters for CatchBook

When you reach Phase 21 (DevOps) and Phase 28 (Launch), you'll use tools like `semantic-release` that automatically:
1. Read your commit history
2. Determine the next version number based on commit types
3. Generate a changelog
4. Create a GitHub release

This only works if you consistently use `feat` for features and `fix` for bugs. These two types are the foundation of the entire Conventional Commits system.

## Supporting Commit Types: docs, style, refactor, test, chore, perf

Beyond the required `feat` and `fix`, Conventional Commits supports additional types for changes that don't directly affect user-facing functionality. These don't trigger version bumps but provide important context in commit history.

### docs

**Purpose:** Documentation changes only

**Examples for CatchBook:**
```
docs(readme): add API authentication guide
docs(contributing): update pull request template
docs(api): add JSDoc comments to catch service
docs(architecture): document database schema
```

**When to use:**
- README updates
- Code comments
- API documentation
- Architecture diagrams
- Contributing guidelines

**When NOT to use:**
- If code changes accompany docs (use feat/fix/refactor instead)

**Version impact:** None (documentation doesn't change functionality)

---

### style

**Purpose:** Code style/formatting changes that don't affect meaning

**Examples for CatchBook:**
```
style(ui): format catch card with prettier
style(api): fix eslint spacing warnings
style(species): add missing semicolons
style: run prettier on all files
```

**When to use:**
- Prettier/ESLint fixes
- Whitespace cleanup
- Missing semicolons
- Formatting adjustments
- Import statement reordering

**When NOT to use:**
- If formatting reveals a bug you then fix (use `fix`)
- If you refactor while formatting (use `refactor`)

**Version impact:** None (no functional changes)

---

### refactor

**Purpose:** Code changes that neither fix bugs nor add features

**Examples for CatchBook:**
```
refactor(api): extract auth logic to middleware
refactor(species): simplify classification pipeline
refactor(photo): consolidate upload handlers
refactor(catch): rename catchData to catch
```

**When to use:**
- Restructuring code without changing behavior
- Renaming variables/functions for clarity
- Extracting reusable functions
- Simplifying complex logic
- Improving code organization

**When NOT to use:**
- If you fix a bug while refactoring (use `fix`)
- If you add functionality (use `feat`)
- If just formatting (use `style`)

**Version impact:** None (behavior unchanged)

---

### test

**Purpose:** Adding or updating tests

**Examples for CatchBook:**
```
test(auth): add unit tests for JWT validation
test(species): add integration tests for AI API
test(catch): update snapshot tests for catch card
test: increase overall code coverage to 80%
```

**When to use:**
- Adding new test cases
- Updating existing tests
- Fixing broken tests
- Adding test utilities

**When NOT to use:**
- If tests are part of a feature commit (include in `feat`)

**Version impact:** None (tests don't change production code)

---

### chore

**Purpose:** Maintenance tasks that don't modify source or test files

**Examples for CatchBook:**
```
chore(deps): update react to v18.2.0
chore(build): configure webpack for production
chore(ci): add GitHub Actions workflow
chore: update .gitignore for node_modules
```

**When to use:**
- Dependency updates
- Build configuration
- CI/CD setup
- .gitignore updates
- Package.json maintenance

**When NOT to use:**
- If updating dependencies fixes a bug (use `fix`)

**Version impact:** None (infrastructure changes)

---

### perf

**Purpose:** Performance improvements without changing functionality

**Examples for CatchBook:**
```
perf(photo): optimize image compression algorithm
perf(species): cache classification results
perf(api): add database query indexing
perf(ui): lazy load catch history images
```

**When to use:**
- Optimizing algorithms
- Reducing memory usage
- Speeding up queries
- Caching strategies

**When NOT to use:**
- If performance work adds features (use `feat`)
- If fixing performance bug (use `fix`)

**Version impact:** Technically none, though some teams treat this as `PATCH`

### Choosing the Right Type

When in doubt, ask yourself:

1. **Does this add user-facing functionality?** → `feat`
2. **Does this fix broken behavior?** → `fix`
3. **Does this only change documentation?** → `docs`
4. **Does this only change formatting?** → `style`
5. **Does this restructure code without changing behavior?** → `refactor`
6. **Does this only add/update tests?** → `test`
7. **Is this infrastructure/tooling maintenance?** → `chore`
8. **Does this improve performance without changing behavior?** → `perf`

For CatchBook, you'll most commonly use:
- `feat` and `fix` (user-facing changes)
- `refactor` (code cleanup as you learn better patterns)
- `docs` (README and code comments)
- `test` (as you add test coverage in Phase 19)

## Understanding Scope: What Area of Code Is Affected

The **scope** is optional but valuable for organizing commits in projects with multiple features or modules. It's a noun in parentheses that indicates which part of the codebase changed.

### Why Use Scope?

For CatchBook, imagine you're three months in with 200+ commits. You need to review all photo-related changes before releasing the photo upload feature. With scopes, you can search for:

```
git log --oneline --grep="(photo)"
```

And immediately see:
```
feat(photo): add HEIC format support
fix(photo): handle upload timeout
refactor(photo): extract compression logic
test(photo): add integration tests
```

Without scopes, you'd have to read every commit message to find photo-related changes.

### Choosing Good Scopes for CatchBook

Scopes should map to **logical modules** in your application, not file names or technical implementation details.

**Good scopes (feature-based):**
```
auth      → Authentication and user management
photo     → Photo capture, compression, upload
species   → AI species identification
catch     → Catch logging and data management
equipment → Rod, reel, lure tracking
weather   → Weather and tide integration
api       → Backend API endpoints
ui        → Shared UI components
db        → Database schema and queries
```

**Bad scopes (too specific):**
```
catchcard.jsx          → Too file-specific
species-classification → Too verbose
backend                → Too vague
```

**Bad scopes (technical details):**
```
component    → What kind of component?
service      → What service?
utils        → Too generic
```

### Scope Consistency Rules

**1. Keep scopes stable across the project**

Once you establish scopes, use them consistently. Don't mix:
```
feat(auth): add login       ← Good
feat(authentication): ...   ← Bad (different name, same scope)
```

**2. Use the most specific scope that makes sense**

```
feat(species): add AI classification  ← Good (specific feature)
feat(api): add species endpoint       ← Less good (too broad)
feat: add species classification      ← Bad (missing useful context)
```

**3. Omit scope when changes span multiple areas**

```
refactor: restructure project architecture  ← Good (affects everything)
chore(deps): update all dependencies        ← Good (dependency updates often cross-cut)
```

### CatchBook Scope Strategy

For CatchBook, start with these core scopes (Phase 1-10):

**Frontend scopes:**
- `ui` → Shared components
- `catch` → Catch logging interface
- `photo` → Photo capture UI
- `equipment` → Equipment tracking UI
- `auth` → Login/registration UI

**Backend scopes:**
- `api` → API routes
- `db` → Database schema
- `auth` → Authentication service
- `species` → Species classification
- `weather` → Weather integration

**Infrastructure scopes:**
- `build` → Build configuration
- `ci` → CI/CD pipelines
- `deps` → Dependencies

As CatchBook grows, you can add scopes for new features:
- `social` (Phase 20: Social features)
- `analytics` (Phase 22: Analytics dashboard)
- `mobile` (Phase 27: Native mobile)

### Examples in Context

Here's how scopes help tell CatchBook's development story:

```
feat(auth): add user registration
feat(auth): implement JWT tokens
feat(db): create users table
feat(api): add /auth/register endpoint
test(auth): add registration flow tests
docs(auth): document authentication flow

feat(photo): add camera capture
feat(photo): implement HEIC conversion
fix(photo): handle iOS permission denial
perf(photo): optimize image compression
test(photo): add upload integration tests
```

See how grouping by scope creates narrative arcs? You can see the evolution of the auth system, then the photo system, all without reading full commit messages.

## Writing the Description: Imperative Mood, Lowercase, No Period

The description is the most visible part of your commit message—it's what shows in `git log --oneline` and GitHub's commit history view. Getting it right makes your history scannable and professional.

### Rule 1: Use Imperative Mood

Write descriptions as commands: "**add** feature", not "**added** feature" or "**adds** feature".

**Why?** The imperative mood completes the sentence: "If applied, this commit will **[description]**"

**Good examples:**
```
add user registration
fix photo upload timeout
update README installation steps
remove deprecated API endpoint
refactor species classification logic
```

**Bad examples:**
```
added user registration        ← Past tense
adds user registration         ← Present tense
adding user registration       ← Gerund form
user registration added        ← Passive voice
new feature for registration   ← Not imperative
```

**Test your descriptions:**
- ✅ "If applied, this commit will **add user registration**"
- ❌ "If applied, this commit will **added user registration**"

### Rule 2: Start with Lowercase

Descriptions start lowercase (unless the first word is a proper noun or acronym).

**Good examples:**
```
add JWT authentication         ← JWT is acronym, stays uppercase
fix iOS photo upload           ← iOS is proper noun
update README                  ← README is all caps
refactor catch card component  ← Regular words lowercase
```

**Bad examples:**
```
Add user registration  ← Unnecessary capitalization
Fix Bug In Upload      ← Title case
REFACTOR SPECIES API   ← All caps
```

**Exception:** If scope is omitted and type starts the line, the description still starts lowercase:
```
feat: add user registration  ← Lowercase after colon
fix: resolve upload timeout  ← Lowercase after colon
```

### Rule 3: No Ending Period

Descriptions are fragments, not sentences. Don't add a period.

**Good examples:**
```
add social login
fix memory leak in classification
update dependencies to latest versions
```

**Bad examples:**
```
add social login.
fix memory leak in classification.
update dependencies.
```

### Rule 4: Keep It Concise

Aim for 50 characters or less for the entire header (type + scope + description). Most tools truncate after 72 characters.

**Good examples (concise):**
```
feat(auth): add Google OAuth
fix(photo): handle upload retry
docs(api): update endpoint list
```

**Bad examples (too verbose):**
```
feat(auth): implement Google OAuth authentication with automatic token refresh and session management
fix(photo): fix the bug where photos don't upload correctly when the user has a slow internet connection
```

**For longer explanations, use the commit body:**
```
feat(auth): add Google OAuth

Implements full Google OAuth flow with automatic token refresh.
Users can now sign in with their Google account instead of
creating a separate CatchBook account.

Closes #42
```

### Real CatchBook Examples

Here are well-formed descriptions for various CatchBook features:

```
feat(catch): add manual location override
feat(species): implement AI classification retry logic
feat(equipment): add lure color customization
fix(photo): prevent duplicate uploads
fix(api): handle malformed JWT tokens
fix(ui): resolve catch card z-index overlap
docs(readme): add environment setup steps
docs(api): document authentication headers
refactor(catch): extract validation to separate module
refactor(species): simplify classification pipeline
test(auth): add registration validation tests
test(photo): mock EXIF data extraction
chore(deps): update react to v18.2.0
chore(build): configure production webpack
style(ui): format components with prettier
perf(photo): add image compression caching
```

Notice the pattern:
- Imperative verbs: add, implement, prevent, handle, resolve, update, extract, simplify, mock, configure, format
- Lowercase start (except proper nouns)
- No ending periods
- Concise (most under 40 characters)

### Common Mistakes to Avoid

**Mistake 1: Vague descriptions**
```
fix bug           ← What bug? Where?
update code       ← What code? Why?
refactor stuff    ← What stuff?
```

Better:
```
fix photo upload timeout on slow networks
update species classification accuracy threshold
refactor database query builders for readability
```

**Mistake 2: Too much detail in description**
```
fix(photo): fix the bug where HEIC photos from iPhone 13 and newer wouldn't convert properly because we weren't handling the new compression format
```

Better (use body for details):
```
fix(photo): handle HEIC format from iPhone 13+

The new HEIC compression format requires explicit conversion
parameters. Updated the conversion logic to detect iPhone 13+
format and apply appropriate settings.
```

**Mistake 3: Describing the diff instead of the intent**
```
refactor(api): change getUserById to fetchUserById
fix(ui): update line 42 in CatchCard.jsx
```

Better (describe the purpose):
```
refactor(api): clarify user fetching function names
fix(ui): prevent catch card overflow on mobile
```

## Breaking Changes: The ! Syntax and BREAKING CHANGE Footer

Sometimes you need to make changes that **break backward compatibility**—changes that require users or other parts of your system to update how they use a feature. Conventional Commits has specific syntax for marking these critical changes.

### What Is a Breaking Change?

A **breaking change** (also called a **backward incompatible change**) is any modification that requires existing users or integrations to change their code or configuration.

**Examples of breaking changes for CatchBook:**

**1. API contract changes:**
```
Before: GET /api/catches?userId=123
After:  GET /api/users/123/catches    ← Endpoint URL changed
```

**2. Function signature changes:**
```
Before: uploadPhoto(file)
After:  uploadPhoto(file, options)    ← Required parameter added
```

**3. Data format changes:**
```
Before: { "species": "Largemouth Bass" }
After:  { "species": { "common": "Largemouth Bass", "scientific": "Micropterus salmoides" } }
```

**4. Removed features:**
```
Before: Manual species entry supported
After:  Manual species entry removed, AI-only    ← Feature removed
```

**5. Configuration changes:**
```
Before: API_KEY environment variable
After:  AUTH_TOKEN environment variable    ← Variable renamed
```

### When Breaking Changes Matter for CatchBook

In Phase 1-10, you're working solo, so breaking changes won't affect anyone else. But you should still mark them because:

1. **Version tracking:** Breaking changes trigger MAJOR version bumps (1.2.3 → 2.0.0)
2. **Documentation:** Changelogs highlight breaking changes separately
3. **Future collaboration:** When others join CatchBook (or you open-source it), they'll know what changed
4. **API design:** Forces you to think about backward compatibility early

By Phase 15 (AI Integration) and Phase 21 (DevOps), CatchBook might have users or integrations. Breaking changes then become critical to communicate clearly.

### Syntax 1: The ! Marker

Add `!` immediately after type or scope to mark a breaking change:

**After type:**
```
feat!: change authentication to OAuth2
fix!: remove deprecated species endpoints
```

**After scope:**
```
feat(api)!: change photo upload endpoint
refactor(auth)!: rename login method
```

This is the **shorthand** syntax. It's quick and appears in the commit subject, making breaking changes visible in `git log --oneline`.

### Syntax 2: BREAKING CHANGE Footer

For more detail, use a footer starting with `BREAKING CHANGE:` or `BREAKING-CHANGE:`:

```
feat(api): change authentication to OAuth2

BREAKING CHANGE: Authentication now requires OAuth2 tokens.
JWT tokens are no longer supported. Update client code to use
the new OAuth flow. See migration guide in docs/oauth-migration.md
```

The footer provides:
- **What changed:** Authentication mechanism
- **Impact:** JWT no longer works
- **Action required:** Update client code
- **Resources:** Migration guide location

### Combining ! and BREAKING CHANGE Footer

You can use both for maximum visibility:

```
feat(api)!: change authentication to OAuth2

Replaces JWT authentication with industry-standard OAuth2 flow.
Provides better security and enables social login integration.

BREAKING CHANGE: JWT tokens no longer accepted. All API clients
must migrate to OAuth2. See docs/oauth-migration.md for details.
Migration tool available: npm run migrate-auth
```

Here:
- `!` makes it visible in short log (`git log --oneline`)
- `BREAKING CHANGE:` provides migration details in full log (`git log`)

### Real CatchBook Examples

**Example 1: API endpoint restructure**
```
feat(api)!: restructure catch endpoints for REST compliance

BREAKING CHANGE: Catch endpoints now follow RESTful conventions.
- Old: POST /catches/create
- New: POST /api/v1/catches
- Old: GET /catches/list?userId=123
- New: GET /api/v1/users/123/catches
Update all frontend API calls accordingly.
```

**Example 2: Required parameter addition**
```
feat(photo)!: require image metadata for uploads

BREAKING CHANGE: Photo upload now requires EXIF metadata object.
All uploadPhoto() calls must include metadata parameter:
uploadPhoto(file, { exif: exifData, location: gps })
```

**Example 3: Configuration change**
```
chore(config)!: rename environment variables for consistency

BREAKING CHANGE: Environment variable names updated:
- API_KEY → CATCHBOOK_API_KEY
- DB_URL → DATABASE_URL
- AWS_BUCKET → S3_BUCKET_NAME
Update .env files before deploying.
```

**Example 4: Removed feature**
```
refactor(species)!: remove manual species entry

BREAKING CHANGE: Manual species entry removed in favor of
AI-only classification. Users must use photo-based identification.
For edge cases, use the "Report Incorrect Classification" feature.
```

### Version Impact

Breaking changes trigger **MAJOR** version bumps regardless of commit type:

```
feat(api)!: ...     → 1.2.3 → 2.0.0
fix(auth)!: ...     → 1.2.3 → 2.0.0
refactor(db)!: ...  → 1.2.3 → 2.0.0
```

This follows semantic versioning rules:
- MAJOR version = incompatible API changes
- MINOR version = backward-compatible features
- PATCH version = backward-compatible bug fixes

### When NOT to Use Breaking Changes

**Don't mark these as breaking:**

**1. Internal refactoring (no API changes):**
```
refactor(api): reorganize route handlers    ← Not breaking
```

**2. Additive changes (backward compatible):**
```
feat(catch): add optional notes field       ← Not breaking
```

**3. Bug fixes that restore documented behavior:**
```
fix(api): return correct HTTP status codes  ← Not breaking
```

**4. Deprecation warnings (feature still works):**
```
feat(api): deprecate old auth endpoint      ← Not breaking yet
```

Mark something breaking only if it **requires users to change their code**.

### Best Practices for Breaking Changes

**1. Bundle breaking changes together**

Instead of:
```
feat(api)!: rename species endpoint
feat(api)!: rename catch endpoint
feat(api)!: rename user endpoint
```

Do:
```
feat(api)!: restructure all API endpoints for v2

BREAKING CHANGE: All endpoints now under /api/v2.
See migration guide for full mapping.
```

**2. Provide migration paths**

Always explain how to adapt:
```
BREAKING CHANGE: useAuth() now returns object instead of array.
Before: const [user, login, logout] = useAuth()
After:  const { user, login, logout } = useAuth()
```

**3. Use deprecation warnings first (when possible)**

```
Phase 15: feat(auth): add OAuth support (JWT still works)
Phase 16: feat(auth): deprecate JWT (warning logged)
Phase 17: feat(auth)!: remove JWT support (breaking change)
```

**4. Document in changelogs**

Tools like `semantic-release` automatically create "BREAKING CHANGES" sections in release notes, making them highly visible.

## Optional Commit Body: Explaining What and Why, Not How

The commit header (type, scope, description) is required, but the **body** is optional. Use it when you need to explain context that doesn't fit in 50 characters.

### When to Include a Body

**Include a body when:**

**1. Changes are complex or non-obvious:**
```
refactor(species): simplify classification pipeline

Previous implementation used three separate API calls sequentially.
New implementation batches all requests into a single call,
reducing latency from ~3s to ~800ms. Maintains identical results.
```

**2. Explaining the "why" behind the change:**
```
fix(photo): add retry logic for failed uploads

Users on slow networks reported uploads timing out frequently.
Added exponential backoff retry (3 attempts, max 30s total).
Improves success rate from 87% to 99% on poor connections.
```

**3. Describing trade-offs or decisions:**
```
feat(catch): implement client-side photo compression

Compressing photos client-side reduces server load and bandwidth.
Trade-off: Slightly slower upload preparation on low-end devices.
Compression is optional and can be disabled in settings.
```

**4. Breaking changes need context:**
```
feat(api)!: migrate to GraphQL

REST API was becoming unwieldy with 40+ endpoints and complex
nested queries. GraphQL provides better type safety, reduces
over-fetching, and simplifies client data requirements.

BREAKING CHANGE: All REST endpoints deprecated. Migrate to
GraphQL API by Phase 20. See docs/graphql-migration.md
```

### When to Skip the Body

**Skip the body when:**

**1. The header is self-explanatory:**
```
fix(ui): correct catch card padding    ← Obvious, no body needed
docs(readme): fix typo                  ← Self-explanatory
style(api): run prettier                ← No context needed
```

**2. Changes are trivial:**
```
chore(deps): update react to v18.2.0    ← Routine maintenance
test(auth): add missing assertion       ← Simple test update
```

**3. You'd just be repeating the header:**
```
feat(catch): add manual location override

This commit adds the ability to manually override location.   ← Redundant
Users can now manually override the GPS location.             ← Redundant
```

### Body Formatting Rules

**1. Separate body from header with a blank line:**
```
feat(photo): add HEIC format support
                                    ← Blank line required
HEIC (High Efficiency Image Format) is the default on iOS 11+.
Added conversion to JPEG for cross-platform compatibility.
```

**2. Wrap lines at 72 characters:**
```
This line is exactly 72 characters long, wrapping here nicely for term
```

Why 72? Git adds 4 spaces of padding when displaying commits. 72 + 4 = 76, which fits in an 80-character terminal window.

**3. Use present tense, explain what and why:**

**Good:**
```
Refactors the classification pipeline to use batch processing.
This reduces API calls from N (one per photo) to 1 (batch),
significantly improving performance for multi-photo uploads.
```

**Bad:**
```
I refactored the code.                    ← Vague, past tense
The classification function is changed.   ← Passive voice
Use batch processing.                     ← Imperative (save for description)
```

**4. Use bullet points for lists:**
```
Changes include:
- Add HEIC to JPEG conversion
- Support iOS 11+ photo formats
- Maintain EXIF data during conversion
- Add fallback for unsupported formats
```

### Body vs. Description: What Goes Where?

**Description:** High-level summary (what changed)
**Body:** Context, rationale, impact (why it changed, how it affects things)

**Example:**
```
feat(species): cache classification results

Header explains WHAT: caching is added

Caches AI classification results in Redis with 24-hour TTL.
Reduces API calls to classification service by ~80% for
frequently photographed species. Cache is invalidated when
model is updated. Memory usage impact: +50MB average.

Body explains WHY (reduce API calls), HOW MUCH (80% reduction),
SIDE EFFECTS (memory usage), and EDGE CASES (cache invalidation).
```

### Real CatchBook Body Examples

**Example 1: Feature with trade-offs**
```
feat(photo): implement client-side compression

Compresses photos to max 2MB before upload to reduce bandwidth
and server storage costs. Uses browser-native canvas API for
cross-platform compatibility.

Trade-offs:
- Slower on low-end devices (~2s compression time)
- Loss of original quality (acceptable for fishing logs)
- Cannot compress if canvas API unavailable (fallback to original)

Performance: Reduces average upload from 8MB to 1.8MB (77% savings)
```

**Example 2: Complex refactoring**
```
refactor(api): extract database queries to repository pattern

Previous implementation scattered SQL queries across route handlers,
making testing difficult and violating separation of concerns.

Changes:
- Create repository layer for each entity (User, Catch, Species)
- Move all queries from routes to repositories
- Add dependency injection for testability
- Update tests to mock repositories instead of database

No behavior changes, but enables future features:
- Easy database migration (PostgreSQL → MongoDB)
- Better test coverage (mock repositories)
- Clearer separation of concerns
```

**Example 3: Bug fix with root cause**
```
fix(auth): prevent token refresh infinite loop

Root cause: Token refresh triggered by 401 response, but refresh
endpoint also returned 401 when refresh token expired, causing
infinite retry loop and browser hang.

Solution: Detect refresh endpoint 401 specifically and logout user
instead of retrying. Added max retry limit (3) as safety mechanism.

Tested: Manual token expiration, clock skew scenarios, network interruption
```

### Think of the Future

Write bodies for **future you** and **future collaborators**. Six months from now, you won't remember why you made a decision. The body preserves context:

```
feat(catch): store catches in IndexedDB for offline support

Initially considered localStorage but it's limited to 5-10MB.
IndexedDB provides ~50MB+ storage and better performance for
structured data. Required for Phase 23 (PWA offline mode).

Implementation notes:
- Uses Dexie.js wrapper for simpler API
- Syncs to server when connection restored
- Conflict resolution: server wins (for now)
```

This body explains:
- **Why IndexedDB over localStorage** (capacity and structure)
- **Future dependency** (Phase 23 PWA)
- **Implementation choices** (Dexie.js)
- **Known limitations** (server wins conflicts)

Six months later, you'll thank yourself for this context.

## Optional Commit Footer: Issue References and Metadata

The **footer** is the last section of a commit message, separated from the body by a blank line. It contains metadata like issue references, breaking change notices, and other structured information.

### Footer Format: Token: Value

Footers follow this pattern:
```
<token>: <value>
```

Or for multi-word tokens:
```
<token> #<value>
```

Common tokens:
- `Closes:` or `Fixes:` or `Resolves:` → Link to resolved issues
- `Refs:` or `References:` → Link to related issues
- `BREAKING CHANGE:` → Breaking change description
- `Reviewed-by:` → Code reviewer
- `Co-authored-by:` → Multiple authors
- Custom tokens for project-specific metadata

### Issue References: Closes, Fixes, Resolves

GitHub automatically closes issues when commits containing these keywords are merged:

**Single issue:**
```
fix(photo): handle upload timeout

Adds retry logic with exponential backoff.

Closes #42
```

**Multiple issues:**
```
feat(auth): implement OAuth2 login

Adds Google and GitHub OAuth providers.

Closes #15
Closes #27
Closes #33
```

**Alternative syntax:**
```
Fixes #42           ← Also works
Resolves #42        ← Also works
Closes: #42         ← Colon syntax
```

### References (Without Closing)

Use `Refs` or `References` to link issues without closing them:

```
feat(species): add manual classification override

Allows users to correct AI misidentifications.

Refs #23
Refs #45
```

This links the commit to issues #23 and #45 but doesn't close them (useful for partial implementations or related work).

### Multiple Footers

You can combine multiple footers:

```
feat(api)!: migrate to GraphQL

REST API deprecated in favor of GraphQL for better type safety
and reduced over-fetching.

BREAKING CHANGE: All REST endpoints removed. See migration guide.
Closes #102
Closes #103
Reviewed-by: @senior-dev
```

### CatchBook Footer Examples

**Example 1: Bug fix closing issue**
```
fix(photo): prevent duplicate upload on slow networks

Added debounce logic to upload button (500ms delay).
Tracks in-flight requests to prevent race conditions.

Closes #67
```

**Example 2: Feature closing multiple issues**
```
feat(equipment): add lure color and size tracking

Users can now specify lure color (8 options) and size range.
Enables better catch pattern analysis in Phase 22.

Closes #88
Closes #92
Refs #105
```

**Example 3: Breaking change with references**
```
feat(api)!: restructure catch data schema

Normalizes catch data to separate species, location, and
conditions into distinct tables for better query performance.

BREAKING CHANGE: Catch API response format changed.
Old: { catch: { species: "Bass", location: {...} } }
New: { catch: {...}, species: {...}, location: {...} }
See docs/api-v2-migration.md for details.

Closes #120
Refs #115
```

**Example 4: Documentation with references**
```
docs(api): document authentication flow

Adds comprehensive auth docs with diagrams and examples.
Includes OAuth2 flow, token refresh, and error handling.

Refs #42
Refs #56
```

### Co-authored-by: Multiple Contributors

If you pair program or someone contributes to your commit:

```
feat(species): implement AI classification API

Initial implementation of species ID using Claude API.
Returns species name, confidence score, and fallback suggestions.

Co-authored-by: Alice Johnson <alice@example.com>
Co-authored-by: Bob Smith <bob@example.com>
```

GitHub recognizes this syntax and credits all authors.

### Reviewed-by: Code Review Credit

After PR review:

```
fix(auth): handle expired refresh tokens

Gracefully handles token expiration by redirecting to login
instead of throwing unhandled exception.

Reviewed-by: @tech-lead
Closes #89
```

### Custom Tokens for CatchBook

You can define project-specific footer tokens:

```
feat(catch): add weather data integration

Fetches weather conditions at catch time using OpenWeather API.
Stores temperature, conditions, wind speed, and barometric pressure.

Phase: P07
Closes #134
Tested-on: iOS 16, Android 13
```

Custom tokens:
- `Phase:` → Links commit to curriculum phase
- `Tested-on:` → Platform testing notes

### Footer Formatting Rules

**1. Blank line before footer:**
```
feat(photo): add compression

[Body text here]
                          ← Blank line required
Closes #42
```

**2. Multi-line footers use hanging indent:**
```
BREAKING CHANGE: Authentication system migrated to OAuth2.
  JWT tokens no longer supported. All API clients must update
  to OAuth flow. See migration guide for details.
```

**3. Footer order convention:**
```
[Body]

BREAKING CHANGE: ...    ← Breaking changes first (if any)
Closes #42              ← Issue closures
Refs #15                ← References
Reviewed-by: ...        ← Credits
Co-authored-by: ...     ← Co-authors
```

### When to Use Footers

**Always include footers when:**
- Closing or referencing GitHub issues
- Marking breaking changes (use `BREAKING CHANGE:` footer)
- Crediting co-authors or reviewers

**Optionally include when:**
- Adding project-specific metadata
- Linking to external resources
- Documenting test coverage

**Skip footers when:**
- No issues to reference
- No breaking changes
- Solo work with no reviewers

### Complete Footer Example

```
feat(api)!: migrate authentication to OAuth2

Replaces JWT-based auth with industry-standard OAuth2 flow.
Enables social login integration (Google, GitHub, Apple).
Improves security with automatic token rotation.

Migration steps:
1. Update API clients to use OAuth2 endpoints
2. Configure OAuth providers in .env
3. Run migration script: npm run migrate-auth-tokens

BREAKING CHANGE: JWT authentication removed. All API clients
  must migrate to OAuth2. JWT tokens issued before this change
  will be rejected. See docs/oauth-migration.md for details.
Closes #102
Closes #103
Refs #89
Reviewed-by: @senior-dev
Tested-on: iOS 16, Android 13, Web (Chrome/Firefox/Safari)
```

This commit has:
- **Header:** Type, scope, description, breaking change marker
- **Body:** What changed, why, and how to migrate
- **Footer:** Breaking change details, issue closures, references, reviewer credit, test coverage

## How Conventional Commits Enable Automated Tools

One of the most powerful benefits of Conventional Commits is **machine parseability**—tools can read your commit history and automate tedious tasks. This section shows how structured commits unlock automation that will save you hours as CatchBook grows.

### Semantic Versioning Automation

Tools like **semantic-release** read commit types and automatically determine the next version number:

**Commit history:**
```
fix(photo): handle upload timeout          → Patch bump
fix(auth): prevent token refresh loop      → Patch bump
feat(species): add confidence scores       → Minor bump
docs(api): update authentication guide     → No bump
```

**Result:** Version `1.2.3` → `1.3.0`

Why 1.3.0? The `feat` commit triggers a minor bump. Bug fixes are already included in that bump. Docs don't affect version.

**With breaking changes:**
```
feat(api)!: migrate to GraphQL             → Major bump
fix(auth): handle expired tokens           → Included in major
```

**Result:** Version `1.2.3` → `2.0.0`

The `!` or `BREAKING CHANGE:` footer triggers a major version bump.

**Manual versioning (what you'd do without this):**
```
$ git log                        # Read all commits
$ ...                            # Determine if changes are breaking
$ ...                            # Decide on version number
$ npm version 2.0.0              # Manual bump
$ git tag v2.0.0                 # Manual tag
$ git push --tags                # Push tag
```

**Automated versioning (with semantic-release):**
```
$ npm run release                # Analyzes commits, bumps version, creates tag, pushes
```

This will be invaluable in Phase 21 (DevOps) and Phase 28 (Launch) when you're releasing CatchBook versions frequently.

### Automated Changelog Generation

Tools like **conventional-changelog** parse commits and generate structured release notes:

**Commit history:**
```
feat(species): add AI classification
feat(photo): implement HEIC conversion
fix(auth): prevent token refresh loop
fix(ui): resolve catch card overlap
docs(api): update authentication guide
chore(deps): update react to v18
```

**Generated changelog:**
```markdown
# 1.3.0 (2025-01-24)

### Features

* **species:** add AI classification ([abc123](link))
* **photo:** implement HEIC conversion ([def456](link))

### Bug Fixes

* **auth:** prevent token refresh loop ([ghi789](link))
* **ui:** resolve catch card overlap ([jkl012](link))
```

Notice:
- Features and bug fixes are separate sections
- Docs and chore commits are omitted (not user-facing)
- Scopes are preserved
- Commit hashes are linked

**With breaking changes:**
```markdown
# 2.0.0 (2025-01-24)

### ⚠ BREAKING CHANGES

* **api:** Authentication migrated to OAuth2. JWT tokens no longer supported.

### Features

* **api:** migrate to OAuth2 authentication ([mno345](link))
```

Breaking changes get their own prominent section at the top.

**Manual changelog (without this):**
```
# 1.3.0
- Added some features
- Fixed some bugs
- Updated dependencies
```

Vague, unhelpful, time-consuming to write.

**Automated changelog (with conventional-changelog):**
```
$ npx conventional-changelog -p angular -i CHANGELOG.md -s
```

Generates a beautiful, structured changelog in seconds.

### GitHub Release Notes Automation

When combined with GitHub Actions, conventional commits enable fully automated releases:

**Workflow:**
1. Push commits to `main` branch
2. GitHub Actions runs `semantic-release`
3. Tool analyzes commit types
4. Determines version bump (major/minor/patch)
5. Updates `package.json` version
6. Generates changelog
7. Creates GitHub release with notes
8. Publishes to npm (if applicable)
9. Deploys to production (if configured)

**All of this happens automatically because your commits follow a standard format.**

### Commit Linting (Enforcing Standards)

Tools like **commitlint** validate commit messages in CI/CD:

**Invalid commit (caught before merge):**
```
$ git commit -m "fixed bug"

⧗   input: fixed bug
✖   type may not be empty [type-empty]
✖   subject may not be empty [subject-empty]
✖   found 2 problems, 0 warnings
```

**Valid commit (passes):**
```
$ git commit -m "fix(photo): handle upload timeout"

✔   found 0 problems, 0 warnings
```

This prevents inconsistent commits from polluting your history. You'll set this up in Phase 2 (Professional Tooling).

### Searchable History

Conventional commits make `git log` incredibly powerful:

**Find all features:**
```
$ git log --oneline --grep="^feat"
```

**Find all auth-related changes:**
```

```

**Find all breaking changes:**
```

```

**Find all bug fixes in the photo module:**

```

**Generate a feature list for a release:**
```

This would be impossible with inconsistent commit messages.

## CatchBook Commit Strategy: Planning Our Conventions

Now that you understand Conventional Commits, let's define the specific conventions CatchBook will use across all 28 phases.

### Core Commit Types for CatchBook

CatchBook will use these standard types:

| Type | Purpose | Example |
|------|---------|---------|
| `feat` | New user-facing features | `feat(species): add AI classification` |
| `fix` | Bug fixes | `fix(photo): handle upload timeout` |
| `docs` | Documentation only | `docs(readme): update setup steps` |
| `style` | Formatting, no code change | `style(ui): run prettier on components` |
| `refactor` | Code restructuring | `refactor(api): extract auth middleware` |
| `test` | Add or update tests | `test(catch): add integration tests` |
| `chore` | Maintenance tasks | `chore(deps): update react to v18` |
| `perf` | Performance improvements | `perf(photo): cache compressed images` |

**No custom types.** These eight cover all scenarios you'll encounter.

### Scopes for CatchBook

Start with these scopes in Phase 1-10:

**Feature scopes:**
- `auth` → Authentication and user management
- `photo` → Photo capture, upload, processing
- `species` → Species identification
- `catch` → Catch logging and data management
- `equipment` → Rod, reel, lure tracking
- `weather` → Weather and tide integration
- `ui` → Shared UI components
- `api` → Backend API
- `db` → Database schema and queries

**Infrastructure scopes:**
- `build` → Build configuration (webpack, vite)
- `ci` → CI/CD pipelines
- `deps` → Dependencies
- `config` → Environment configuration

As CatchBook grows, add scopes for new features:
- `social` (Phase 20: Social features)
- `analytics` (Phase 22: Analytics dashboard)
- `mobile` (Phase 27: Native mobile app)

**Scope rules:**
- Use lowercase
- Use singular form (`photo` not `photos`)
- Be consistent (always `auth`, never `authentication`)

### When to Use Scope vs. Omit It

**Use scope when:**
- Change affects a specific module (most commits)
- You want commits grouped by feature area

**Omit scope when:**
- Change spans multiple modules: `feat: add offline mode`
- Trivial changes: `chore: update .gitignore`
- Project-wide refactoring: `refactor: migrate to TypeScript`

### Description Style for CatchBook

Follow these patterns:

**Features:**
```
feat(photo): add batch upload
feat(species): implement confidence scores
feat(catch): enable manual location override
```

**Bug fixes:**
```
fix(auth): handle expired tokens
fix(photo): prevent duplicate uploads
fix(ui): resolve card overflow on mobile
```

**Refactoring:**
```
refactor(api): extract validation to middleware
refactor(catch): simplify data transformation
refactor(db): consolidate query builders
```

**Pattern:** `<action> <what>` where action is imperative verb

**Common actions:**
- add, implement, enable (for features)
- fix, resolve, prevent, handle (for bugs)
- extract, simplify, consolidate, migrate (for refactoring)
- update, upgrade (for dependencies)

### Body Guidelines for CatchBook

Include a body when:

**1. Explaining non-obvious decisions:**
```
feat(photo): use JPEG for iOS HEIC photos

HEIC format provides better compression but isn't supported
on Android or web browsers. Converting to JPEG ensures
cross-platform compatibility at the cost of ~15% larger files.
```

**2. Documenting performance impacts:**
```
perf(species): cache classification results

Caches AI responses for 24 hours, reducing API calls by ~80%.
Memory impact: +50MB average. Cache invalidated on model updates.
```

**3. Providing migration steps:**
```
feat(api)!: restructure catch endpoints

BREAKING CHANGE: Endpoint structure changed for REST compliance.
Migration: Update API calls from /catches/create to /api/v1/catches
See docs/api-migration.md for full mapping.
```

**4. Listing changes in large refactorings:**
```
refactor(catch): modularize catch logging flow

Changes:
- Extract photo upload to separate service
- Move EXIF parsing to utility module
- Consolidate validation in middleware
- Update tests to use new architecture
```

### Footer Strategy for CatchBook

**Always include:**
- `Closes #N` when implementing features or fixing bugs tracked in issues
- `BREAKING CHANGE:` when making backward-incompatible changes

**Optionally include:**
- `Refs #N` for related issues
- Custom tokens like `Phase: P07` to link commits to curriculum phases

**Example with all footers:**
```
feat(species)!: migrate to Claude API v3

Upgrades from Claude API v2 to v3 for better accuracy and
lower latency. Classification accuracy improves from 87% to 94%.

BREAKING CHANGE: API response format changed.
Old: { species: "Bass", confidence: 0.9 }
New: { species: { common: "Bass", scientific: "..." }, confidence: 0.9 }

Update frontend to handle new response structure.

Phase: P15
Closes #234
Refs #189
```

### Commit Frequency for CatchBook

**Commit often:**
- After completing a logical unit of work
- Before switching tasks
- At the end of each coding session
- When tests pass

**Good commit cadence:**
```
feat(photo): add camera capture UI
test(photo): add camera permission tests
feat(photo): implement photo preview
refactor(photo): extract camera logic to hook
fix(photo): handle permission denial gracefully
```

**Bad commit cadence:**
```
feat(photo): complete entire photo upload feature
```

The first approach creates a readable history. The second creates a massive, hard-to-review commit.

### Pre-commit Checklist

Before committing, verify:

1. **Format:** `type(scope): description`
2. **Type:** Valid type (feat, fix, docs, etc.)
3. **Scope:** Lowercase, singular, consistent
4. **Description:** Imperative mood, lowercase, no period, <50 chars
5. **Body:** Blank line before body, wrapped at 72 chars
6. **Footer:** `Closes #N` if implementing/fixing tracked issue
7. **Tests:** All tests passing (when applicable)

Here are examples you'll likely write in the next few phases:

**Phase 1 (Foundations):**

## Summary

You've mastered the Conventional Commits specification, a standardized format that will transform your Git history from random notes into structured documentation. This foundation will serve you throughout CatchBook's entire 28-phase development lifecycle.

**You've learned:**

1. **Why commit consistency matters:** CatchBook will have hundreds of commits across 28 phases. Structured messages make history searchable, understandable, and enable automation for changelogs and versioning.

2. **Commit message anatomy:** Every conventional commit follows `type(scope): description` with optional body and footer. Type and description are required; scope, body, and footer are optional but recommended.

3. **Required types (feat/fix):** Map directly to semantic versioning—`feat` triggers minor version bumps (1.2.3 → 1.3.0), `fix` triggers patch bumps (1.2.3 → 1.2.4), and breaking changes trigger major bumps (1.2.3 → 2.0.0).

4. **Supporting types:** Eight standard types cover all scenarios—feat, fix, docs, style, refactor, test, chore, perf. No need for custom types; these handle everything you'll encounter in CatchBook development.

5. **Scopes organize by module:** Use lowercase, singular nouns (auth, photo, species, catch) to group commits by feature area, making history scannable and searchable by module.

6. **Description rules:** Imperative mood ("add" not "added"), lowercase start, no ending period, under 50 characters. Should complete: "If applied, this commit will [description]."

7. **Breaking changes syntax:** Use `!` after type/scope for visibility in short logs, plus `BREAKING CHANGE:` footer for migration details. Both together maximize clarity for backward-incompatible changes.

8. **Optional body for context:** Use body to explain why (not how), document trade-offs, provide migration steps, or list changes in complex commits. Wrap at 72 characters, separate from header with blank line.

9. **Footers for metadata:** Use `Closes #N` to link and close issues, `Refs #N` for related issues, `BREAKING CHANGE:` for incompatible changes, and custom tokens for project-specific metadata.

10. **Automation enablement:** Structured commits unlock semantic versioning automation (semantic-release), changelog generation (conventional-changelog), commit linting (commitlint), searchable history, and complete CI/CD workflows—all from one well-formatted commit message.

**Next steps:**

In the next lesson (P01-M03-L02), you'll practice writing conventional commits for real CatchBook scenarios. You'll compose commit messages following the format, review examples, and get hands-on experience with the tools that enforce and utilize these conventions.

By the end of Module 3, conventional commits will be second nature, and you'll have established the repository hygiene patterns that will support CatchBook's evolution across all 28 phases—from first commit to production launch.
