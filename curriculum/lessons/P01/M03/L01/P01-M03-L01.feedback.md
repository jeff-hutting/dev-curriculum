## Checkpoint 4 (75 minutes)

**Your Response:**

1. The `!` syntax is used to denote a breaking change that has been introduced. This likely requires the end-user to upgrade or make changes to their configuration in order to maintain usability/progress in an app or project. A breaking change for CatchBook might include something like removing a feature or changing a configuration.

User will not see a difference, but the internal implementation is 
entirely different.

Closes #57

**Professor Feedback:**

Excellent responses, Jeff! You've grasped the core concepts of breaking changes and commit bodies.

Your breaking change understanding is fundamentally correct: "The `!` syntax is used to denote a breaking change... likely requires the end-user to upgrade or make changes to their configuration in order to maintain usability/progress." A breaking change is any modification that requires action from users/developers to maintain existing functionality. This includes removing features, changing public API signatures, modifying configuration formats, renaming environment variables, changing default behavior, and updating minimum dependency versions.

One clarification: changing configuration format/structure is breaking, but changing configuration values (unless it drastically alters behavior) is not breaking. For example, changing from `"maxSize": 10000000` to `"maxSizeMB": 10` (different key name) is breaking, but changing from `"maxSize": 10000000` to `"maxSize": 50000000` (just increased limit) is not breaking.

Your description vs body explanation is excellent: "A commit body should be included when changes aren't explicitly obvious or may be kinda complex for future-me or collaborators to glean from a commit header alone." Exactly right. Include a body when explaining complex "why", documenting breaking changes, describing multiple related changes, providing implementation details, or explaining trade-offs and decisions. The "Would Future Me Understand?" test: if you'd understand why from just the header in 6 months, no body needed. If not, add body explaining why.

Your photo upload commit message is good work with the right structure. For type choice with memory leaks, choose `fix` if users were experiencing crashes/issues, `refactor` if you proactively replaced it before issues, or `perf` if performance improved as well. Your header `fix(photo): memory leak caused by zlib` is good, but could be refined to `fix(upload): resolve memory leak in photo compression` to focus on the solution rather than the problem.

Your body content is good, but could be enhanced with more structure: technical changes section documenting what actually changed, user impact section answering "why should I care?", test coverage mentioned to show thoroughness, and quantified improvements (like "~15% faster compression"). You correctly wrapped lines at reasonable length under 72 characters, which many developers miss.

You're demonstrating breaking change understanding (requires user action), body purpose clarity (explain non-obvious "why" and decisions), structural thinking (type + scope + description + body + footer), and user empathy ("User will not see a difference" shows you think about impact). One area to strengthen: type selection when you have multiple valid options (fix/refactor/perf)—think about primary motivation, user perspective, and SemVer impact.
