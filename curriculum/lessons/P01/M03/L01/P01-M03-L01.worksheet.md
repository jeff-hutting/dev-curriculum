## Checkpoint 1 (20 minutes)

**Questions:**

1. In your own words, explain why commit message consistency matters for CatchBook development.
2. What are the three parts of a conventional commit header? Which are required and which are optional?
3. Given this commit: `feat(species): add AI classification API`, identify the type, scope, and description. What does each part tell you about the change?

**Answers:**

1. There are several reasons that message consistency matters for ANY development. Commit messages need to be concise, but informative. The need to be human AND machine readable, useful in search queries, yet not too wordy. Quality, consistent commit messages will drive Semantic Versioning as the project develops. Adding proper context to commit messages will also help in collaborative efforts down the road.

2. A conventional commit header consists of a type, a scope, and a short description. Type and Description are required, a scope is optional. It should be noted that whether or not a scope is included, the type must be followed immediately by a colon and a space immediately preceding a description.

3. The type is 'feat', the scope is (species), and the description is 'add AI classification API'. The type tells me that this is a commit related to a feature, the scope infers that this commit has to do with species identification, and the description tells me that we added an API to enable AI species classification.

## Checkpoint 2 (40 minutes)

**Questions:**

1. What's the difference between `feat` and `fix` in terms of semantic versioning? How does each affect the version number?
2. You're working on CatchBook and you extract database query logic into a separate service file without changing any functionality. Which commit type should you use and why?
3. For each of these scenarios, identify the correct commit type:
   - Adding species identification confidence scores to the UI
   - Fixing a crash when uploading photos larger than 10MB
   - Running Prettier to format all JavaScript files
   - Updating the README with installation instructions

**Answers:**

1. `feat` will often add new user-facing features, and would likely bump a version from, for example, 1.1.0 to 1.2.0. A `fix` would most likely squash a bug, increase app stability, or the like. As such, we would see a bump from, say, 1.1.0 to 1.1.1.

2. I would say refactor would be most likely. `refactor(db): extract query logic to service file` may be something I would write as a commit header. This would be a code change that doesn't affect any of the apps functionality, so I'd use refactor. If the intent was to increase efficiency/performance, I may opt for `perf` in that case.

3. 1) feat(species): add ID confidence scores to UI  2) fix(photo): crash on U/L over 10MB  3) style(js): prettier format across js files  4) docs(README): add installation instructions

## Checkpoint 4 (75 minutes)

**Questions:**

1. When should you use the `!` syntax in a commit header? Provide a CatchBook example of a breaking change and explain why it's breaking.
2. What's the difference between the commit description and the commit body? When should you include a body?
3. You've just refactored the photo upload system to use a new compression library because the old one had memory leaks. The functionality is identical from the user's perspective, but the internal implementation is completely different. Write a complete commit message (header + body) following Conventional Commits format.

**Answers:**

1. The `!` syntax is used to denote a breaking change that has been introduced. This likely requires the end-user to upgrade or make changes to their configuration in order to maintain usability/progress in an app or project. A breaking change for CatchBook might include something like removing a feature or changing a configuration. 

2. A commit body should be included when changes aren't explicitly obvious or may be kinda complex for future-me or collaborators to glean from a commit header alone. I may need to explain the 'why' for a commit a little deeper than a 52-character header allows. Sometimes things like trade-offs or certain decisions need to be explained more in-depth, and a commit body allows that. Breaking Changes often need more context then a simple header provides.

3. 
fix(photo): memory leak caused by zlib

Moved from zlib compression library to libdeflate. 
User will not see a difference, but the internal implementation is 
entirely different.
