## Checkpoint 1 (20 minutes)

**Questions:**

1. Explain the difference between Git and GitHub in your own words. Use an analogy if it helps.
2. What are the three most important reasons (in your opinion) for pushing CatchBook to GitHub?
3. If you make a commit locally but don't push it to GitHub, where does that commit exist? What happens if your computer crashes before you push?

**Answers:**

1. Git is the Version Control Software that operates on my local machine. GitHub is a remote server that stores a copy of my local repository and is built on Git's architecture. GitHub is a solution for Disaster Recovery, working on multiple machines, collaboration, and creating a professional portfolio of projects.

2. The most important reason for me to push CatchBook to GitHub is Disaster Recovery. Second is portfolio building (for now), and third would be collaboration.

3. The local commit is stored in the .git/ directory of the the local repo. If by 'crash' you mean it freezes and I need to do a hard-reset of my machine, I'll assume nothing was lost locally. If by 'crash' you mean dropped overboard from a kayak and is now resting at the bottom of Lake Berryessa, it means that everything I haven't pushed to GitHub yet is lost and I need to restore from my latest GitHub repo on my new machine when it arrives (I really hope this doesn't happen!).

## Checkpoint 3 (60 minutes)

**Questions:**

1. What does `git remote add origin <URL>` do? Why is the remote typically named "origin"?
2. Explain what the `-u` flag does in `git push -u origin main`. Why would you use it?
3. After you've pushed, where does your CatchBook code now exist? (List all locations.)

**Answers:**

1. This command links my local repository to a remote repository at the location <URL>. The remote is typically named 'origin' mostly because everyone else does it - it's a common naming convention. Can be named anything, really, but for consistency's sake, we call it 'origin'

2. The -u flag sets upstream tracking. It creates a link between my local branch and the remote one. Mostly for convenience, it allows for git push or git pull commands without listing origin main every single time. 

3. Once pushed, the CatchBook code exists in my local repo and in my GitHub repo.

## Checkpoint 4 (80 minutes)

**Questions:**

1. What is the difference between `git fetch` and `git pull`?
2. Describe a scenario where you'd use `git clone` for CatchBook.
3. If you're working on CatchBook from two computers (desktop and laptop), what's the typical workflow to keep them in sync?

**Answers:**

1. `git pull` is basically `git fetch` and `git merge` rolled into one command. `git fetch` will retrieve the remote commits, but not merge them to your local branch automatically. You can review the commits through the `git log` command and then merge once approved. `git pull` is fine for solo developers since no one else (should!) be making changes but me.

2. I would use `git clone` when I need to work from another machine and there isn't copy of my repo on the new machine yet.

3. (Desktop) --> `git commit` --> `git push` --> (Laptop) `git pull` --> `git commit` --> `git push` --> (Desktop) `git pull`
